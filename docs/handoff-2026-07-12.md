# Handoff 2026-07-12

Date: 2026-07-12  
Status: Final Design layout fidelity 운영 반영 완료, 브랜드 스타일 fidelity는 별도 트랙  
Scope: n8n 3단계 Worker, Admin LLM 설정, LO-FI → Final 이미지 편집, 실패 처리, 운영 검증

## Executive Summary

오늘은 `Integrated Brief → LO-FI Draft → Final Design` 3단계 n8n 흐름을 점검하고, LO-FI와 Final 결과가 크게 달라지던 핵심 원인을 해결했다.

핵심 원인은 운영 Final Worker가 Confirm된 LO-FI 이미지를 입력으로 사용하지 않고 OpenAI `/v1/images/generations`로 새 이미지를 생성하던 구조였다. 이를 Confirmed LO-FI binary를 전달하는 `/v1/images/edits` multipart 호출로 변경하고 `input_fidelity=high`를 적용했다.

백업 Worker에서 실패·성공 경로를 검증한 뒤 운영 `Promo Final Design Worker`에 동일 구조를 게시했다. 운영 실행 `1181`이 성공했으며 DB의 `ready`, `final_design_ready`, 이미지 URL 저장, `referenceMode=image_edit`를 확인했다. LO-FI와 Final 이미지를 직접 비교한 결과 주요 영역의 순서와 상대 위치가 유지됐다.

OpenAI API 키는 사용자 결정에 따라 n8n HTTP Request 노드에 유지했다. 저장소의 export fixture에는 실제 키를 포함하지 않는다.

## 1. 주요 결론

### 1.1 LO-FI와 Final 차이의 직접 원인

변경 전 Final Worker:

```text
Prompt only
→ POST /v1/images/generations
→ LO-FI 이미지 입력 없음
→ 새로운 레이아웃 생성
```

변경 후 Final Worker:

```text
Confirmed LO-FI proxy URL
→ LO-FI binary 다운로드
→ POST /v1/images/edits (multipart/form-data)
→ input_fidelity=high
→ Final 이미지 저장
```

`confirmedDraftId`만 프롬프트에 포함하는 것으로는 레이아웃을 보존할 수 없다. 실제 이미지 파일을 image edit 입력으로 전달해야 한다.

### 1.2 Admin에서 LLM을 바꾸는 의미

Admin의 provider/model 설정은 Worker가 실행 snapshot을 읽어 실제 API 호출에 반영할 때만 의미가 있다. 오늘 반영한 Worker 계약은 payload의 다음 값을 사용한다.

- `execution.provider`
- `execution.model`
- `execution.modelOptions`
- `confirmedDraft.draftImageProxyUrl`
- `layoutFidelityPolicy`

Final 검증값:

```text
provider: openai
model: gpt-image-1
inputFidelity: high
referenceMode: image_edit
```

## 2. n8n 변경 사항

### 2.1 Integrated Brief Worker

- provider/model 실행 snapshot 반영 구조를 점검했다.
- OpenAI timeout/error 시 일반 실패 처리와 최소 1회 재시도 방향을 반영했다.
- 비정상적으로 긴 응답에 대한 길이 guard 요구사항을 계획에 유지했다.
  - 15,000자: warning
  - 20,000자: retry
  - 30,000자: fail

주의: 오늘의 주된 운영 전환 대상은 Final Worker다. Integrated Brief 백업 변경과 운영 반영 상태는 n8n Version History에서 다시 확인한 뒤 추가 변경해야 한다.

### 2.2 LO-FI Draft Worker

### 3.3 Final prompt 32,000자 초과 Hotfix

추가 실사용 실행에서 Final prompt가 39,675자로 증가해 OpenAI의 32,000자 제한 오류가 발생했다.

오류:

```text
Invalid 'prompt': string too long.
Expected maximum length 32000, got 39675.
```

조치:

- 운영 Final Worker의 OpenAI `prompt` 입력을 최대 30,000자로 제한했다.
- 동일 실패 실행을 Copy to editor로 재실행했다.
- n8n 실행 `1185`가 약 72초, 5MB로 성공했고 모든 노드가 완료됐다.
- 서버 측 정식 해결로 `api/_final-design-prompt-budget.js`를 추가했다.
- `/api/prompts-render`와 execution snapshot 양쪽에서 앞 72%와 뒤 28%의 핵심 문맥을 보존하며 30,000자 이하로 압축한다.
- 회귀 테스트에서 43,000자 이상의 합성 입력을 30,000자 이하로 줄이고 앞·뒤 내용과 layout policy 보존을 확인했다.

서버 측 수정 로컬 커밋:

- `c07ed07 Guard final design prompt length`

배포 주의:

- 로컬 GitHub HTTPS 인증이 없어 push가 실패했다.
- 연결된 GitHub 앱도 저장소 쓰기 권한이 없어 403을 반환했다.
- 따라서 현재 운영 장애는 n8n Hotfix로 해소됐지만, 서버 측 커밋 `c07ed07`은 GitHub 인증 후 push하여 Vercel에 배포해야 한다.

## 6. 보안 결정

사용자 결정:

- n8n의 OpenAI API 키는 현재 상태로 유지한다.
- OpenAI Credential 등록 오류가 있어 HTTP Request 노드의 기존 키를 제거하지 않는다.

적용 원칙:

- n8n 내부 키는 유지
- 키 값을 문서, 로그, 응답에 기록하지 않음
- 저장소의 Final Worker fixture는 `Bearer __RETAIN_EXISTING_N8N_KEY__` placeholder 사용
- 실제 키가 Git에 추가되지 않았는지 secret scan 수행

남은 위험:

- n8n export 또는 MCP 조회 시 평문 키가 노출될 수 있다.
- 공유·다운로드·로그 보관 시 workflow JSON을 민감정보로 취급해야 한다.
- n8n/OpenAI Credential 등록 버그가 해결되면 Credential 참조 전환을 재검토한다.

## 7. 남은 작업

### 우선순위 1. 실사용 콘텐츠 회귀 검증

오늘 검증은 smoke-test 콘텐츠를 사용했다. 실제 프로모션 콘텐츠로 다음을 추가 확인한다.

- 한글 가시 텍스트 정확도
- 긴 제목과 긴 CTA에서 레이아웃 유지
- 섹션 수가 많은 디자인
- 모바일/데스크톱 비율별 결과
- 브랜드 Design MD가 강한 경우 스타일 DNA 유지

### 우선순위 2. 브랜드 스타일 fidelity 별도 트랙

이번 작업은 레이아웃 fidelity를 해결했다. 선택한 Design MD의 스타일 DNA가 Integrated Brief 단계에서 일반화되는 문제는 별개다.

다음 단계 후보:

- Integrated Brief에 design token/style DNA 필수 필드 추가
- Final prompt에 typography, color, radius, spacing, imagery 규칙 전달
- 브랜드 reference와 layout reference를 분리
- 자동 시각 비교 기준 정의

### 우선순위 3. 비용 모니터링

`input_fidelity=high`는 low 대비 이미지 입력 토큰을 약 10배 사용할 수 있다는 운영 가정으로 모니터링한다. 공개 API의 고정 배율은 아니므로 실제 usage의 image token 값을 기준으로 경보 임계치를 보정한다.

### 우선순위 4. 백업 Workflow 정리

Final 백업 Workflow는 회귀 검증용 Webhook으로 게시돼 있다. 검증 기간 종료 후 다음 중 하나를 결정한다.

- 계속 유지하고 호출 권한/이름을 명확히 관리
- 비활성화하고 Version History만 보존
- 운영 Worker의 staging 환경으로 정식 분리

### 우선순위 5. 기존 QA label guard 실패 정리

기존 3개 workflow JSON에 누락된 guard 문구를 보완하거나, 더 이상 사용하지 않는 파일이면 archive 대상인지 결정한다.
