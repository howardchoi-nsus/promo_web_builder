# Handoff - 2026-07-07

## 오늘 진행 요약

오늘은 PROMO WEB BUILDER의 LLM 프롬프트 관리 구조를 n8n 내부 중심에서 Web App / DB 중심으로 전환하는 1차 개발을 진행했다.

핵심 방향은 아래와 같다.

```text
프롬프트 관리 = Web App
프롬프트 저장 = DB
프롬프트 치환/검증 = Web API
workflow 실행 = n8n
LLM 호출 = n8n
```

이번 1차 개발에서는 프롬프트 관리 페이지, DB 테이블, 관리 API, 렌더 API, 기존 통합 브리프 프롬프트 API의 DB 연동까지 반영했다.

커밋은 진행하지 않았다.

## 작업 배경

기존 n8n workflow는 LLM 프롬프트와 이미지 생성 프롬프트 조립 로직을 workflow 내부에 가지고 있었다.

이 방식의 문제는 다음과 같다.

- 프롬프트 수정 시 n8n workflow를 직접 수정해야 한다.
- 변경 이력 추적이 어렵다.
- 프롬프트 롤백이 어렵다.
- 비개발자가 관리하기 어렵다.
- B섹션 프로모션 입력값이 최종 이미지 생성 프롬프트로 전달되는 과정에서 요약/누락될 수 있다.

따라서 n8n은 workflow 실행에 집중하고, 프롬프트 본문과 버전 관리는 Web App에서 처리하는 구조로 전환하기로 했다.

## 오늘 확정한 정책

### 프롬프트 수정 방식

프롬프트는 신규 생성 중심이 아니라 업데이트 방식으로 진행한다.

단, 업데이트 시마다 변경 기록을 생성한다.

저장해야 할 기록:

- 변경 전 body
- 변경 후 body
- 이전 version
- 신규 version
- 이전 status
- 신규 status
- 변경 사유
- 변경 시간

### 프롬프트 삭제 방식

실제 삭제하지 않고 archive 처리한다.

운영 규칙:

- active 프롬프트는 archive 불가
- archive 된 프롬프트는 기본 목록에서 제외
- 과거 생성 결과에서 참조할 수 있도록 DB에는 유지

### Active 프롬프트 정책

같은 type에는 active 프롬프트를 1개만 허용한다.

DB partial unique index로 보장한다.

```text
type별 active 1개
```

### 변수 치환 위치

변수 치환은 n8n이 아니라 Web API에서 처리하는 것으로 결정했다.

권장 흐름:

```text
n8n
-> Web API 호출
-> Web API가 active prompt 조회
-> Web API가 변수 검증
-> Web API가 변수 치환
-> n8n에 renderedPrompt 반환
-> n8n이 LLM 호출
```

## 미해결 이슈

### Issue 1. n8n workflow 단순화 미완료

프롬프트 관리 페이지와 render API는 준비됐지만, n8n workflow가 아직 완전히 `/api/prompts-render` 중심으로 바뀐 것은 아니다.

다음 작업에서 workflow 수정 필요.

### Issue 2. 2차 이미지 프롬프트의 B섹션 반영력 미검증

현재 가장 중요한 품질 이슈는 B섹션 입력값 반영이다.

오늘은 관리 구조를 먼저 만들었고, 실제 image_execution 프롬프트 적용 후 반영률 검증은 내일 이어서 해야 한다.

### Issue 3. 생성 결과 재현성 정책 미확정

동일 입력에 대해 최대한 같은 결과가 나오게 하려면 hash 기반 추적이 필요하다.

아직 구현 확정 전이며, 테스트 후 적용 범위를 결정하기로 했다.

### Issue 4. DB migration 운영 반영 필요

실제 배포 DB에는 아래 migration이 적용되어야 한다.

```text
db/migrations/010_prompt_templates.sql
```

미적용 환경에서는 프롬프트 관리 API가 정상 동작하지 않는다.
