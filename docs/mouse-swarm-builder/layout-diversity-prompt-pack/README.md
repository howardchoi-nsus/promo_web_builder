# 구조 변경 없이 레이아웃 다양성을 높이는 프롬프트 보정안

작성: 2026-11-24 · 상태: 교체용 본문 준비 / Admin 미등록·미활성화 / 실제 모델 비교 미실행

## 목표와 경계

현재 PageSchema·범용 렌더러·영역 단위 생성·소스 배정·토큰 정책·저장/품질 검증을 유지한다. 구조 실행 코드나 DB 스키마를 바꾸지 않고, AI가 이미 허용된 컬럼 비율·그룹·정렬·이미지 관계를 더 명확히 선택하도록 본문을 보정한다. 새 고객 승인 단계나 레이아웃 선택 UI를 추가하지 않는다.

핵심은 ‘다양하게 만들라’는 문장을 반복하는 대신 **어떤 단계에서 어떤 배치를 결정해야 하는지 명시**하는 것이다. 신규 페이지의 배치는 바뀔 수 있지만 동일 요청의 매번 다른 결과, 운영 품질 향상이나 처리 시간 유지는 아직 실증하지 않았다.

Admin 표시 이름은 편집 가능하므로 타입을 기준으로 찾는다. 위 MD는 추가 문장만이 아니라 **교체 가능한 전체 본문**이다. 기존 098 패키지를 기반으로 계약을 보존했으며 파일 끝의 보정 블록에서 신규 판단 기준을 구분한다. 운영에서 별도로 편집한 활성 본문의 사본은 아니므로, Admin 적용 시 맞춤 지시를 대조해 보존하고 동일 취지의 구문은 중복 추가하지 않는다. 원래 094–098 마이그레이션과 기존 패키지 파일은 수정하지 않았다. 이미지 생성 프롬프트·요청 요약 프롬프트·기존 스킬 연결은 이번 범위에서 유지한다.

## 2. 구체적인 보정 방법

### 작업 계획: 완성된 템플릿 대신 배치 의도를 선택

- 같은 모델 호출 안에서 적합한 구도 가능성을 짧게 비교한 뒤 하나의 기존 manifest만 반환한다. 여러 완성 페이지 생성·별도 LLM 호출·고객 선택을 요구하지 않는다. 사고 과정이나 후보 배열을 출력 필드로 추가하지 않는다.
- 섹션 수를 개요 항목 수에 기계적으로 맞추거나 모든 요청을 히어로/동일 카드/CTA로 변환하지 않는다. 전달 목적·원문 길이·반복 항목의 비교 필요·이미지 요구에 따라 묶는다.
- 파싱된 hero 필드가 null이어도 이미 전달되는 requestText/explicitRequirements의 명시 요구를 읽는다. ‘시네마틱’이라는 분위기만으로 중앙형을 강제하지 않는다.
- 기존 intent의 160자 제한 안에 이미지/텍스트 관계, 핵심 비율, CTA 위치 등 후속 생성에 필요한 구도를 기록한다. 새 JSON 필드를 만들지 않는다.
- 셸은 기존 container이며 비어 있어야 한다. 셸 타입을 grid로 바꾸지 않고, 내부 grid 구도는 intent로 전달한다. 셸 간 중첩/소스 소유권·이미지 요구는 기존 계획 계약을 따른다.

### 영역 구성: null을 자동 디자인으로 오해하지 않도록 보정

- 현재 compact 계약에서 layout=null은 세로/늘림/전체 폭 기본값이다. 주요 배치 그룹·stack·card·grid에는 필요한 desktop 배치를 명시한다. 단순 잎 요소와 의도적인 세로형은 기본값을 계속 사용할 수 있다.
- 1:1, 2:1, 1:2 같은 비율은 가능한 예시이지 고정 선택지가 아니다. 긴 설명에는 읽기 폭을, 비교 항목에는 동등한 위계를, 대표 혜택에는 집중도를 부여한다. 등록된 물리 그리드 안에서 기존 논리 컬럼/스팬으로 표현한다.
- 가로 stack에 전체 폭 자식을 여러 개 넣으면 다시 줄바꿈될 수 있음을 명시한다. 의미 있는 컬럼 배치는 grid와 적절한 스팬을 사용한다.
- 앞선 영역의 스타일 방향은 이어가되 내부 트리를 그대로 반복하지 않는다. 동일 카드 반복이 실제 비교에 유용하면 유지한다.
- 배경 이미지와 텍스트는 지원되는 같은 컨테이너 관계 안에서 구성한다. 다른 형제 영역에 생성한 이미지가 자동으로 텍스트 배경이 된다고 가정하지 않는다.

### 디자인·검토: 잘못된 구도를 꾸미기로 해결하지 않음

- 디자이너는 기존 허용 styles/spacing/overlay만 반환한다. 트리·컬럼·이미지 presentation 변경을 요구하지 않는다.
- 등록 후보의 실제 값과 의미를 보고 제목/본문/통계/CTA의 위계를 다르게 적용한다. 모든 그룹을 카드로 만들거나 색상을 임의로 늘리지 않는다.
- 검토자는 스크린샷을 보았다고 주장하지 않는다. 구조와 측정에서 확인되는 요구 미충족만 기존 패치·issue·summary로 표현한다. 반복 자체를 실패나 자동 재생성 조건으로 만들지 않는다.

## 3. 기존 문제와 이번 보정의 대응 범위

| 확인한 원인 | 프롬프트로 가능한 보완 | 남는 한계 |
| --- | --- | --- |
| 미지정 배치의 세로형 기본값 | 중요한 그룹의 명시 배치와 비율 결정 지시 | null 기본값 코드는 유지됨. 모델이 지시를 따르는지 실제 확인 필요 |
| 최초 셸 고정 | 첫 계획의 구도 판단·intent 전달을 구체화 | 후속 프롬프트가 잠긴 셸을 수정할 수는 없음 |
| 구도 키워드 해석이 좁음 | 기존 원문 필드도 디자인 자료로 읽게 지시 | 구조화 브리프 추출 자체는 개선되지 않음 |
| 누적 생성에 최근 구도 이력 없음 | 현재 자료 안에서 적합한 구도를 선택 | 이전 결과가 입력되지 않으면 프롬프트가 과거 반복을 알 수 없음 |
| 기존 페이지 재실행은 보존 수정 | 명시적으로 요청된 영역 변화와 문구 수정 구분 | 명시 재설계 없이 반복 클릭만 하면 새 구도를 보장하지 않음 |
| 서버의 배경형 지시 등 충돌 | 그 제약 안에서 문구 그룹·정렬·주변 섹션을 개선 | 본문으로 서버 제약을 해제하지 않음. 배경형을 강제하는 전체 생성 경로를 완전히 자유화했다고 주장하지 않음 |
| 구조적 미감 검토 한계 | 요청 구도·비율·위계와 근거 기반 issue 검토 | 전체 DOM 재구성, 이미지 미감 평가나 새 시각 점수 체계를 구현하지 않음 |

레이아웃 차이는 명시 요청과 자료에 적합해야 한다. 무작위 seed/temperature 증가, 매 섹션 다른 색상, 큰 빈 공간, 불필요한 이미지 추가는 다양성 대책으로 사용하지 않는다. 비교·법적 문구 등 세로형이나 반복형이 적합한 콘텐츠까지 강제로 바꾸지 않는다.

## 4. 정책·스킬·프롬프트 구분

| 구분 | 이번 처리 |
| --- | --- |
| 정책 | 등록 토큰·사실·보안·접근성·자동 진행을 유지하며 이번 개선은 프롬프트 우선으로 진행한다는 범위를 AGENTS/계획서에 기록 |
| 스킬 | 기존 연결·불변 버전·순서 유지. 본문과 같은 고정 히어로/카드 지시가 있는지는 Admin의 최종 조립 지시문에서 확인. 이번에 글로벌 새 스킬이나 중복 버전을 추가하지 않음 |
| 프롬프트 | 단계별 판단 기준을 위 5개 전체 본문에 반영. 기존 필수 변수와 결과 계약 유지 |
| 코드·설정 | 렌더러/스키마/API/기본값/상태 전이/병렬/모델/토큰 정책 변경 없음. 새 migration·기능 플래그 없음 |

## 5. Admin 적용 순서

1. 활성 버전의 본문·필수 변수·모델·온도·출력 한도·modelOptions·Execution Snapshot·정책/스킬 연결을 기준본으로 남긴다. 이미 열린 Draft가 있으면 내용을 보존하고 비교한다. 이번 파일로 활성 레코드를 직접 덮어쓰지 않는다.
2. 먼저 작업 계획 V2와 영역 구성 V2의 Draft 본문만 교체한다. V2의 pageDraftContractVersion=2, Snapshot V2 이상 및 기존 설정/필수 변수/스킬 연결은 유지한다. 새 스킬 추가나 모델 변경을 함께 진행하지 않는다.
3. 최종 조립 지시문을 확인한다. pre/post/additionalInstructions, harness와 스킬에 고정 3카드·센터형 강제 등이 있으면 본문만 바꿨다고 해결됐다고 판단하지 않는다. 서버의 강제 제약은 프롬프트에서 무시하도록 쓰지 않고 별도 한계로 기록한다.
4. 관리자 검증과 실제 테스트 호출로 확인한 후 적용한다. 아래 비교는 유료 모델/이미지 호출을 발생시킬 수 있으므로 이 문서 작성 과정에서는 실행하지 않았다. 기존 모델·온도를 유지해 본문 변경의 효과를 비교한다.
5. 결과가 개선되면 신규 작업 사이에 두 Draft를 검증/활성화한다. 진행 중인 단위 작업의 고정 버전과 충돌하지 않게 한다. 그 뒤 사용 중인 전체 페이지 플래너·디자이너·검토자에 같은 방식으로 후속 보정을 적용한다. 누적 생성 ON/OFF에 따라 실제 사용 프롬프트가 다르므로 적용된 경로를 기록한다.
6. 오류율·대기 시간·구도 적합성이 악화되면 해당 타입의 이전 활성 버전으로 되돌린다. 이미 저장된 페이지는 변경하지 않는다. 새로운 고객 승인이나 수동 QA 작업을 추가하지 않는다.

## 6. 비교 요청과 판정

신규 구도 비교는 기존 페이지의 보존 수정과 구분되는 새 테스트 문서에서 진행한다. 모델·토큰·입력·활성 스킬을 고정하고 기존/후보 프롬프트 결과를 비교한다. 같은 내용을 쓰더라도 아래 명시 구도가 결과에 반영되는지를 확인하며 매 실행이 달라야 한다는 조건은 두지 않는다.

| 요청 | 확인할 변화 | 유지할 조건 |
| --- | --- | --- |
| 동일 승인 혜택으로 텍스트와 이미지를 좌우 비대칭으로 배치 | 컬럼 비율·이미지/텍스트 관계가 실제 트리에 존재 | 사실·기존 이미지 요구·등록 그리드 |
| 동일 승인 혜택을 배경 키비주얼 위의 집중형 구성으로 제작 | 지원되는 같은 컨테이너의 배경 이미지·문구 그룹·읽기 순서 | 등록 오버레이/대비가 없으면 안전한 허용 대안 |
| 긴 설명과 여러 혜택을 편집형 흐름으로 구성 | 모든 항목을 동일 카드로 나열하지 않고 정보 묶음·밀도에 근거한 배치 | 승인된 긴 사실 문구를 자르거나 재작성하지 않음 |
| 비교해야 할 동등한 혜택을 명확하게 구성 | 필요하면 동등한 반복 카드 유지 | 다양성을 위해 비교 가독성을 해치지 않음 |
| 기존 페이지에서 제목 문구만 수정 | 관련 문구 수정 범위 준수 | 무관한 구조·이미지·동작 유지 |
| 기존 페이지의 지정 영역을 좌우 배치로 수정 | 현재 서버가 허용하는 요청 범위의 구도 변화 | 선택 밖 변경 금지, 재검증·자동 검사 |

평가는 섹션/그룹 트리·컬럼 비율·이미지 관계·정보 위계·등록 스타일 실제 값·세 화면 가독성을 함께 본다. 구조 해시가 다르다는 것만으로 디자인 개선을 인정하지 않는다. 신규 스키마 오류·이미지 누락·사실 변조·고객 추가 클릭 없이 명시 구도가 반영돼야 한다. 모델 응답 길이·지연·토큰 사용량도 비교한다. 추가 호출을 요구하지 않아도 지시 길이·판단량으로 비용/시간은 늘 수 있다.

## 검증 상태

로컬에서 저장소의 실제 promptVariableContract/validatePromptTemplateContract와 renderPrompt/assembleEffectivePrompt 함수를 사용한 **5종 검사 통과**(`/tmp/layout-diversity-prompt-contract.log`). 기준 본문과 변수 목록이 동일하고 렌더/조립 후 미해결 변수가 없음을 확인했다. 이 검사는 결과물 디자인 품질, 운영 활성 프롬프트·스킬 조합 또는 실제 공급자 성공을 증명하지 않는다. 실제 모델 호출·DB 쓰기·Admin 활성화는 실행하지 않았다. 현재 패키지는 배포나 DB 등록만으로 활성화되지 않는다.
