# Zero-Click 관점의 Promo Web AI Builder E2E — AX 도입 개념 정립

- 작성일: 2026-07-14 (지속 업데이트 예정)
- 상태: 개념/전략 문서 / 소스코드 미반영
- 용도: Promo 웹AI빌더 시연·발표 준비 자료 — 발표 시점까지 반복 보완, 이후 발표 자료(PPT)의 기반 콘텐츠로 사용
- 참고: `README.md`, `docs/product-direction-and-gap-review.md`, `docs/automated-vue-web-generation-process-recommendation-2026-07-14.md`, `docs/claude/cms-integration-readiness-review-2026-07-14.md`

## 결론

이 프로젝트는 "더 나은 디자인 템플릿 빌더"가 아니라 **운영자의 반복 클릭(수작업 판단)을 단계적으로 제거해가는 자동화 파이프라인**으로 재정의할 수 있다. E2E 흐름(Concept → Content → LO-FI → HI-FI/Web Output → Publish)의 각 단계는 개별 기능이 아니라, 궁극적으로 "사람이 몇 번 개입해야 결과물이 나오는가"를 줄여가는 하나의 축 위에 있다. 이것이 **Zero-Click 기획**이며, 조직 관점에서는 "AI 기능 추가"가 아니라 **업무 프로세스의 의사결정 구조 자체를 AI로 재설계하는 AX(AI Transformation) 프로젝트**로 포지셔닝해야 한다.

이 재프레이밍의 실익은 두 가지다. 첫째, 프로젝트 가치를 "디자인 품질"이 아니라 "운영 리소스 구조 변화"로 설명할 수 있다. 둘째, WordPress/Directus 연동, Rule Base 고도화, 자동 QA 확장처럼 흩어져 보이는 다음 작업들을 "Zero-Click 단계 승급"이라는 단일 기준으로 우선순위 정렬할 수 있다.

한 가지는 분명히 해야 한다. **Zero-Click은 언젠가 도달해서 완료되는 미래 시점의 상태가 아니라, Zero Trust·Zero Defect·Zero Downtime과 같은 계열의 추상적 지향점(compass)이다.** 문자 그대로 클릭 수 0을 달성하고 멈추는 종착점이 아니라, 매 단계에서 "이 판단을 왜 아직 사람이 해야 하는가"를 계속 되묻게 만드는 기준선이다. 발표에서도 "언제까지 완전 무인화한다"가 아니라 "이 원칙으로 다음 단계를 계속 줄여나간다"는 진행형 서사로 제시하는 것이 정확하다.

## 1. Zero-Click의 기획적 정의

Zero-Click은 최종 산출물(발행 가능한 프로모션 페이지)이 나오기까지 운영자가 **클릭해야 하는 의사결정·승인·수작업 지점**을 최소화하거나 제거하는 기획 원칙이다.

핵심은 "자동화 기능을 넣는다"가 아니라, 각 단계마다 "왜 사람이 개입해야 하는가"를 묻고, 그 개입 이유(정책 리스크, 품질 리스크)를 **Rule Base(정책 코드화)**와 **자동 QA(결정적 검증)**로 대체할 수 있는지 검토하는 방법론이라는 점이다. 사람의 판단이 필요한 지점만 남기고 나머지는 시스템이 대신 판단하도록 재설계하는 것이 Zero-Click 기획의 본질이다.

이 원칙은 이미 프로젝트 문서에 명시적으로 드러나 있다.

- README: "AI 생성 결과는 즉시 배포물이 아니라 운영자가 검수하는 초안" — 현재는 사람이 매 단계 확인하지만, 구조 자체는 확인 단계를 줄여나갈 수 있게 설계되어 있음.
- 자동화 Vue 웹페이지 생성 권고안(2026-07-14): "페이지 자동 생성 과정에서 사람의 참여를 최소화하거나 제거한다", "수동 확인 없는 자동 모드의 완료 조건"을 별도로 정의 — 이것이 Zero-Click 기획이 실제로 적용된 사례다.

## 2. Zero-Click과 AX의 관계

- DX(Digital Transformation): 수작업을 디지털 도구로 대체 — 사람이 도구를 "다루는" 클릭 수를 줄인다.
- AX(AI Transformation): 사람이 하던 "판단"과 "생성" 자체를 AI가 수행하고, 사람은 예외/정책 관리자로 역할이 바뀐다 — 판단 자체의 클릭을 제거한다.

Zero-Click 관점은 AX의 운영적 정의로 볼 수 있다. "AI가 무엇을 생성하는가"가 아니라 **"사람이 몇 번 개입해야 결과물이 나오는가"**를 기준으로 프로젝트의 AX 성숙도를 측정할 수 있다.

## 3. Zero-Click 성숙도 모델 (제안)

| Level | 정의 | 사람의 역할 |
|---|---|---|
| 0. Manual | 모든 필드 수작업 입력, 템플릿 수동 선택 | 실행자 |
| 1. AI-Assisted Draft | AI가 초안 생성, 매 단계 사람이 확인/승인 | 매 단계 검수자 |
| 2. AI-Autonomous + Approval Gate | 생성·검증까지 AI가 자동 수행, 발행 직전 1회만 승인 | 최종 승인자 |
| 3. Zero-Click | Rule Base + 자동 QA 통과 시 사람 개입 없이 발행까지 완료 | 예외 상황 관리자 |

Level이 올라갈수록 "사람이 무엇을 더 잘하는가"가 아니라 "시스템이 무엇을 대신 판단해도 안전한가"가 설계 기준이 된다.

이 표는 로드맵의 종착점을 정의하는 것이 아니라 **현재 위치를 측정하는 자(scale)**다. Level 3에 실제로 도달하는지 여부보다, 시간이 지나며 Level 1→2 방향으로 꾸준히 이동하고 있는지가 진행을 보여주는 핵심 지표다.

## 4. 현재 프로젝트 위치 매핑

- Concept / Content / LO-FI / Final Design: **Level 1** — 매 단계 사람이 결과를 확인하고 다음으로 진행.
- Web Output(Vue 코드 자동 생성 + 자동 QA, 설계 완료·구현 착수 전): **Level 2 진입 설계 완료**. 자동화 권고안에서 정의한 fatal QA gate(빌드 성공, 콘텐츠 커버리지 100%, overlap/overflow 없음 등)가 Level 1→2 전환의 실질적 조건.
- Publish(WordPress/Directus 연동, 아직 미구현): **Level 2 → 3 전환의 핵심 관문**. 여기서 Rule Base 컴플라이언스 게이트가 결정적 역할을 한다 — CMS 연동은 단순 기술 통합이 아니라 "이 지점에서 사람 승인을 계속 남길 것인가"를 결정하는 지점이다.

## 5. AX 도입 주제로서의 가치 제안

- **조직 관점**: 리전 담당자의 반복 작업 제거 → 신규 프로모션 페이지 생성 리드타임 단축.
- **품질 관점**: 사람이 놓치기 쉬운 오류(약관 누락, CTA 링크 오류, 문구 불일치)를 자동 QA가 결정적(fatal gate)으로 차단 — 오히려 사람보다 일관된 품질을 보장할 수 있음.
- **확장 관점**: 리전·마켓이 늘어나도 필요한 사람 리소스가 선형으로 늘지 않음. 스케일과 사람 리소스를 분리하는 것이 AX의 핵심 가치.
- **거버넌스 관점**: 정책을 Rule Base로 코드화하면 정책 변경 시 전체 파이프라인에 즉시 반영된다. "사람에게 공지하고 기억에 의존"하는 기존 방식보다 안전하다.

## 6. Zero-Click 도달을 위한 전제 조건 (거버넌스)

Zero-Click은 "검증 없는 자동화"가 아니다. 승인 단계를 없애는 대신 반드시 다음이 선행되어야 한다.

- **Rule Base 정책 커버리지**: 약관, Responsible Gaming, Bonus Code, Affiliate, Q-TAG, CTA 링크 정책 등 (`product-direction-and-gap-review.md` 5번 항목에서 이미 식별됨).
- **자동 QA fatal gate**: 빌드 성공, 콘텐츠 커버리지 100%, CTA label/URL 일치, overlap/overflow 없음 등 (`automated-vue-web-generation-process-recommendation-2026-07-14.md` 8절).
- **예외 에스컬레이션 경로**: 완전 무인이 아니라 "실패·정책 위반 시에만 사람에게 명확히 알림"이 되는 구조.
- **되돌리기(rollback) 가능성**: 잘못 발행되어도 즉시 회수할 수 있어야 함 — `docs/claude/cms-integration-readiness-review-2026-07-14.md`의 `promo_publish_jobs` 상태 모델과 직접 연결됨.

## 7. 프로젝트 내러티브 재정의 제안

- 기존 프레이밍: "WordPress 빌더의 한계를 보완하는 AI 디자인 도구"
- 제안 프레이밍: **"리전 담당자의 반복 클릭을 제거해나가는 Zero-Click 프로모션 운영 자동화 — 조직의 AX 도입 사례"**

## 8. 다음 단계 제안

1. 기존 로드맵을 "Level 3 도달 시점"이 아니라 "Level 1→2 방향으로의 지속적 이동"을 보여주는 방식으로 재정리.
2. 각 Level 승급의 Definition of Done을 자동 QA/Rule Base 커버리지 기준으로 명시(완료 선언용이 아니라 다음 구간 진입 조건으로 사용).
3. WordPress/Directus 연동 작업을 "Level 2 → 3 전환 작업"으로 재배치하여 다른 백로그와 우선순위를 함께 논의.
4. 경영/의사결정층 보고 시 "완전 무인화 목표 시점"이 아니라 "Zero-Click 전환율(Level별 커버리지)이 어느 방향으로 움직이고 있는가"를 진행 지표로 제시.

## 9. 발표 활용 메모

- 이 문서는 몇 주 뒤 예정된 Promo 웹빌더 시연·발표를 위한 기초 콘텐츠다. 발표일까지 계속 업데이트하며, 최종적으로 발표 자료(PPT) 구성의 근거 문서로 사용한다.
- 발표 내러티브 초안: (1) 기존 WordPress 빌더의 한계 → (2) Zero-Click이라는 지향점 도입 → (3) 현재 Level 1 위치와 Level 2 설계 완료 현황 → (4) CMS 연동을 Level 2→3 전환 관문으로 제시 → (5) "언제 완료되는가"가 아니라 "어떤 원칙으로 계속 개선하는가"로 마무리.
- 발표 자료 제작(PPT) 시점에는 이 문서의 결론/모델/현재 위치 매핑 부분을 슬라이드 구조로 옮기는 작업을 별도로 진행한다.

## 10. 예상 질문 대응 (Q&A)

### Q. Wizard·템플릿화로 구성하다 보니 LLM/AI의 역할보다 Rule Base 개념이 더 강해 보인다. AI 프로젝트가 맞나?

**한 줄 답변**: AI와 Rule Base는 경쟁 관계가 아니라 역할 분담이다. AI는 해석과 생성을, Rule Base는 정책과 안전을 맡고, 이 분리 자체가 Zero-Click을 가능하게 만드는 전제조건이다.

**근거 1 — 처음부터 의도된 설계다.** README의 기획 원칙에 이미 "NLP가 요구사항을 해석하고, Rule Base가 운영 정책과 필수 구조를 통제하며, Template Family와 Component를 조합해 검수 가능한 초안을 생성한다"고 명시되어 있다. Wizard·템플릿화는 부족해서 넣은 우회로가 아니라 설계 원칙이다.

**근거 2 — 도메인 특성상 당연하다.** 프로모션 페이지는 약관, Responsible Gaming 문구, Bonus Code, Q-TAG, 리전별 법적 고지처럼 "창의적으로 생성해도 되는 영역"이 아니라 "100% 정확해야 하는 영역"을 포함한다. 이런 텍스트를 LLM 자유생성에 맡기면 hallucination 리스크를 그대로 안게 된다. 오히려 이런 도메인에서 Rule Base 없이 자유생성만 쓰는 것이 더 무책임한 AI 도입이다. 자율주행이 인식은 신경망에 맡기되 신호 위반 같은 안전 규칙은 하드코딩하는 것과 같은 논리다.

**근거 3 — AI 역할은 이미 구체적으로 정의돼 있다.** 자동화 Vue 웹페이지 생성 권고안에 "LLM이 필요한 단계"와 "필요 없는 단계"가 명확히 구분되어 있다. LLM은 LO-FI→컴포넌트 구조 해석, 이미지/콘텐츠 영역 분석, 이미지 프롬프트 생성, Vue/CSS 초안 생성, Vision QA 기반 수정처럼 판단·생성이 필요한 곳을 맡는다. build, 해시 생성, ZIP, URL 주입, 배포처럼 결정적이고 재현 가능해야 하는 곳은 일반 코드로 처리한다. "AI 역할이 작다"가 아니라 "AI를 AI가 잘하는 곳에만 정확히 쓰고 있다"가 맞는 설명이다.

**근거 4 — Zero-Click 관점과 직결된다.** Rule Base가 약하고 LLM 자유생성 비중이 높았다면 결과를 신뢰할 수 없어 매번 사람이 전수 검수해야 했을 것이다. 즉 지금보다 오히려 Level 1에서 벗어나지 못했을 것이다. Rule Base가 강하다는 것은 AI가 약하다는 신호가 아니라, 사람의 클릭을 안전하게 제거해도 되는 신뢰 기반이 마련됐다는 신호다.

**근거 5 — 비율은 고정값이 아니라 진화 중이다.** 지금은 Wizard·템플릿 비중이 크지만, LO-FI → Vue 코드 생성 단계로 갈수록 AI의 생성 범위가 이미지 한 장에서 실행 가능한 코드 전체로 넓어지고 있다. 현재 스냅샷만 보고 "AI 비중이 낮다"고 판단하면 이 흐름을 놓치는 것이다.

**Q&A 현장용 짧은 방어 문장**: "Rule Base가 강한 건 AI가 부족해서가 아니라, 사람의 승인 없이도 믿고 넘어갈 수 있는 안전판을 만든 것입니다. 완전 자유생성이었다면 오히려 지금보다 자동화 수준이 낮았을 겁니다."
