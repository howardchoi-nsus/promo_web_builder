# 디자인 미리보기 이미지·보더·아이콘 안정화 계획

작성일: 2026-11-12  
기준 정책: 저장소 루트 `AGENTS.md`  
대상: PageSchema 기반 최신 AI 제작 경로  
상태: 기능 코드와 migration 090·범위 한정 회귀 검사 구현. 로컬 검증 기록과 운영 선행 조건은 `design-preview-stabilization-rollout-2026-11-12.md` 참조. 실제 공급자·Neon·Blob·Preview 통합 검증과 Production 배포는 미완료.

## 1. 목표와 완료 기준

디자인 미리보기에서 의도한 키비주얼·섹션 이미지·컴포넌트 이미지·보더·아이콘이 누락되는 연결 문제를 해결한다. 구조 생성에서 실제 에셋 준비와 렌더링까지 같은 계약으로 관리한다.

- 승인한 PageSchema의 노드 순서·중첩·컬럼·간격을 유지한다.
- 필요한 이미지는 자동 생성 또는 허용된 기존 에셋 재사용 후 연결한다.
- 등록된 보더 토큰이 노드 역할·색상·두께·선 종류를 거쳐 실제 화면에 반영된다.
- 아이콘은 허용된 실제 카탈로그에서 선택하고 공통 렌더러로 표시한다.
- 새로고침·재시도·추가 수정 후에도 완료 에셋과 승인 상태가 일관되게 유지된다.
- 미디어가 준비되지 않은 문서를 완료 또는 최종 출력 가능으로 표시하지 않는다.

## 2. 정책 대조

| AGENTS.md 정책 | 계획에 적용할 기준 |
| --- | --- |
| 채팅으로 입력·응답·수정·승인 진행 | 진행 안내, 추가 요청, 재시도, 복구 액션은 채팅에 표시 |
| 별도 폼·수정 범위 선택창 금지 | 미디어 연결 폼을 복원하지 않고 단일 채팅 입력창 사용 |
| 오른쪽은 조회용 | 에셋·보더·아이콘 결과와 준비 상태만 표시 |
| 요약 → 와이어프레임 → 승인 → 디자인 순서 | 승인 후 에셋 준비 단계를 거쳐 디자인 확인으로 연결 |
| 와이어프레임과 디자인의 배치 일치 | 에셋 교체로 구조를 재생성하지 않고 미디어 비율·영역을 보존 |
| 등록 토큰과 활성 사용 정책만 사용 | 토큰 누락 시 임의 CSS·대체 색상·선 두께를 삽입하지 않음 |
| 미정 사실·URL 임의 생성 금지 | 사용자 제공 또는 소유권 확인된 에셋만 연결. 검증된 저장 URL은 시스템이 발급 |
| PageSchema와 범용 렌더러 사용 | 임의 HTML·CSS·SVG 문자열을 AI가 직접 출력하지 않도록 유지 |
| 안정화 1: 공통 계약 | 생성 스키마·서버 검증·렌더러에 같은 역할·에셋 규칙 적용 |
| 안정화 2: 실제 DB 왕복 | 생성·저장·재조회·승인·에셋 연결·수정까지 검증 |
| 안정화 3: 회귀 사례 | 기존 승인 식별값·토큰 역할 오류와 새 미디어 실패를 고정 테스트로 관리 |
| 안정화 4: 배포 준비 | 코드·DB·프롬프트·모델·토큰·스토리지 설정의 호환성 확인 |
| 안정화 5: Preview 통합 검증 | 실제 공급자·테스트 DB·격리된 스토리지로 검증 후 Production 반영 |
| 안정화 6: 상태 책임 분리 | 승인·미디어 작업·품질 검사의 상태와 전환을 분리 |

기존의 ‘토큰이 없으면 프롬프트 값이나 AI 값으로 대체’ 제안은 채택하지 않는다. 현재 정책은 등록 토큰 전용이다. 디자인 토큰은 스타일 자원이고 이미지·아이콘 파일은 에셋 자원으로 구분하되, 둘 모두 등록·허용 범위를 검증한다.

## 3. 코드에서 확인한 문제

| 항목 | 현재 상태 | 개선 대상 |
| --- | --- | --- |
| 최초 이미지 컨텍스트 | `contentContext()`가 `assets: {}`로 시작 | 재사용 가능한 에셋 공급과 생성 요청 연결 |
| 구성 승인 | `approveDynamicStructure()`가 승인 후 바로 `render_ready`로 전환 | 승인과 에셋 준비 완료를 별도 상태로 관리 |
| 이미지 생성 | `promo-page-schema-media.js`에 개별 생성·저장 API 존재 | 승인 후 자동 처리·재시도 오케스트레이션 부재 해소 |
| 미디어 UI | 폼 제거 후 이를 대신할 자동 연결이 불충분 | 폼 복원 없이 채팅 흐름 완성 |
| 보더 | 버튼 색상·두께 역할은 있으나 일반적인 선 종류 적용이 부족 | 등록값과 실제 CSS의 연결 검증 |
| 섹션·카드 보더 | 해당 용도의 역할·매핑이 부족 | 적절한 대상의 등록 토큰만 연결 |
| 아이콘 | 체크·화살표·별·정보 문자에 한정 | 실제 허용 카탈로그와 렌더러 연결 |
| 배경 키비주얼 | 일반 이미지와 별개의 배경·레이어 계약이 부족 | 별도 계약 검토 후 단계적으로 지원 |

이 내용은 코드 조사 결과다. 특정 Production 문서의 저장 데이터나 실제 Admin 등록 토큰·에셋 목록을 확인한 결과는 아니다. 구현 전 환경별 등록 상태를 확인해야 한다.

## 4. 목표 서비스 흐름

```text
자연어 요청 및 추가 대화
  → 요청 요약
  → PageSchema 설계·검증·저장
  → 이미지 영역·아이콘·보더 계획이 포함된 와이어프레임
  → 채팅에서 구성 승인
  → 승인 리비전에 연결된 에셋 작업 등록
  → 재사용 가능한 에셋 확인 / 필요한 이미지 생성
  → 소유권·파일 형식·크기·연결 대상 검증
  → 구조를 유지한 채 에셋 연결·저장
  → 디자인 미리보기
  → Desktop·Tablet·Mobile 자동 품질 검사
  → 조건 충족 시 웹 출력·HTML

실패 → 채팅 진단 → 실패 항목만 재시도
추가 수정 → 같은 채팅 → 요약·구조 갱신 → 영향받은 에셋만 무효화
```

준비 중인 결과는 조회할 수 있지만, 미완료 에셋이 있으면 ‘디자인 준비 중’임을 명확히 표시한다. 이를 준비 완료나 품질 검사 통과로 표현하지 않는다. 모든 처리가 끝나기 전에 품질 검사가 반복 실행되는 루프를 막는다.

## 5. 단계별 구현 계획

### 단계 A. 계약·등록 상태·기존 문서 조사

1. 실제 활성 토큰과 사용 정책에서 섹션·카드·버튼·아이콘에 필요한 속성을 대조한다.
2. 기존 컴포넌트 및 에셋 저장소의 소유권·버전·파일 형식·재사용 가능 범위를 확인한다. `api/_item-components-store.js`, `api/_promo-builder-assets.js` 등은 재사용 후보이며 바로 연결할 수 있다고 가정하지 않는다.
3. 이미지 노드, `mediaRequests`, 저장된 에셋과 기존 아이콘 ID의 호환표를 작성한다.
4. 필요한 계약 변경을 스키마·정책·렌더러별로 나열하고 기존 저장 문서에 대한 읽기·수정·출력 호환 방식을 결정한다.

산출물: 지원 범위표, 토큰 누락 목록, 에셋 카탈로그 연결 방식, 계약 변경 목록. 토큰 누락을 고객에게 새 필수 입력 폼으로 전가하지 않는다.

### 단계 B. 보더 역할과 공통 스타일 계약

1. `shared/token-usage-policy.mjs`를 원본으로 노드별 보더 색상·두께·선 종류 역할을 정의한다. CJS 파일은 생성 명령으로 갱신한다.
2. 섹션·카드·버튼의 대상 구분을 명확히 하고 버튼 전용 토큰을 섹션에 잘못 재사용하지 않는다.
3. 새 역할은 선택 속성으로 도입해 기존 토큰 라이브러리 전체를 무조건 비활성화하지 않는다.
4. 보더가 필요한 노드에만 해당 매핑을 요구한다. 미등록 선 종류를 `solid` 등으로 임의 대체하지 않는다. 등록된 값이 부족하면 관리자 설정의 구체적인 부족 항목을 알린다.
5. 런타임 생성 스키마, 서버 검증, 브라우저 스타일 계산을 같은 역할 정의에서 도출한다.

대상: `shared/token-usage-policy.mjs`, 생성된 `.cjs`, `shared/page-schema/contract.cjs`, `shared/page-schema/runtime.mjs`, 관리자 정책 UI.

### 단계 C. 일반 이미지·키비주얼 자동 준비

1. 기존 개별 이미지 생성 API의 공급자 호출·파일 검증·스토리지 저장을 재사용 가능한 서비스로 분리한다. 같은 서버의 공개 HTTP API를 내부에서 재호출하는 방식은 피한다.
2. 승인된 `mediaRequests`를 작업으로 등록한다. 작업 키에는 문서·승인 기준 버전·노드·요청 내용·관련 생성 설정을 포함한다.
3. 한 번에 무제한 이미지를 생성하지 않는다. 현재 계약의 요청 수 한도를 지키고 동시성·시간·재시도 예산을 둔다.
4. 문서별 전체 리비전만으로 병렬 생성 결과를 저장하지 않는다. 결과 반영 시 최신 문서를 다시 확인하고 대상 노드·요청이 유효할 때 병합하거나 직렬 적용한다.
5. 이미 연결된 이미지 또는 동일 요청의 완료 작업은 재사용한다. 실패 항목만 재시도하고 새로고침 후 작업 상태를 복원한다.
6. 생성 중 내용이 변경되면 오래된 결과를 덮어쓰지 않는다. 무효 작업·연결되지 않은 파일의 정리 기준을 둔다.
7. 미디어 영역은 생성 전에 비율과 배치를 정한다. 파일의 원본 크기 때문에 승인 배치가 달라지지 않도록 렌더링 계약을 보완한다.

상태 제안: `pending → running → succeeded / failed / superseded`. 실제 필드·테이블과 migration 번호는 단계 A의 기존 구조 대조 후 확정한다.

대상: `api/promo-page-schema-media.js`, `api/promo-page-schema.js`, 생성 작업·문서 저장 모듈, 스토리지 인증·조회 경로.

### 단계 D. 아이콘 카탈로그 연결

1. Admin 및 컴포넌트 관리에서 실제 아이콘 자원을 어떤 형태로 등록하는지 확인한다. 별도 아이콘 카탈로그가 이미 있다고 가정하지 않는다.
2. 허용된 ID·버전·접근 범위를 포함하는 카탈로그를 AI에 제공한다.
3. 기존 네 가지 아이콘 ID는 호환 가능한 기본 등록 항목으로 유지하고 문서를 임의로 다른 아이콘으로 바꾸지 않는다.
4. 등록된 SVG·이미지·폰트 등 실제 형식에 맞는 안전한 렌더링 경로를 만든다. 임의 SVG 문자열·스크립트·외부 참조를 직접 실행하지 않는다.
5. 아이콘 색상·크기 등 스타일도 등록 토큰과 역할 매핑을 사용한다. 누락 ID가 빈 문자열로 조용히 출력되지 않도록 진단한다.
6. 장식용과 의미 전달용 아이콘의 접근성·레이블을 검증한다.

대상: 카탈로그 저장·조회 계층, `api/_page-schema-service.js`, 런타임 생성 스키마, `PageSchemaRenderer.vue`.

### 단계 E. 배경 키비주얼·레이어 표현

이 단계는 일반 이미지 자동 연결과 분리해 진행한다. 자동 생성 연결만으로 영상 히어로·배경 레이어까지 지원된다고 보고하지 않는다.

1. 배경 이미지, 채움 방식, 초점 위치, 콘텐츠 레이어 관계를 표현할 선언형 계약을 설계한다.
2. 새로운 높이·정렬·레이어 기능은 범용 레이아웃 기능으로 제공한다. 고정 히어로 DOM 템플릿을 추가하지 않는다.
3. 오버레이 색상·gradient·불투명도·간격 등 시각 값은 등록 토큰과 승인된 매핑으로만 적용한다.
4. 모바일 가독성, 콘텐츠 증가, 이미지 실패 시 표현을 검증한다.
5. 와이어프레임은 자리 표시, 디자인은 실제 에셋으로 표현하며 같은 구조와 측정값을 유지한다.

영상 자동 재생·모바일 메뉴 상호작용은 이번 이미지·보더·아이콘 문제 해결과 별도 범위로 둔다.

### 단계 F. 승인·에셋·품질 상태 연결

1. `AiBuilderApp.vue`에서 에셋 준비 책임을 별도 상태 관리 모듈로 분리한다. 화면 전체를 한 번에 재작성하지 않는다.
2. 승인 상태와 디자인 준비 상태를 구분한다. 이미지 실패를 구성 승인 실패로 잘못 표시하지 않는다.
3. 채팅에서 ‘이미지 준비 중’, ‘일부 실패’, ‘다시 시도’, ‘완료’를 안내하고 단일 입력창을 유지한다.
4. 준비 완료 후 품질 검사를 한 번 예약하고, 관련 문서 버전이 변경되면 이전 검사 결과를 무효화한다.
5. 추가 수정에서는 영향받지 않은 에셋·노드·연결을 보존하고 변경된 요청만 다시 처리한다.

## 6. 프롬프트 및 관리자 변경

| 대상 | 변경 계획 |
| --- | --- |
| 요청 분석 `promo_overview_parser` | 사용자 요청의 시각 소재·이미지 의도 보존 여부를 점검. 불필요한 개편은 하지 않음 |
| 동적 설계 `promo_page_schema_planner` | 실제 지원하는 보더·아이콘·에셋 ID와 이미지 요청 계약을 실행 컨텍스트로 제공 |
| 이미지 생성 `component_image` | 기존 실행 경로를 우선 재사용. 키비주얼 목적·화면 비율·내용 보존 조건이 충분한지 확인 |
| 안전 계약 | 지원 범위 변경이 있을 때 스키마·검증·버전 호환을 함께 갱신 |
| 관리자 토큰 정책 | 실제 등록값만 연결하고 새 선택 역할의 검증·활성화 제공 |

배경 키비주얼에 별도 이미지 프롬프트 유형이 필요하면 기존 이미지 유형과의 차이를 먼저 검토한다. 사용하지 않는 프롬프트를 일괄 수정하거나 활성 버전을 자동 교체하지 않는다. 실제 활성 모델·공급자·출력 예산은 운영 설정을 확인한다.

## 7. 검증 계획

| 검증 | 필수 사례 |
| --- | --- |
| 공통 계약 | 노드별 역할 일치, 보더 속성 조합, 등록되지 않은 아이콘·토큰 차단 |
| 정상 생성 | 키비주얼 + 섹션 이미지 + 컴포넌트 이미지 + 보더 + 아이콘이 함께 있는 대표 요청 |
| 이미지 없는 문서 | 불필요한 공급자 호출·추가 필수 조건이 생기지 않음 |
| 공급자 실패 | timeout·과금·응답 오류 후 실패 항목만 재시도 |
| 스토리지 실패 | 업로드·DB 기록·접근 권한 실패 시 정리와 복구 |
| 상태 충돌 | 중복 클릭·다중 탭·병렬 결과·생성 중 수정·오래된 응답 |
| 실제 DB 왕복 | 요구사항 저장 → 구조 생성 → jsonb 저장·재조회 → 승인 → 에셋 연결 → 재조회·추가 수정 |
| 브라우저 | 단일 채팅 입력창, 오른쪽 읽기 전용, 세 화면 크기, 이미지 로드·보더 computed style·아이콘 표시 |
| 구조 보존 | 승인 전후 노드 순서·중첩·컬럼·간격·미디어 영역 비교 |
| 기존 오류 | 속성 순서에 무관한 승인, `root`의 `text.font` 차단, 기존 문서 호환, 선택 정보 미입력 허용 |
| 출력 격리 | 와이어프레임 전용 표현·빌더 CSS가 디자인과 HTML 출력에 남지 않음 |
| 접근성·보안 | alt·레이블·장식 구분·소유권·URL·파일 형식·SVG 처리 |

테스트 결과는 단위/fixture, 실제 DB, 실제 LLM·스토리지, Preview 브라우저 통합으로 구분해 기록한다. 실제 공급자 검증에서는 생성 지연·호출 수·사용량·재시도 중복 호출 여부도 확인한다.

## 8. 배포 준비와 롤백

1. 기능별 변경과 계약 버전·호환 전략을 먼저 검토한다.
2. 필요한 migration을 테스트 DB에 적용하고 기존 문서 읽기·저장 호환을 확인한다.
3. 실제 프롬프트·등록 모델, 토큰·사용 정책, 스토리지·에셋 접근 권한을 확인한다.
4. 코드·DB·프롬프트·정책의 기준 버전을 고정한 Preview 환경에서 실제 통합 검증을 수행한다.
5. 검증 결과와 미해결 항목을 기록하고 Production에 반영한다. 소스 push와 Vercel Production Ready는 구분한다.
6. 자동 미디어 준비는 독립적인 기능 설정으로 끌 수 있도록 설계한다. 롤백해도 기존 문서·완료 에셋·작업 기록을 삭제하지 않는다.
7. DB 변경은 가능한 한 확장 방식으로 도입한다. 구버전이 해석할 수 없는 새 계약 문서는 무조건 구버전에서 렌더링하지 않고 명시적인 호환 오류를 제공한다.

현재 실행 환경에서 실제 Production DB·모델·스토리지 접근과 Vercel 상태를 확인하지 못했다. 자격 증명은 채팅으로 받지 않고 환경의 비밀 설정으로 구성한다. 검증할 수 없는 항목은 미검증으로 남기며 완료로 보고하지 않는다.

## 9. 구현 순서 및 완료 보고

**A 조사·계약 확정 → B 보더 → C 이미지 자동 준비 → D 아이콘 → F 상태 연결·통합 검증 → E 배경 레이어 확장** 순서로 진행한다. C와 D에도 F에 정의한 작업 상태·연결 규칙을 적용하고, 마지막에 전체 여정을 검증한다.

각 단계의 완료 보고에는 변경 파일·계약·DB·프롬프트·정책 버전, 재현 사례, 실행한 테스트, 실제 환경 검증 여부, 남은 제약을 포함한다. 단계 완료를 전체 기능 또는 Production 완료로 표현하지 않는다.

이 계획은 기존 정책 안에서의 구현 방안이다. 새로운 기능 지원 방식이나 정책 변경이 추가로 확정되면 `AGENTS.md`를 함께 갱신한다.

## 10. 추가 범위: 타이포그래피·컬러 선택의 단조로움

### 확인한 구조적 원인

- 현재 타이포그래피 역할은 기본 글꼴, 제목·본문 크기, 제목·본문 굵기·줄 높이 등으로 제한된다.
- 역할 하나는 `usagePolicy.bindings[role]`의 단일 토큰으로 연결된다. 등록된 토큰 전체가 AI의 선택 후보가 되는 구조가 아니다.
- AI의 설계 입력에는 활성 매핑된 `policyRoles`만 전달된다. 등록됐지만 역할에 연결되지 않은 스타일 토큰은 직접 선택할 수 없다.
- 렌더러는 모든 heading에 같은 `text.titleSize`, 나머지 text에 같은 `text.bodySize`와 기본 글자색을 먼저 적용한다. 제목 레벨만 바꿔도 자동으로 다른 토큰 크기가 적용되지는 않는다.
- 글꼴 굵기·줄 높이·보조색 역할은 AI가 선택한 경우에 적용하므로, 기본 역할만 사용하면 화면의 위계가 약해질 수 있다.

### 개선 계획

1. 실제 등록 토큰과 활성 매핑을 대조해 등록·노출·선택·렌더링의 각 단계별 사용 가능 목록을 만든다. Production 등록 상태를 확인하기 전에는 특정 토큰이 누락됐다고 단정하지 않는다.
2. 히어로 제목·섹션 제목·카드 제목·본문·보조 설명·라벨·강조 수치 등 콘텐츠 역할을 정의하고, 해당 용도에 적합한 등록 토큰 후보를 연결한다.
3. 역할별 허용 후보 또는 등록된 스타일 조합을 AI에 제공하는 계약을 설계한다. 토큰 전체를 무분별하게 공개하거나 버튼 전용 토큰을 일반 텍스트에 사용하지 않는다.
4. 크기·굵기·줄 높이·색상을 함께 고려하되 각 값은 등록 토큰에서만 선택한다. 모바일 대응과 색 대비를 검증한다.
5. 기존 단일 매핑은 기존 문서의 호환 경로로 유지한다. 새 선택 계약과 서버·브라우저 검증·렌더러를 함께 버전 관리한다.
6. 토큰 사용량을 늘리는 것을 목표로 하지 않는다. 콘텐츠 위계에 맞는 일관된 조합을 선택하고, 미등록 값 대체와 가독성을 해치는 무작위 변형을 금지한다.

검증에는 제목 레벨별 역할 선택, 실제 computed style과 등록값 일치, 잘못된 대상 토큰 차단, 컬러 대비, 모바일 잘림, 기존 문서 저장·재조회·출력 호환을 포함한다. 단계 A의 사용 가능 목록 작성에 이 범위를 포함하고, 단계 B의 공통 스타일 계약 보완과 연계한다. 코드와 로컬 검증을 추가했으며 실제 운영 등록 상태와 모델 효과 검증은 남아 있다.
