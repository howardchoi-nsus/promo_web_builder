# 채팅·요청 요약·페이지 미리보기·디자인 미리보기 개선 계획

작성일: 2026-11-15 (Asia/Seoul)  
기준 코드: `ea6b255` / `codex/ai-quality-review-agent`  
상태: 계획서 작성. 이 문서는 추가 구현·정책 반영·운영 배포 완료를 의미하지 않는다.

## 1. 목표

고객이 채팅으로 요청하고, 서술형 요청 요약과 전체 콘텐츠가 보이는 와이어프레임을 확인한 뒤 구성을 승인하도록 한다. AI는 요청에 맞는 PageSchema를 설계하고, 최종 디자인은 등록된 토큰과 활성 사용 정책으로 렌더링한다. 운영 버전 차이, 기존 미리보기 경로, 토큰 선택, 미디어 연결 중 어디서 문제가 생겼는지 구분할 수 있게 한다.

유지할 서비스 흐름:

자연어 요청 → 요청 요약 → 페이지 미리보기 → 고객 구성 승인 → 미디어 준비 → 디자인 미리보기 → 자동 검사·제한된 보정 → 출력

고객 입력·수정·승인은 왼쪽 채팅에서 진행한다. 오른쪽에는 요약과 미리보기를 표시한다. 화면 크기 전환 등 보기 기능은 유지한다.

## 3. 1차: 실행 경로와 배포 기준선 확인 — P0

### 작업

- 작업 브랜치, 원격 main, 실제 서비스의 배포 커밋을 대조한다.
- 대표 문서에 대해 문서 ID·Revision, 사용한 생성 API, 기존 경로/PageSchema 경로, 활성 프롬프트·모델·스킬 버전을 관리자 실행 기록으로 확인한다.
- 같은 요청의 입력 요약, AI 반환 구조, 검증 후 구조, DB 재조회 구조, 미리보기 구조를 비교한다.
- migration 091/092 및 관련 활성 설정을 확인한다. 092는 품질검토 프롬프트 Draft를 생성하므로 마이그레이션 성공과 검증·활성화를 구분한다.
- 기술 진단은 고객 화면에 노출하지 않고 관리자·개발 기록에서 확인한다. 원문 요청·비밀 값의 불필요한 기록을 피한다.

### 완료 기준

증상별로 ‘미배포’, ‘기존 경로 사용’, ‘AI 생성 문제’, ‘저장·복원 문제’, ‘렌더링 문제’, ‘설정 누락’ 중 확인된 원인을 근거와 함께 분류한다. 접근할 수 없는 운영 정보는 미확인으로 남긴다.

## 4. 2차: 채팅 6개 항목 확인·보완 — P0

기존 구현을 재사용하고, 아래 인수 기준에서 실패한 부분만 수정한다.

| 항목 | 목표 동작 및 인수 기준 |
| --- | --- |
| 과거 CTA | 현재 맥락이면 정상 처리. 완료·만료·이전 문맥이면 현재 상태와 가능한 다음 행동 안내. 과거 승인·생성을 재실행하거나 409를 반복하지 않음 |
| 단계와 Mask reveal | 요청 분석·구성 설계·미디어 생성·품질검사 등 실제 작업에 맞는 단계 표시. reduced motion에서는 즉시 표시. 애니메이션이 입력·처리 잠금 원인이 되지 않음 |
| 이력 행 추가 | 시작·단계 변경·완료·실패·재시도는 새 행. 기존 행의 문구 유지. 동일 폴링 결과 중복 억제. 지난 시작 행은 계속 진행 중으로 표시하지 않음 |
| 예상 잔여 시간 | 관측한 처리 시간만 사용. 근거가 없으면 ‘예상 시간 계산 중’. 현재 구현은 앱 실행 중 측정치 기반이며 세션 간 통계 기능과 구분. 의미 있는 ETA 변경이 생길 때 새 이벤트 기록 |
| 입력창 확장 | 하단 고정 상태에서 위로 확장. 현재 최대 높이 180px 이후 내부 스크롤. 전송 후 축소. 붙여넣기·가로폭 변경·한글 조합·Shift+Enter 정상 처리 |
| 사용자 메시지 | 텍스트 오른쪽 정렬과 내용에 맞는 말풍선 폭. 긴 문장·URL은 최대 폭 안에서 줄바꿈. RTL 전환 없이 한글·영문·숫자 혼합 표시 |

진행 이력은 DB 저장·재조회 및 새로고침 후에도 순서·단계·상태를 보존해야 한다. 현재 단계는 메시지 문구 추측보다 실제 작업 상태를 기준으로 연결하고, 상태 표시용 로직과 생성·승인 상태를 분리한다.

## 5. 3차: 요청 요약 서술형 전환 — P1

### 작업

- 목적·핵심 혜택·대상·분위기·예정 콘텐츠를 상단에서 표 또는 속성 목록 대신 1~2개 문단으로 표시한다.
- 구조화된 overview를 원본 데이터로 유지하고, 문장 표시용 변환 함수를 분리한다. 표시 형식 변경 때문에 별도 LLM 호출을 추가하지 않는다.
- 미입력 항목은 문장에서 생략하고, ‘미입력’을 자연어에 끼워 넣지 않는다.
- 혜택의 금액·대상·조건·통화·순서를 보존한다. 서로 다른 혜택의 조건을 합치지 않는다.
- 예정 콘텐츠는 실제 `contentSections` 순서를 사용한다. 헤더·히어로 등을 정해진 목록으로 덧붙이지 않는다.
- 이번 변경은 상단 요약에 우선 적용한다. 기존 ‘세부 내용 보기’의 상세 표는 유지하며, 상세까지 서술형으로 바꾸는 작업과 구분한다.

### 표시 예시

아래 문장은 입력 데이터에 해당 사실이 있을 때만 사용한다.

> 신규 고객을 위한 경품 지급 프로모션 페이지를 제작합니다. 핵심 혜택은 $100 무료 티켓과 포커달러, 100% 매칭 보너스이며 활기찬 분위기로 구성합니다.
>
> 예정 콘텐츠는 보너스 소개, 주요 혜택, 참여 방법으로 구성합니다.

### 완료 기준

금액·조건·목록이 원본 데이터와 일치하고, 자연어 수정 직후 요약이 갱신된다. 기존 구성 결과가 오래된 경우 기존 안내를 유지한다. 고객 편집 폼은 추가하지 않는다.

## 6. 4차: 와이어프레임과 동적 구조 개선 — P1

### 6.1 정렬 의미 구분

기존 ‘가로 배치’는 컴포넌트 박스의 부모 영역 내 위치(`justify-self`)이며 텍스트 정렬과 다르다. 채팅 요청을 다음처럼 구분한다.

- ‘카드를 오른쪽으로’: 부모 영역 내 컴포넌트 배치.
- ‘글자를 가운데로’: 텍스트 노드의 내부 정렬.
- ‘카드를 가로로 나란히’: 부모 grid/stack의 방향·컬럼 구성.

기존 계약이 해당 표현을 지원하는지 먼저 확인한다. 부족하면 구조화 출력·공통 계약·서버 검증·렌더러·저장 호환을 함께 수정하고, 임의 CSS 문자열로 우회하지 않는다. 별도 고객 정렬 폼을 추가하지 않는다.

### 6.2 전체 콘텐츠와 기술 정보

- 기존 미리보기의 문자열 말줄임과 반복 항목 일부 표시를 제거한다. 보안상 URL·내부 키 필터는 별도 판단하여 유지한다.
- 원문 전체를 실제 줄바꿈과 콘텐츠 높이로 표시한다. tooltip만으로 전체 표시를 대신하지 않는다.
- 공백·문단·리스트·반복 카드가 원본과 일치하는지 확인한다.
- 고객 화면의 ‘기술 정보 보기’를 제거한다. 관리자 진단에서는 경로·구조·검증 정보를 확인할 수 있게 유지한다.

### 6.3 자유로운 구조 설계와 기존 문서 호환

- 신규 생성은 PageSchema 경로로 이어지는지 확인한다. 기존 저장 문서의 표시·재시도 지원은 유지하며 일괄 변환하지 않는다.
- 활성 `promo_page_schema_planner`와 전달 입력에 고정 섹션 수·순서·템플릿을 강제하는 지침이 있는지 점검한다.
- 구체적 수정 요청은 현재 구조를 입력으로 받아 필요한 노드·순서·중첩·배치를 변경하도록 한다. 문구만 바꾸고 완료 처리하지 않는다.
- 최근 구조 해시 경고와 명시적 수정 요청의 이행 검사를 구분한다. 같은 콘텐츠에서 적절한 구조가 반복되는 것 자체를 오류로 보지 않는다.
- 요청과 무관하게 무작위 구조를 강제하거나 무제한 재생성하지 않는다. 미반영은 제한된 재시도 또는 구체적인 원인 안내로 처리한다.
- 와이어프레임과 승인 후 디자인은 동일 PageSchema 구조·반응형 배치를 사용한다. 구조가 달라지는 보정은 기존 승인 절차로 돌린다.

### 완료 기준

‘2열로 변경’, ‘혜택을 히어로 내부로 이동’, ‘모바일에서 순서 변경’ 요청이 해당 계약 범위에서 구조에 반영된다. 저장·재조회 후에도 반영되고, 컴포넌트 전체 내용이 보인다. 신규·기존 문서에서 고객 기술 정보가 노출되지 않는다.

## 7. 5차: 디자인 토큰·미디어 출력 개선 — P1

### 7.1 공통 선택 경로 추적

Admin 등록 토큰 → 활성 사용 정책 → 요소·속성·상태별 호환 후보 → AI 역할 선택 → 검증 → 저장·재조회 → 최종 CSS 순서로 확인한다.

각 요소의 선택 역할·토큰·제외 사유를 관리자 진단에 연결한다. 출력물에는 빌더 `--app-*` 스타일, 미등록 값 또는 임의 대체값을 적용하지 않는다.

### 7.2 타이포그래피

- 제목·리드·본문·보조 설명·강조 수치별로 사용 가능한 색상·크기·굵기·행간 후보를 점검한다.
- 등록돼 있어도 대상이 호환되지 않는 토큰은 제외한다. 버튼 라벨 전용 색상을 본문에 전용하지 않는다.
- 호환 후보가 충분한데 AI가 기본 역할만 반복하는 경우 planner 지침과 입력 후보 표현을 개선한다.
- 크기·색상을 무조건 여러 개 사용하도록 강제하지 않는다. 위계·가독성·반응형을 기준으로 검토한다.

### 7.3 보더

- 필요한 요소의 color·width·style 조합과 상태별 매핑을 검증한다.
- 필수 토큰이나 매핑이 없으면 관리자 설정 누락으로 분류한다. 임의 `solid`·픽셀·색상을 만들어 우회하지 않는다.
- 보더가 불필요한 요소에까지 필수 적용하지 않는다.

### 7.4 이미지·키비주얼·아이콘

- 콘텐츠 요청 → 이미지/아이콘 노드 또는 참조 → 생성 작업 → 완료 에셋 → PageSchema 바인딩 → 브라우저 로딩을 단계별로 검사한다.
- 생성 실패, 연결 누락, 비어 있는 노드, 로딩 실패, 텍스트에 가림을 별도 원인으로 분류한다.
- 필요한 미디어가 준비되기 전에 디자인 준비 완료로 표시하지 않는다.
- 재시도에서 완료된 이미지를 보존하고 실패한 항목만 재개한다.
- 텍스트 대비·이미지 가림·화면별 이미지 비율을 자동 검사한다. 구조 변경이 필요하면 구성 재승인 절차를 유지한다.

### 완료 기준

대표 페이지에서 요청된 미디어가 실제 로딩되고, 보더 및 타이포그래피가 등록 토큰의 유효한 역할로 렌더링된다. 후보 부족·매핑 누락·외부 생성 실패를 구분해 안내한다. 보더나 이미지가 필요 없는 페이지에 장식을 의무화하지 않는다.

## 10. 릴리스와 완료 판정

1. 1차 기준선 확인 후 원인별 수정 범위를 확정한다.
2. 2~4차 화면·구조 개선을 검증 가능한 단위로 반영한다.
3. 5차 토큰·미디어 개선 후 핵심 여정 전체 회귀를 수행한다.
4. Preview에서 실제 LLM·테스트 DB·미디어 저장소로 통합 검증한다. 연결 불가 항목은 미검증으로 보고한다.
5. 코드·마이그레이션·활성 프롬프트·모델·스킬·토큰 정책 버전을 대조한 후 Production에 반영한다.
6. 실제 배포 커밋과 서비스 핵심 여정을 확인한 뒤 완료로 보고한다. 소스 푸시만으로 완료 처리하지 않는다.

새 스키마 변경이 필요하면 기존 문서 호환과 롤백을 먼저 정의한다. 프롬프트·토큰 정책의 이전 활성 버전과 마지막 정상 배포를 기록한다. 롤백 시 고객 문서·이미지·대화 이력은 삭제하지 않는다. 과거 한시적 Preview 생략 승인을 이번 배포에 자동 적용하지 않는다.
