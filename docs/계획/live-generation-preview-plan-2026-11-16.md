# 실시간 생성 미리보기 구현 계획

작성일: 2026-11-16 (Asia/Seoul)  
기능명: 실시간 생성 미리보기 / Live Generation Preview  
렌더링 방식: 점진적 렌더링 / Progressive Rendering  
상태: 정책 확정·계획 작성. 애플리케이션 구현 및 배포는 이번 작업에 포함하지 않는다.

## 1. 목표와 참고 영상

첨부 영상에서는 회색 와이어프레임이 먼저 나타나고, 색상·텍스트·이미지가 화면별로 채워진 뒤 완성 결과를 보여준다. 영상 자체로 실제 AI 응답 스트리밍과 사후 애니메이션을 구분할 수는 없다.

이 서비스에서는 실제 완료 결과를 점진적으로 반영한다. 승인 구조를 유지한 채 준비된 영역은 먼저 보여주고, 생성 중인 영역만 로딩 상태로 표시한다. 단순 애니메이션 재생을 AI 생성 완료로 취급하지 않는다.

## 2. 기존 기능과 적용 범위

- PageSchema와 공통 렌더러, 구성 승인, 순차·재개 가능한 이미지 준비, 완료 에셋 보존, 자동 검사·보정을 재사용한다.
- `page-media-preparation.mjs`는 저장된 snapshot·Revision을 `onUpdate`로 전달한다. 이 완료 단위를 활용한다.
- 1차는 기존 검증·저장 결과의 표시 방식 개선이다. 모델의 토큰 스트리밍, 서버 SSE/WebSocket, 병렬 이미지 생성은 필수 요건이 아니다.
- 이미 PageSchema에 적용된 스타일을 별도 AI가 단계마다 새로 만드는 것처럼 표현하지 않는다. ‘스타일 적용’은 실제 검증된 토큰을 화면에 적용하는 단계다.
- 1차 구현 때문에 모델·프롬프트·스킬을 추가하지 않는다. 히어로 배경 이미지 정책과 이 표시 기능은 별개 변경으로 관리한다.
- 기존 비-PageSchema 문서는 현재 미리보기 경로를 유지한다. 지원 여부를 명시하며 강제 변환·일괄 마이그레이션하지 않는다.

## 3. 고객 여정

| 시점 | 오른쪽 미리보기 | 왼쪽 채팅 |
| --- | --- | --- |
| 구성 승인 전 | 기존 와이어프레임 | 기존 구성 확인·승인 흐름 |
| 승인 후 | 승인 구조를 유지하고 준비 중인 미디어 위치를 표시 | 디자인 준비 시작 |
| 스타일 준비 | 유효한 등록 토큰의 배경·폰트·보더·간격 반영 | 실제 단계가 바뀔 때 새 이력 행 |
| 미디어 생성 중 | 해당 이미지 영역에만 로딩 표시 | 현재 작업·실제 완료 개수 안내 |
| 에셋 연결·로드 완료 | 준비된 이미지부터 짧은 Reveal로 표시 | 완료 또는 다음 작업 안내 |
| 검사·보정 | 완성된 결과 유지, 필요한 노드만 갱신 | 자동 검사·보정 내역 |
| 전체 통과 | 최종 디자인 유지 | 기존 새 창 보기·출력 기능 활성화 |
| 부분 실패 | 완료 결과 유지, 실패 영역 구분 | 원인·기존 재시도 흐름 제공 |

텍스트는 승인된 콘텐츠를 처음부터 읽을 수 있게 한다. 장식적 효과를 위해 문구 전체를 오래 숨기지 않는다. 모바일에서도 동일한 읽기 순서를 보존한다.

## 4. 상태와 데이터 설계

### 4.1 상태 분리

- 생성 작업: queued → running → persisted 또는 failed. 실제 서버 상태를 기준으로 한다.
- 미디어 표시: waiting → loading → ready 또는 failed. 저장된 바인딩과 브라우저 load/decode 결과를 함께 사용한다.
- 디자인 검사: not-ready → checking → passed 또는 blocked. 미디어 준비 및 현재 Revision과 연계한다.
- Reveal: not-played → played. 생성·승인 상태와 별개인 클라이언트 표시 상태다.

이미지 노드 외 텍스트·카드 등은 유효한 snapshot에 포함되면 바로 표시한다. 없는 작업의 진행 상태를 만들어 내지 않는다.

### 4.2 식별과 갱신

문서 ID·Revision·노드 ID·작업/에셋 ID를 기준으로 이벤트를 연결한다. 노드별로 작업·에셋이 바뀌었는지 판별하며 부모 문서의 Revision 증가만으로 모든 이미지 효과를 재생하지 않는다.

저장된 snapshot이 생성 결과의 원본이다. 필수 생성 상태는 기존 서버 기록·에셋 바인딩에서 복원하고, 로컬 상태만으로 완료를 판단하지 않는다. 화면 표시용 로컬 상태가 사라진 경우에도 완료된 결과를 처음부터 재생성하지 않는다.

지연 응답, 중복 polling 응답, 문서 전환, 동시에 진행된 수정은 기존 Revision 충돌 방어를 유지한다. 이벤트를 적용하기 전 현재 문서·작업과 일치하는지 검증한다.

## 5. 렌더링·효과 설계

- 공통 범용 렌더러를 유지하고 미리보기 전용 표시 계층에서 로딩·강조·Reveal을 제어한다. 별도 고정 섹션 템플릿을 만들지 않는다.
- 이미지 크기 영역은 PageSchema 배치와 선언된 비율을 기준으로 확보한다. 이미지 완료 때 텍스트나 아래 섹션이 크게 밀리지 않게 한다.
- 승인 구조를 모사하는 스켈레톤은 사용자 콘텐츠·편집 가능한 최종 노드가 아니다. 빌더 표시 계층이며 출력용 PageSchema에 저장하지 않는다.
- 실제 노드의 색상·타이포그래피·보더·오버레이는 기존 등록 토큰 정책을 따른다. 스켈레톤 표시 스타일이 출력 CSS에 섞이지 않도록 한다.
- 권장 Reveal 초안은 짧은 opacity 전환 250~400ms다. 구현 시 가독성과 재측정 영향을 검증해 확정한다. 채팅의 1.8초 Mask reveal과 별도 효과이며 이를 자동 복사하지 않는다.
- 색상 대비가 낮은 상태로 실제 이미지 위 텍스트를 먼저 노출하지 않는다. 미디어 준비 동안 승인된 구조를 보존하는 중립적 준비 표시로 처리하고 실제 조합을 검사한다.
- 자동 스크롤·줌·포커스 이동은 도입하지 않는다. reduced motion은 효과 없이 즉시 표시한다.

## 6. 자동 품질검사와 출력 격리

부분 렌더 중의 스켈레톤·숨김·투명도 전환을 실제 페이지 결함으로 측정하지 않는다. 검사에서는 표시 효과를 제거한 동일한 최종 구조를 사용하고, 필수 미디어 로딩·디코딩을 확인한다. 로딩 실패는 건너뛰어 통과 처리하지 않는다.

코드 보정과 AI 품질검토의 기존 횟수 제한을 유지한다. 구조가 달라지면 기존 구성 승인으로 돌아간다. 보정 패치로 영향받지 않은 완료 에셋은 유지한다.

출력·새 창 보기·HTML 다운로드에는 로딩 계층과 Reveal용 미리보기 스타일을 포함하지 않는다. 전체 준비와 현재 Revision의 품질검사·필수 AI 검토를 통과한 결과만 기존 출력 기능으로 연결한다.

| 순서 | 작업 | 주요 대상 | 완료 기준 |

| 2 | 노드별 표시 상태 모델 구현 | 신규 표시 상태 helper, 기존 서비스 콜백 | 정상·실패·중복·지연·문서 전환 상태 회귀 통과 |

기존 iframe/srcdoc 갱신이 전체 문서를 다시 만들어 Reveal 상태를 잃는지 1단계에서 확인한다. 필요한 경우 노드별 표시 상태를 부모에서 유지하고 검증된 메시지 채널로 표시 상태만 전달한다. 이때 수신 origin/source·문서/노드 ID를 검증하고 임의 HTML·스크립트를 전달하지 않는다. 구현 전에 현재 통신 구조에 맞춰 최소 변경안을 결정한다.

## 9. 도입·복구와 완료 판정

미리보기 표시 계층을 비활성화하면 기존 최종 렌더링으로 복귀할 수 있게 구현한다. 복구 때문에 PageSchema·에셋·승인·대화 이력을 삭제하지 않는다. 새 DB 필드는 기존 기록으로 복원할 수 없는 상태가 확인되는 경우에만 설계하고 별도 마이그레이션을 작성한다.

빌드·회귀 통과와 실환경 검증을 구분하고, 코드·DB·프롬프트·토큰 사용 정책 버전을 확인한다. 실제 Preview 연결이 없으면 미검증으로 남긴다. 과거 배포의 한시적 예외를 이번 기능에 자동 적용하지 않는다.

완료 조건은 ‘생성 중 표시가 움직인다’가 아니라, 실제 완료 결과의 점진적 표시·중복 방지·부분 실패 복구·검사 격리·최종 출력 일치가 검증되는 것이다.

후속 개발에서 1차 점진적 표시 계층을 구현했다. 실제 이미지 준비 콜백, 노드별 표시, 검사 격리와 재시도를 연결했고 빌드 및 로컬 회귀 39개가 통과했다. 구체적 구현·검증 범위와 실환경 미검증 사항은 `live-generation-preview-implementation-2026-11-16.md`를 따른다. 위 ‘이번 작업은 계획 작성’ 문구는 최초 계획 작성 시점의 범위다.

## 후속 범위 보정

이미지 로딩 위주의 1차 구현은 요청한 전체 디자인 생성 과정을 충족하지 못했다. 후속 확정안과 실제 영역별 디자인 작업 구현·활성화 절차는 `live-generation-preview-v2-section-design.md`를 따른다. 새 흐름은 migration 093의 Admin 프롬프트와 `PAGE_SCHEMA_SECTION_DESIGN_ENABLED=true`가 필요하며, 위 1차 범위를 현재 최종 동작으로 간주하지 않는다.
