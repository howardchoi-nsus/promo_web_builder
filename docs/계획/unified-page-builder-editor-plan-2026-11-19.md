# 페이지 제작 통합·웹빌더 에디터 개발 계획

최초 작성 2026-11-19 · 최신 정책 결정 2026-11-23 · **제품 목표는 26절, 개발 반영 이력은 27절, 성능 개선·제한적 병렬 실행은 28절, Admin 작업 로그는 29절, 성능 선행 개발의 반영 범위는 30절을 기준으로 한다.**

기존 구현·로컬 검증 이력은 해당 절의 범위에 한정한다. 10~25절의 사용자 승인/재승인·상세 진행 행 관련 표현은 당시 설계·검증 이력이며 현재 목표 정책이 아니다. 26절 자동 진행·최소 정보·디자인 품질 우선의 코드 반영과 로컬 검증 범위는 **27절**에 기록한다. 운영 DB 설정·실제 모델 검증·배포는 별도이며 문서 갱신만으로 운영 기능이 바뀌지 않는다.

## 1. 확정 방향

최우선 목표는 요청과 콘텐츠에 맞는 다양한 구조 및 높은 디자인 품질이다. 상단 단계는 **1. 요청 요약 → 2. 페이지 제작**이며, 사용자는 자연어 요청 한 번으로 완료까지 진행한다. 와이어프레임은 확인용이고 단계별 승인·구조 변경 재승인·품질 승인으로 멈추지 않는다.

내부 구조 검증·저장·디자인·미디어·검사 상태는 분리해 유지한다. 자동 진행은 검증 생략이나 사용자 승인 기록 위조를 뜻하지 않는다. 대표 히어로 배경형도 가능한 구도 중 하나이며 고객 지정/콘텐츠/등록 토큰에 맞춰 선택한다. 완성 후 수정·출력은 선택적으로 제공한다.

## 2. 고객 흐름과 관리자 흐름

| 영역 | 사용자 경험 | 시스템/관리자 책임 |
|---|---|---|
| 요청 입력·요약 | 자연어와 선택적 참고 자료, 짧은 서술형 요약 | 개요 분석·사실·이미지 의도 보존, 진행을 멈추는 확인 버튼 없음 |
| 페이지 제작·구성 | 실제 스켈레톤/와이어프레임 누적 확인 | 단위 검증·저장·최종 조립 후 내부 검증으로 자동 전환 |
| 디자인·이미지 | 구도에 맞는 결과가 준비되는 과정 확인 | 등록 스타일·이미지 생성/저장/디코딩, 완료 에셋 보존 |
| 마무리 | 간단한 진행 안내 | 자동 검사·제한 보정·재검사, 필요 시 내부 구조 보정 |
| 완성 | 채팅/에디터 수정·새 창 보기·다운로드 선택 | 현재 Revision 품질/미디어/출력 게이트 |
| 복구 | 자동 복구 후 미해결일 때만 쉬운 설명과 행동 하나 | 세부 오류·요청 ID·실행 이력은 운영 로그, 완료 결과 보존 |
| Admin 설정 | 고객에게 노출하지 않음 | 정책·스킬·프롬프트·모델·토큰·검증/활성화·품질 비교 |

요약과 와이어프레임 확인은 선택적 관찰이며 고객의 승인 액션을 요구하지 않는다. 질문은 안전한 보완·미정 사실 제외로 진행할 수 없는 필수 선택에만 한정한다. 외부 공개 배포는 생성 자동화와 구분해 별도 권한을 따른다.

## 4. 상태와 데이터 계약

아래 명칭은 신규 UI 상태 설계안이며 기존 API enum에 즉시 추가하지 않는다.

`idle → planning → building → validating_structure → designing → preparing_media → checking → completed`

실패는 해당 작업 상태·완료 결과를 보존한다. 재시도는 실패 작업부터 재개한다. 새로고침에서는 서버 스냅샷과 현재 Revision으로 내부 상태를 복원한다. 상단 단계가 두 개라고 서버 상태까지 둘로 압축하지 않는다.

편집은 `completed → editing → saving → checking → completed`로 이어진다. 구조 변경은 `saving → validating_structure → 필요한 재처리 → checking`으로 이어지고 고객 재승인을 요구하지 않는다. 미해결 오류면 출력 게이트는 닫되 저장·되돌리기·안전한 복구 경로는 유지한다. 품질검사 실행 자체를 수동 승인으로 대체하지 않는다.

- 원본은 동일 documentId의 PageSchema와 콘텐츠 소스·토큰 버전·정책·미디어 바인딩이다. HTML/별도 편집 스냅샷을 새 원본으로 만들지 않는다.
- 변경은 baseDocumentRevision과 비교해 저장한다. 충돌 시 조용히 덮어쓰지 않고 편집 내용을 보존해 최신 버전과 해결한다.
- Undo/Redo는 현재 작업 세션의 명령 이력으로 제공한다. 저장된 과거 버전 복원은 새 Revision으로 기록해 감사·품질 이력을 유지한다.
- 저장 후 기존 품질 결과는 무효화한다. 검증된 구조 지문·자산·토큰 의존성에 따라 필요한 영역만 재처리하고 현재 Revision에서 최종 검사한다.
- 편집 중 자동 생성 응답이 늦게 도착하면 documentId/runId/Revision으로 차단한다. 두 화면이 동시에 편집하는 경우에도 같은 충돌 규칙을 적용한다.

## 5. 와이어프레임 생성과 Mouse Swarm

섹션별·컴포넌트별로 실제 동적 트리의 작업 대상을 표시한다. 기본 커서 풀은 12개이며 활성·대기를 구별한다. 바운딩 박스와 마우스 커서는 각각 그룹 단위로 `opacity: 0.5`(불투명도 50%)를 적용한다. 라벨·핸들·캐럿을 포함하되 자식에 중복 적용하지 않고 생성 콘텐츠·이미지는 흐리게 만들지 않는다. 텍스트 선택 박스·모서리 핸들·캐럿은 컴포넌트 작업에만 연결한다. 실제 입력 폼이나 편집 권한을 뜻하지 않는다.

생산 환경에서는 샘플의 숨긴 완성 템플릿·타이머·완료 텍스트 지연을 사용하지 않는다. 기존 전체 응답 API는 응답 전 대기 표시만 가능하다. 실제 누적 와이어프레임에는 아래 별도 계약을 사용하며 구현·활성화 상태는 15절을 따른다.

1. 생성 run·초안 단위·순서·의존 노드·소스 참조를 서버가 식별한다.
2. 부분 초안은 별도 계약으로 검증·저장한다. 현재 최종 문서 검증기의 h1·필수 소스 요구를 완화하지 않는다.
3. 클라이언트는 저장 이벤트 뒤 해당 초안을 가져와 누적 표시한다. 미완성 JSON 스트림은 렌더링하지 않는다.
4. 전체 조립본을 공통 PageSchema 계약으로 검증·저장한 다음 사용자 클릭 없이 디자인 단계로 자동 전환한다.
5. 텍스트 입력 효과는 검증·저장된 반영 단위가 있을 때만 사용한다. 전체 결과만 있으면 즉시 표시한다.

표시 계층은 사용자 입력을 막지 않으며, 축소 모션을 존중하고 품질검사·HTML/배포 출력에서 제외한다. 자세한 이벤트·표시 계약은 [Mouse Swarm 정책](../mouse-swarm-builder/policy.md)을 따른다.

## 6. 에디터 범위와 변경 규칙

| 기능 | 허용 방식 | 저장 이후 처리 |
|---|---|---|
| 일반 제목·설명 | 직접 텍스트 편집 / 선택 영역 AI 수정 | 사실 여부·소스 규칙 검증 후 재검사 |
| 잠긴 사실·혜택·법적 문구 | 근거/소스 변경 절차로 분리 | 원본 참조·조건 보존, 새 소스 검증 |
| 이미지·아이콘 교체 | 승인 에셋 선택 / 기존 생성 경로 | 기존 에셋 보존, 교체 대상만 준비·검사 |
| 글자색·크기·보더·간격 | 호환되는 등록 역할·토큰 후보 선택 | 미등록 값 저장 차단, 재검사 |
| 정렬·컬럼·반응형 | 허용 enum·비율·토큰 범위 | 구조 지문 변경 시 내부 재검증·자동 재검사 |
| 섹션 추가·삭제·순서 변경 | 동적 트리 명령 | 필수 콘텐츠·h1·깊이·노드 수 검증, 자동 재검사 |
| 되돌리기·이력 복원 | 명령 이력 / 새 Revision 복원 | 품질 상태 갱신 후 재검사 |

필수 사실 콘텐츠를 삭제한 문서는 최종 저장·출력 검증을 우회하지 못한다. 사용자가 의도적으로 요구사항을 변경하면 요구 요약·콘텐츠 소스를 정식 갱신한다. 일반 텍스트 수정으로 금액·URL 정책을 우회하지 않는다.

## 7. 프롬프트·스킬·모델

기존 [등록 패키지](../mouse-swarm-builder/README.md)를 유지하되 고객 화면 명칭은 ‘페이지 제작’ 내부 작업으로 변경한다.

| 내부 작업 | 기존 타입 | 변경 원칙 |
|---|---|---|
| 페이지 구조 설계 | promo_page_schema_planner | 필수 변수 유지, 동적 구조·안전한 소스·노드 경계 |
| 영역 디자인 | promo_page_section_designer | 내부 검증된 트리 보존, 등록 스타일 패치만 |
| 자동 검토·수정 | promo_page_quality_reviewer | 현재 Revision 측정값·허용 패치·최대 2회 |
| 에디터 선택 영역 AI 수정 | 구현 단계에서 기존 계약 재사용 가능성 검증 | 기존 section designer는 문구/트리 변경 불가. 범위가 다르면 별도 등록 타입·스키마·소유권·패치 계약을 설계한 뒤 도입 |

프롬프트 목록의 기존 여정 번호를 고객 화면 번호와 혼동하지 않는다. 단순 탭 통합을 이유로 내부 타입·모델을 삭제·교체하지 않는다. 새 프롬프트가 필요하면 필수 변수·응답 스키마·안전 계약·스킬 버전·회귀 검증을 함께 정의한다. 선택 영역 AI 편집은 기존 구조 설계 프롬프트를 사용하며 서버에서 선택 영역 밖 변경을 거부한다. 배경 키비주얼 `section_background_image`와 컴포넌트 이미지 `component_image`도 공통 브리프 Draft 적용 대상이며 기존 모델·변수 계약을 유지한다.

## 8. 개발 순서: 6단계, 단계별 검증 후 진행

| 단계 | 산출물 | 다음 단계 진행 조건 |
|---|---|---|
| 1. 공통 상태·호환 계약 | 2단계 상단·내부 상태, 버전/해시 있는 공통 디자인 브리프, 토큰 후보 선정·표현 가능성 계약 | 과거 세션 복원, 명시 요청/추론/미지원 구분, 브리프 저장·캐시 식별 검증 |
| 2. 페이지 제작 화면 통합 | 한 캔버스, 구조 단계에서 구도 설계·내부 검증, 브리프·토큰 후보를 구조/디자인/미디어/검토에 주입 | 구조 검증·저장 전 디자인 호출 없음, 전 단계 같은 브리프 버전, 요청 구도·후보 적합성 검증 |
| 3. 초안 누적 생성·스웜 | 서버 초안 검증/저장/조립, 이벤트 식별, 12커서·박스·캐럿 | 실제 저장 결과만 표시, 초안 최종 출력 불가, 지연/중복/다른 문서 이벤트 차단 |
| 4. PageSchema 직접 편집 | 실제 에디터 진입, 선택·텍스트·미디어·등록 스타일·배치·구조 명령, 필요한 표현 계약 확장 | 미리보기/에디터/출력 동일, 불법 변경 차단, 새 표현의 SSR/저장/구버전 호환 |
| 5. 선택 영역 AI·저장·복구 | 범위 제한 AI 수정 계약, Revision 저장, Undo/Redo·이력·충돌·복귀 | 선택 밖 변경 차단, DB 왕복·충돌·실패 복구에서 편집/완료 에셋 보존 |
| 6. 자동 재검증·출시 준비 | 저장 후 품질 무효화·내부 재검증·자동 재검사, 실제 Preview 통합, 롤백 | 아래 필수 TC와 실제 LLM·DB·Blob 여정 통과 후 Production 검토 |

## 10. 이행·롤백

- UI 통합과 PageSchema 편집은 기존 문서 타입으로 분기한다. 실제 누적 초안은 별도 PAGE_SCHEMA_DRAFT_ENABLED 플래그로 점진 적용한다.
- 초안 데이터·작업 이벤트 저장소에 새 테이블/필드가 필요하면 추가형 migration을 작성하고 idempotency·이전 문서 로드·복원 검사를 통과시킨다. 이 계획서는 migration 적용을 의미하지 않는다.
- Preview 통합 검증 전 활성 프롬프트·스킬·모델을 일괄 교체하지 않는다. 기존 활성 버전을 기록하고 필요한 Draft만 검증한다.
- 롤백 시 새로운 편집 결과를 삭제하거나 이전 스키마로 손실 변환하지 않는다. 미지원 문서는 안전한 읽기 전용 미리보기와 복구 안내로 보존한다. 기존 문서 생성/출력 경로를 유지한다.
- 후속 개발 요청에 따라 저장소 구현을 반영했다. Admin 등록/활성화·Production 배포는 수행하지 않았다. 최신 상태는 15절을 따른다.

## 12. 채팅 진행 이력·표시 효과 상세 규격

### 채팅 진행 메시지

생성 진행은 왼쪽 채팅에 일반 메시지로 표시한다.2026-11-25 확정 정책에 따라 단계별 새 행·같은 단계의 기존 행 갱신을 사용한다. 사용자에게 기술 노드 ID를 요구하거나 별도 진행 폼을 생성하지 않는다.

| 전환 | 메시지 예시 | 생성 근거 |
|---|---|---|
| 요청 정리 | ‘총4단계 중1단계 진행 중 · 요청 정리’ / ‘요청하신 목적과 콘텐츠를 정리하고 있어요.’ | 실제 요청 분석/참고 자료 처리 |

예시는 고정 섹션 이름을 뜻하지 않는다. 실제 동적 섹션·컴포넌트의 사용자 친화적 이름으로 표시한다. group 상태만 제공되는 경우 컴포넌트별 완료를 추정하지 않는다.

- 메시지 상단에는 서비스 단계/총4단계/상태, 아래에는 실제 작업의 짧은 설명을 표시한다. 내부 호출/모델/코드·세부 로그와 근거 없는 ETA/퍼센트는 노출하지 않는다. 커서 수로 진행률을 계산하지 않는다.
- 새 서비스 단계에 진입할 때만 새 행을 추가하고 동일 단계의 대상/문구/상태 변경은 기존 표시 행에서 갱신한다. 종료한 단계의 마지막 완료/실패 설명은 보존한다. 동일 이벤트 재수신·폴링·재시도로 행을 반복 추가하지 않는다.
- documentId/runId/taskId/상태 전환/이벤트 순서에 근거해 중복을 방지한다. 저장 이력을 재로드하면 같은 행과 순서로 복원한다. 지연된 이전 문서의 진행 메시지는 현재 작업에 섞이지 않는다.
- 진행 중 메시지의 작업 설명만 기존1.8초 주기의 Mask Reveal을 반복한다. 같은 단계의 갱신마다 효과를 초기화하지 않는다. 종료·실패·다음 단계 전환 시 효과를 해제하며 재생을 위해 작업/표시를 지연하지 않는다.
- 완료 행은 계속 읽을 수 있게 유지한다. 과거 CTA는 현재 문서·상태를 확인해 응답하되 승인·생성 작업을 중복 실행하지 않는다.
- 사용자가 이전 대화를 읽는 동안 하단으로 강제 이동하지 않는다. 새 진행 이력과 화면 효과는 키보드·스크린리더·모션 감소 설정을 존중한다.

### 바운딩 박스·스웜 커서 불투명도

- 바운딩 박스 그룹과 마우스 커서 그룹에 각각 **opacity: 0.5 (불투명도 50%)**를 적용한다.
- 박스의 라벨·핸들·캐럿 및 커서 라벨은 각 그룹에 포함한다. 자식에 다시 0.5를 적용하여 최종 25%가 되지 않도록 한다.
- 공통 오버레이 부모, 캔버스, 생성된 텍스트·이미지의 opacity는 변경하지 않는다. 실제 에디터 선택 도구의 불투명도까지 자동 변경하는 규칙은 아니다.
- 이는 미리보기 표시 계층의 값이다. PageSchema·디자인 토큰 출력·품질검사 대상·HTML 다운로드에 저장하거나 포함하지 않는다.

### 개발 단계와 검증 연결

기존 6단계를 늘리지 않는다. 2단계에 채팅 이력·전환·복원 계약을, 3단계에 실제 작업 이벤트 연결 및 opacity 50%를, 6단계에 통합 회귀를 포함한다.

| TC | 검증 | 기대 결과 |
|---|---|---|
| P01 | 섹션/컴포넌트 작업 전환 | 실제 대상·단계·상태가 새 채팅 행으로 추가 |
| P02 | 중복 폴링·이벤트 재전송 | 중복 메시지 없음, 기존 문구 보존 |
| P03 | 새로고침·과거 작업 응답 | 저장된 순서 복원, 다른 문서 이벤트 차단 |
| P04 | 진행·완료·실패·재시도 | 진행 행에만 Mask Reveal, 종료 효과 정리, 완료 결과 보존 |
| P05 | 예상 시간 데이터 유무 | 실측 추정 또는 계산 중 표시, 임의 카운트다운 없음 |
| P06 | 박스·커서·자식·콘텐츠 스타일 | 그룹 opacity 0.5, 자식 중복 감쇠 없음, 생성 콘텐츠 불변 |
| P07 | 이전 대화 읽기·모션 감소·모바일 | 강제 스크롤 없음, 접근성·기존 CTA 정상 |

본 절은 계획 상세화다. 샘플의 opacity 적용 여부와 실서비스의 채팅 작업 이벤트 연결 구현 여부는 구분해 보고한다.


## 13. 최종 출력: HTML·CSS·필요한 JavaScript

### 확정 구조

| 영역 | 기술/데이터 기준 |
|---|---|
| 빌더·채팅·에디터 | 기존 프레임워크 유지, 편집·상태 관리 담당 |
| 생성·편집 원본 | 검증된 PageSchema JSON·소스·토큰/정책 버전·미디어 바인딩 |
| 미리보기 | 공통 렌더링 규칙으로 같은 원본을 해석 |
| 배포·다운로드 | 프레임워크 런타임 없는 HTML·CSS·필요한 JavaScript |
| 정적 콘텐츠만 있는 결과 | JavaScript 없이 HTML·CSS와 에셋만 포함 |

AI → PageSchema → 공통 스키마·정책 검사 → 현재 Revision 품질검사 → 검증된 exporter → HTML·CSS·허용 JavaScript·에셋 순서로 출력한다. 내보낸 HTML을 에디터의 새 원본으로 역변환하지 않는다. 문서에서 다시 편집하고 새 Revision의 출력물을 재생성한다.

### 패키징 기준

- 기본 다운로드 패키지는 index.html, styles.css, 필요한 경우에만 interactions.js, assets/로 구성한다. 단일 HTML 옵션은 필요한 스타일·허용 동작·에셋을 포함할 수 있지만 동일한 검증을 적용한다. 파일명은 구현 시 고정해 호환성을 관리한다.
- HTML은 의미 있는 문서 구조·접근성·안전한 URL·텍스트 이스케이프를 유지한다. CSS는 원본에 고정된 등록 토큰·사용 정책·레이아웃 규칙에서 생성한다.
- JavaScript는 서버가 허용한 기능 식별자·설정에 대응하는 검증된 정적 모듈만 선택한다. 임의 inline 이벤트·eval·AI 생성 스크립트는 허용하지 않는다. 메뉴·탭·아코디언은 지원 스키마·접근성·동작 계약을 구현한 경우에만 출력한다.
- 프레임워크 hydration, 빌더 앱 번들, 관리자 API·로그인 세션, 채팅·커서·바운딩 박스·타자 효과·편집 이력을 포함하지 않는다. 빌드/서버 내부에서 프레임워크를 사용하더라도 최종 브라우저 산출물에는 프레임워크 런타임을 요구하지 않는다.
- 이미지·동영상·폰트의 허용된 사용·배포 경로를 검증한다. 인증이 필요한 이미지 API·단기 만료 URL을 그대로 넣어 외부 호스팅에서 깨지지 않도록 에셋 복사 또는 지속 가능한 공개 배포 경로를 사용한다. 오프라인을 지원하는 패키지는 외부 리소스 의존성도 제거해야 한다.
- SPA 서버나 특정 호스팅 rewrite가 없어도 정적 호스팅에서 정상 작동해야 한다. 브라우저에서 로컬 HTML을 열어 지원하는 범위와 HTTP 호스팅이 필요한 미디어 기능을 구분해 검증한다.
- 출력 manifest에는 원본 문서/Revision·토큰/정책/렌더러/exporter 버전·에셋 해시를 연결한다. 인증정보나 비공개 실행 컨텍스트는 포함하지 않는다. 이는 신규 패키지 계약 설계이며 현재 구현 완료를 의미하지 않는다.

### 기존 6단계에 반영

1단계에서 출력 형식·허용 동작·에셋 계약을 정의한다. 4단계에서 공통 PageSchema 해석·CSS 생성·에디터 동등성을 유지하며 exporter를 보완한다. 6단계에서 정적 호스팅·브라우저·접근성·미디어·인터랙션과 출력 격리를 검증한다. 새로운 7단계를 추가하거나 빌더 전체를 바닐라 JavaScript로 재작성하지 않는다.

### 추가 출력 TC

| TC | 시나리오 | 기대 결과 |
|---|---|---|
| O01 | 정적 페이지 다운로드 | HTML·CSS·에셋으로 정상 표시, 불필요한 JavaScript 없음 |

| O04 | 동일 Revision 비교 | 미리보기·에디터·출력의 텍스트·토큰·반응형·미디어 일치 |

## 14. 와이어프레임·이미지 전환과 작업 피드백

### 효과 규격

| 상황 | 표현 | 목표 시간/조건 |
|---|---|---|
| 텍스트 반영 | 문구 단위 Mask Reveal, 실제 Range 경계의 캐럿 | 600ms 1회, 검증·저장된 전체 문구는 즉시 DOM 반영 |
| 컴포넌트 추가 | 페이드인 + 아래 6px에서 제자리 이동 | 250ms, 최종 레이아웃 공간을 먼저 확보 |
| 위치·정렬·순서 변경 | 실제 이전/다음 DOM 위치를 측정한 이동 | 340ms, FLIP 또는 동등 방식 |
| 크기·컬럼 변경 | 최종 박스 크기를 반영한 짧은 전환 | 250~350ms, 읽기 순서와 내용 보존 |
| 키비주얼 반영 | 와이어프레임 이미지 자리와 실제 이미지 크로스페이드 | 650ms, 에셋 저장·브라우저 load/decode 성공 후 |
| 일반 컴포넌트 이미지 | 짧은 크로스페이드 | 300~450ms, 동일 준비 조건 |
| 작업 대상 | 실제 진행 대상 테두리 강조 | 작업 중에만, 커서/박스는 opacity 0.5 유지 |
| 작업 완료 | 짧은 테두리 강조·완료 라벨 후 제거 | 약 1.4초, 결과를 지연하지 않는 표시 계층 |
| 변경 영역 | ‘수정됨 · 배치 변경’ 등 대상별 라벨 | 실제 수정 발생 후 약 1.4초, 채팅 이력은 보존 |
| 실패 영역 | 이동·진행 효과 정지, 작은 실패 라벨 | 실제 실패 동안, 상세 원인·재시도는 채팅 |

시간은 미리보기 표시의 목표값이며 모델 호출·서버 저장·작업 완료 시간을 조작하지 않는다. 타이핑 샘플이 있어도 Production에서는 검증·저장된 문구 전체를 일부러 늦게 출력하지 않는다.

### 레이아웃 안정성과 상태 연결

- 완료 이벤트에서 즉시 결과를 반영하고 효과를 시작한다. 애니메이션 종료를 기다렸다가 결과를 저장하거나 완료로 처리하지 않는다.
- 텍스트·이미지 플레이스홀더는 제공된 콘텐츠 길이·종횡비·등록 레이아웃에 맞춰 공간을 예약한다. 임의 고정 높이로 빈 공간을 늘리거나 잘림을 숨기지 않는다.
- 이동은 실제 nodeId가 같은 요소의 이전/최종 위치를 연결한다. 레이아웃 확정은 먼저 수행하고 표시 transform을 짧게 보간해 주변 요소 흔들림을 줄인다. 동시에 많은 대상이 바뀌면 섹션 단위로 묶고 중첩 애니메이션을 피한다.
- 사용자 직접 드래그·입력에는 지연을 주지 않는다. 조작 완료 후 정렬·스냅이 필요한 경우에만 짧게 전환한다. 프레임워크/렌더러 계약상 이동이 불가능하면 즉시 최종 위치를 표시한다.
- 이미지 전환은 텍스트나 CTA를 함께 페이드/이동하지 않는다. 로딩·디코딩 실패는 성공 효과로 처리하지 않으며 재시도에서도 완료된 다른 영역을 보존한다.
- 같은 자산·Revision의 재수신, 레이아웃 보기 전환, 모바일/데스크톱 전환, 재접속에서는 생성 완료 효과를 반복하지 않는다. 명시적 레이아웃 수정의 이동 효과와 단순 화면 크기 변경을 구분한다.
- 화면 밖 대상은 강제로 스크롤하지 않는다. 상태는 채팅에서 확인할 수 있게 하고 표시 계층이 사용자 포커스·키보드·읽기 순서를 방해하지 않게 한다.

### 효과만 일시정지

채팅 또는 기존 서비스 조작 영역에서 ‘효과만 일시정지 / 효과 다시 재생’을 제공한다. 생성 캔버스에 고객 액션 버튼을 추가하지 않는다.

- 스웜 커서·선택 박스·캐럿·강조·이동·Reveal 표시만 멈추거나 숨긴다. 실제 생성·저장·미디어 준비·자동 검사와 채팅 상태 업데이트는 계속한다.
- 서버 작업 중지/취소와 다른 기능임을 명시한다. 샘플의 ‘생성 일시정지’와도 구분한다.
- 정지 중 완료된 결과는 즉시 확인할 수 있어야 한다. 재개 시 지나간 완료 효과를 몰아서 재생하지 않고 현재 작업 상태에 맞춘다.
- 모션 감소 설정에서는 이동·깜빡임·타자·Reveal·크로스페이드를 제거하고 결과와 상태를 즉시 표시한다. 실패 이유·완료 내역은 채팅의 정적 문구로 계속 제공한다.

### 책임·개발 단계

프런트엔드 표시 계층이 담당하며 AI 스킬/프롬프트가 좌표·애니메이션 CSS·진행률을 생성하지 않는다. 출력 HTML·CSS·JavaScript에는 이 빌더 효과와 라벨을 포함하지 않고 품질검사는 효과를 제거한 실제 최종 배치에서 수행한다.

기존 **6단계**를 유지한다. 2단계에 효과 조작·채팅 상태 연결, 3단계에 와이어프레임/이미지 전환·실제 작업 피드백, 4단계에 에디터 변경 대상 식별·이동 처리, 6단계에 아래 검증을 포함한다. 샘플의 ‘배치 수정 체험’은 시연용이며 Production에 고정된 카드 순서 변경 버튼으로 옮기지 않는다.

| TC | 검증 | 기대 결과 |
|---|---|---|
| F01 | 문구·컴포넌트 추가 | 검증·저장 후 즉시 반영, 짧은 등장 효과, 공간 안정 |
| F02 | 위치·정렬·순서·컬럼 변경 | 같은 노드의 이전/최종 위치 연결, 중첩·입력 지연 없음 |
| F03 | 이미지 로딩/디코딩 지연·실패 | 준비 완료 전 공개/성공 처리 없음, 완료 후 크로스페이드 |
| F04 | 완료·수정·실패 피드백 | 실제 대상/상태와 일치, 완료 효과 정리·실패 라벨 및 채팅 유지 |
| F05 | 효과만 정지한 상태에서 생성 완료 | 서버 작업·저장·검사 계속, 결과 즉시 표시, 재개 시 과거 효과 미재생 |
| F06 | 단순 보기 전환·재접속·중복 응답 | 완료 이미지/피드백 재생·작업 재실행 없음 |
| F07 | 모션 감소·모바일·스크롤·키보드 | 즉시 상태 표시, 강제 이동/입력 차단 없음 |
| F08 | 품질검사·HTML 다운로드 | 표시 계층 제외, 현재 Revision 검사 및 출력 일치 |

샘플에서는 이미지 디코딩 후 650ms 전환, 작업 강조, 완료/수정/실패 피드백, 배치 이동, 효과만 일시정지의 동작을 확인했다. 이는 실제 서비스의 작업 이벤트·DB·LLM 통합 검증 완료를 의미하지 않는다.


## 15. 개발 반영 결과와 운영 전환 조건

| 단계 | 구현 결과 | 검증 / 남은 조건 |
|---|---|---|
| 1. 공통 계약 | 원래 요청·수정 요청·아트디렉션·등록 토큰 후보 순위를 공통 브리프로 전달 | 계약·토큰 호환성 검사 통과 |

### 적용 순서

1. 기존 DB 버전 확인 후 094·095 마이그레이션을 적용한다. 094는 활성 프롬프트를 바꾸지 않고 스킬도 비활성으로 등록한다. 기존 스킬 연결이 4개라 Draft 생성을 건너뛴 타입은 충돌을 검토한다.
2. Admin에서 4개 스킬과 관련 Draft를 검증하고 필요한 버전만 활성화한다. 095의 `promo_page_outline_planner`, `promo_page_fragment_writer` 두 타입도 검증·활성화한다. 현재 등록된 모델·실행 설정을 유지한다.
3. `PAGE_SCHEMA_DRAFT_ENABLED=true`로 누적 생성을 켠다. 영역 디자인은 기존 093과 해당 활성 프롬프트를 확인한 뒤 `PAGE_SCHEMA_SECTION_DESIGN_ENABLED=true`를 설정한다. 미디어에는 기존 Blob 연결이 필요하다.
4. 다운로드에는 기존 `PROMO_BUILDER_EXPORT_ENABLED` 설정을 확인한다. `PROMO_PUBLIC_ORIGIN`에 운영 HTTPS 주소를 지정해 상대 링크 기준을 고정한다. 공개 HTML은 기존 게시 권한·상태 검사 후 `format=html`로 제공한다.
5. 실제 Preview에서 LLM·Neon·Blob 연결, 재시도·중단 복구, Desktop/Tablet/Mobile과 새 창·다운로드·에디터 복귀를 확인한 후 Production에 배포한다. 현재 외부 연결 정보가 없어 이 검증과 운영 배포는 하지 않았다.

### 범위와 한계

- 시각 커서 12개는 모델 병렬 실행 수가 아니다. 누적 생성은 구조 1회와 최대 12개 문구 그룹 호출이며 소스만으로 완성되면 추가 문구 호출을 생략한다.
- 등록 토큰의 호환성·허용 범위를 유지한다. 요청한 값이 등록되지 않았거나 호환되지 않으면 진단에 남기며 임의 CSS를 만들지 않는다.
- 정적 HTML은 현재 지원하는 PageSchema 범용 요소를 출력한다. 프레임워크 런타임이나 임의 스크립트를 포함하지 않는다. 기존 레거시 출력 경로는 유지한다.
- 휴대 가능한 다운로드 HTML은 사용한 비공개 생성 이미지를 포함한다. 온라인 새 창 보기는 기존 토큰 보호 이미지 주소를 별도 요청한다(36절). 외부 동영상·폰트 등까지 완전 오프라인 패키징하는 ZIP 기능은 이번 구현 범위가 아니다. 단일 HTML 다운로드의 크기 제한 초과는 명시적 오류로 처리한다.
- 로컬 브라우저 검사는 테스트 응답과 준비된 미디어를 사용한다. 실제 모델의 디자인 품질이나 운영 환경의 응답 시간을 보장하는 결과로 해석하지 않는다.

검증 기록: 전체 50개 회귀검사 및 Admin·Visual editor·Nuxt 빌드 통과. [개발 반영 기록](../mouse-swarm-builder/implementation-status.md)에 활성화 조건과 실환경 미검증 범위를 정리했다.


## 16. 2026-11-21 실제 작업 단위 누적 생성 보정

### 이전 구현의 한계와 확정 변경

V1은 첫 호출에 전체 PageSchema를 생성한 뒤 일부 빈 문구만 후속 생성했다. 승인 소스만 있는 페이지는 중간 초안 없이 완료될 수 있었다. 이는 빈 캔버스부터 실제 작업 결과를 누적한다는 요구를 충족하지 못하므로 V2 작업 계약으로 변경한다. 앞선 15절의 누적 생성 완료 범위는 이 한계를 포함한 로컬 구현 기록이며 V2 검증으로 보완한다.

| 순서 | 처리 | 화면/저장 기준 |
|---|---|---|
| 1 | 가벼운 계획 생성 | 빈 루트, 1~12개 영역/그룹 셸, 부모·순서·소스 배정만 저장. 완성 트리·문구 없음 |
| 2 | 첫 작업 준비 | 다음 작업의 빈 셸만 표시하고 실제 대상에 커서 연결 |
| 3 | 해당 영역/컴포넌트 그룹 생성 | 48노드 이하 범용 트리, 기존 승인 콘텐츠를 해당 단위에서 연결 |
| 4 | 부분 검증·저장·즉시 표시 | 미완료 영역의 콘텐츠 조건만 구분하고 보안·사실·등록 토큰 검증 유지 |
| 5 | 다음 단위 반복 | 이후 콘텐츠는 아직 생성·저장되지 않음. 실패 시 완료 결과 유지 |
| 6 | 마지막 영역 응답 후 전체 조립 | 일반 최종 검증·원자 Revision/채팅 전환 후 구성 승인 허용 |

컴포넌트마다 무조건 모델을 호출하지 않는다. AI가 섹션 또는 관련 컴포넌트 그룹을 작업 단위로 정한다. 큰 섹션은 부모 셸과 종속 그룹으로 나누며 계획된 부모 순서를 지킨다. 임의 고정 섹션·완성 템플릿·미검증 토큰 스트림·숨겨둔 결과의 타이머 공개는 금지한다. DOM 반영을 기다리는 paint checkpoint는 인위적 연출 지연과 구분한다.

### 구현·호환·운영 이행

- 기존 promo_page_drafts JSON 상태에 contractVersion 2와 작업 계획을 저장한다. V1 진행 데이터는 기존 서비스로 재개하고 완료 문서는 변경하지 않는다.
- migration 096은 신규 promo_page_manifest_planner(작업 계획 V2), promo_page_region_builder(영역 구성 V2) 두 Draft를 기존 구조/문구 설정에서 복제한다. 기존 타입과 활성 버전은 유지한다. 모델·실행 설정·스킬 버전을 보존하고 활성 프롬프트를 자동 변경하지 않는다.
- 신규 계약은 modelOptions.pageDraftContractVersion=2를 확인한다. 구버전 활성 프롬프트면 분명한 설정 오류를 표시하며 이전 전체 생성 방식으로 조용히 우회하지 않는다.
- PAGE_SCHEMA_DRAFT_ENABLED 플래그는 유지한다. 코드·096·두 Draft 검증/활성화를 함께 준비한다. 기존 094/095를 반복 실행하지 않는다.
- 플래그 비활성 또는 기존 문서 전체 수정 요청은 기존 생성 경로이므로, 실제 단위 누적 생성으로 표시하지 않는다.

### 필수 검증

1. 승인된 소스만 있는 2개 이상 영역 요청: 첫 영역이 저장·표시된 시점에 두 번째 영역은 빈 작업 셸이며 최종 Revision은 아직 0이다.
2. 첫 계획 응답에는 전체 콘텐츠 트리/문구가 없고 첫 작업 셸 외의 미완성 영역이 표시되지 않는다.
3. 두 번째 실제 모델 작업을 보류한 상태에서 브라우저가 첫 영역을 읽을 수 있다. 모의 부분 응답만으로 검증하지 않고 실제 서비스+PGlite 저장 경로와 브라우저를 연결한다.
4. 단위 실패→리스 해제→재시도, 새로고침/중복 응답, 부모 순서·예약 ID·잘못된 소스·미등록 스타일·사실 조작을 검사한다.
5. 마지막 저장 영역도 완료 응답 전에 관측되며, 전체 검증 후에만 승인 CTA가 생긴다.
6. V1 초안 복구, 096 재실행, 기존 모델/스킬 보존, 계약 미활성 명시 오류, 최종 구조/사실/접근성 검증을 검사한다.

외부 LLM·운영 DB·Blob 통합 확인은 별도이며 로컬 테스트 결과로 완료를 주장하지 않는다.

V2 복구 보완: read-draft는 모델 호출·리스 획득·진행 변경 없이 소유 문서의 저장 초안만 조회한다. 실패 후 새로고침에서도 완료 영역을 복원하고, 실제 실패 대상의 커서 진행을 멈춘 상태로 재시도할 수 있다. 활성 작업 중 새로고침은 기존 start-draft 재개로 저장된 결과를 재사용한다. 배경 탭에서는 paint 대기 때문에 서버 작업 요청이 멈추지 않는다.

16절 구현 검증: 전체 55개 회귀검사, 추가 프롬프트/Admin 계약 4종, Admin·Visual editor·Nuxt 빌드 통과. 실제 서비스+PGlite+브라우저에서 소스만 있는 페이지의 부분 표시·실패 후 복원·재시도·최종 승인 시점을 검증했다. [V2 운영 적용 절차](../mouse-swarm-builder/rollout-units-v2.md)를 별도로 작성했다. 외부 연결 및 Production 배포는 미실시다.


## 17. 2026-11-22 문구 Mask Reveal·캐럿·커서 보정

17절 구현 검증: 전체 56개 회귀검사와 Visual editor 빌드 통과. 별도 브라우저에서 여러 줄/유니코드/RTL 원문과 DOM 유지, 실제 Range 캐럿, 반복 없는 커서 정지/전환, 일시정지·모션 감소·배경 탭·검사 정리, 뷰포트/재부착 재생 억제를 확인했다. 추가 마이그레이션·모델 호출·Admin 설정 변경과 운영 배포는 없다.


## 18. 2026-11-22 전체 스켈레톤 선표시·600ms·데스크톱 우선

### 확정 범위

사용자 요청에 따라 현재 V2 단위별 저장 흐름을 유지하면서 첫 계획의 전체 스켈레톤을 먼저 보여준다. 이전의 "다음 빈 셸 하나만" 규칙은 이 절로 대체한다. 17절의 360ms 문구 Reveal은 600ms로 조정한다. 박스·이미지·작업 커서·완료/실패·효과 정지의 나머지 원칙은 유지한다.

| 단계 | 처리 및 표시 |
|---|---|
| 1. 계획 | AI가 동적으로 빈 루트·영역/그룹·부모/컬럼/반응형 배치·소스 배정을 설계하고 검증·저장 |
| 2. 전체 스켈레톤 | 저장된 모든 계획 셸을 표시. 주요 레이아웃 박스/이미지용 그룹도 계획된 경우만 표시. 고정 템플릿·미리 완성한 콘텐츠 없음 |

2. 초기 안전한 반응형 기본값과 데스크톱→태블릿→모바일 자동 검사는 유지한다. 완성된 페이지에서 채팅의 모바일 구성/배치 요청을 viewportScope=mobile로 전달하고 서버는 기존 ID의 mobile layout/styles/spacing만 적용한다. 데스크톱/태블릿/트리/사실/이미지/동작은 원본을 보존한다. 현재 Revision 품질 통과·구성 승인 이후에 요청하며 변경 후 기존 재승인·자동 검사 경로를 따른다. 새 노드가 필요한 모바일 전용 콘텐츠 편집은 별도 구조 편집 범위다.
3. 요청 요약의 section.media.imageIntent/section.imageIntent/item.imageIntent를 source path에 연결한 imageRequirements로 보관한다. 첫 배정 소스를 가진 단위가 생성 책임을 지며 소스가 없으면 첫 단위로 배정한다. 항목별로 별도 이미지 노드와 소스 연결+등록 이미지/생성 요청이 필요하다. 부분 저장 전 검사로 실패 단위만 재시도하고 최종 조립/일반 생성/구성 승인에서도 검사한다. 이미지 저장 시 요청의 sourceIds를 에셋에 보존하여 완료 후 요청 목록이 비어도 소스 연결을 검사한다. 무작위 이미지나 미등록 디자인값을 삽입하지 않는다.
4. 활성 프롬프트의 필수 변수는 유지하고 constraintsJson/candidateSnapshotJson에 이미지 책임·요구를 전달한다. 기존 저장 문서에 imageRequirements가 없는 경우 과거 이미지 의도는 소급 추정하지 않으며 최신 요청 요약으로 재생성해야 연결된다. 실제 운영 문서의 이미지 누락 원인은 로그 없이 확정하지 않는다.
5. 회귀: 미리보기 헤더 제거·채팅 상태 보존, 완성 후 모바일 요청 라우팅·서버 보존/재승인·세 화면 검사, 섹션/카드 의도별 생성/등록 이미지·누락·중복 사용·단위 배정/실패 재시도를 확인한다. 신규 DB 마이그레이션은 없으며 운영 모델 호출은 별도 검증한다.

검증 기록: 전체 59개 로컬 검사 및 Visual editor 빌드 통과. 모바일 채팅 요청·서버 override 보존, 이미지 요구 누락·생성 완료 소스 연결, 상단 제거 후 채팅 재시도/품질 복구를 확인했다. 실제 외부 LLM·DB·Blob 검증 및 배포 완료는 별도다.

### 26.4 디자인 품질과 구조 다양성

- AI는 요청에 맞게 섹션 수·순서·중첩·컬럼 수/비율·정렬·텍스트/이미지 관계·정보 강조·여백/밀도·반응형을 설계한다. 색상/폰트만 바꾼 고정 구조를 다양한 디자인으로 평가하지 않는다.

- 핵심 구도는 계획/영역 구성/전체 구조 수정에서 정한다. 영역 디자인은 검증된 구조의 등록 스타일 계층을 설계하고, 이미지 제작은 실제 대상·텍스트 위치·피사체·크롭과 연결한다.

- 구조·사실·토큰·미디어·겹침/잘림은 자동 측정한다. 목적 적합성·계층·리듬·이미지 미감은 데모 전 내부 비교 검토로 보완한다. 현재 측정값만 받는 품질 모델을 픽셀/미감 전체 검증으로 과장하지 않는다. 내부 검토를 고객의 수동 승인 단계로 노출하지 않는다.
- 기존 범용 PageSchema·재귀 렌더러·grid/stack·등록 토큰을 재사용한다. 복잡한 자유 좌표·영상 자동재생·스크롤 인터랙션 등 미지원 표현을 프롬프트만으로 구현했다고 주장하지 않는다. 부족한 표현은 서버/스키마/렌더러/SSR/출력 호환을 함께 확장한다.

3. 스킬의 허용 프롬프트 타입을 저장·활성화·실행에서 확인한다. 불활성/해시 오류는 조용히 생략하지 않는다.
4. 스킬 비활성화 전에 연결된 활성 프롬프트와 영향 범위를 확인한다. 긴급 차단 권한과 일반 변경 흐름을 구분한다.

실제 PGlite 서버 저장과 브라우저를 연결하여 요청 1회 → 중간 부분 저장 → ready 전환 → 자동 3화면 QA → 출력 가능을 검증했다. 중간 승인/생성 클릭은 0회이며 사용자 승인 시간은 기록하지 않는다. 잘못된 단위의 1회 보정/재실패 시 저장 커서 유지, Admin 실제 SQL 충돌/범위/조립 검증, 브라우저 Draft 분리도 확인했다.

### 28.1 실제 문제와 범위

현재 계획 스켈레톤 선생성은 이미 존재한다. 주된 구조적 대기는 이후 영역 생성, 영역 디자인, 이미지의 순차 연결이다. 실제 운영 구간별 소요 시간은 아직 확인하지 못했으므로 원인 비중·목표 초·개선율을 확정하지 않는다. 스웜 효과 속도를 바꾸는 것으로 모델 처리 시간이 개선됐다고 보고하지 않는다.

기존 `api/_page-draft-service.js`는 초안 전체 리스 하나·단일 cursor/sequence를 사용하고 `_page-draft-units.js`의 부분 검증은 앞 영역부터 완료한 것으로 가정한다. `_page-section-design.js`는 다음 순서 group만 허용하며 앞서 완료한 디자인을 컨텍스트로 사용한다. 클라이언트가 단순 Promise.all로 기존 API를 호출하는 구현은 금지한다. 이미지 서비스의 최신 상태 확인도 모든 병렬 쓰기 충돌을 해결하는 보장은 아니므로 별도 작업 결과/병합 계약을 설계한다.

### 28.2 목표 흐름과 변하지 않는 경계

요청 요약 → AI 전체 빈 셸 계획·검증·저장 → 의존성 충족 독립 영역 최대 2개 생성 → 영역별 결과 검증·저장·실시간 표시 → 전체 구조 조립·검증·저장 → 영역 디자인과 독립 이미지/다음 디자인 작업 겹침 → 전체 미디어 준비 → 자동 3화면 QA·제한적 보정·재검사 → 완성.

- 전체 계획에는 섹션 순서·중첩·배치·소스 소유권·요청 기반 공통 디자인 방향이 있다. 특정 히어로/카드/색상 패턴을 고정하지 않는다.
- 먼저 완료된 영역은 원래 위치에 표시한다. 완료 순서가 DOM 순서를 결정하지 않는다. 상위 셸·종속 그룹은 계획의 의존성을 지킨다.
- 전체 와이어프레임 검증 전 디자인/미디어 호출은 하지 않는다. 영역 병렬 구성과 구성/디자인 단계 겹침은 다른 변경이며 후자는 이번 범위에서 제외한다.
- 이미지용 카피/구도/등록 스타일 컨텍스트가 준비된 뒤 이미지 작업을 시작한다. 다른 영역의 디자인과 겹칠 수 있지만 같은 노드·공유 자원에 의존하면 대기한다.
- 사용자 입력 1회·중간 승인 0회, 동일 PageSchema·등록 토큰·사실·보안·접근성, 완료 에셋 보존, 현재 Revision의 최종 3화면 QA/출력 권한은 유지한다.

### 28.4 서버 작업·저장 계약

- 실행 공통: owner/document/run, 요구사항 revision/fingerprint, 계획·구조 fingerprint, 토큰/정책·프롬프트/스킬/모델 버전, 공통 브리프 hash, 취소/대체 상태를 식별한다.
- 영역 작업: unit ID, 의존성, pending/running/completed/failed/cancelled, attempt/lease/claim, 입력 해시, 결과·검증·반영 상태와 시간 기록을 관리한다. 실제 DB 스키마/API 버전은 구현 설계에서 확정하며 migration 097/098을 이 용도로 변경하거나 재사용하지 않는다.
- 동시 생성은 최대 2개로 시작하고 이미지·디자인까지 포함한 실행/공급자 총 동시 한도와 429 대응을 둔다. 브라우저 탭 수가 한도를 늘리지 않으며 중복 호출·무제한 재시도를 막는다.
- 부분 검증은 cursor+1이 아니라 완료 영역 집합과 현재 계획을 기준으로 한다. 작업 범위·소스·셸 보존과 전역 ID 충돌·전체 예산·h1/필수 소스의 부분/최종 경계를 검사한다.
- 모델 응답은 결과 레코드로 보존하고 짧은 원자 연산으로 최신 문서에 병합한다. 정상적인 형제 작업 완료와 요구/구조 변경을 구분한다. CAS 충돌만으로 유효한 모델 결과를 다시 유료 생성하지 않는다. 오래된 작업은 자동으로 새 구조에 끼워 넣지 않는다.
- 완료 결과는 현재 서버 스냅샷으로 표시하며 저장 전 렌더링하지 않는다. 결과 도착 순서·폴링 중복·이전 실행 응답이 DOM 순서·완료 데이터·품질 이력을 덮지 못하도록 한다.
- 실패한 단위만 제한적으로 재시도한다. 중간 취소·리스 만료·두 탭·재접속·서버 중단·병합 후 응답 유실에서도 중복 호출/반영이 없다. 순차 복귀 시 완료 결과를 보존하며 구버전 초안은 원래 계약으로 복구한다.

### 28.5 공통 디자인과 프롬프트/스킬 경계

공통 브리프와 페이지별 계층·간격·이미지 방향을 먼저 전달해야 디자인 병렬화가 서로 다른 톤을 만들지 않는다. 기존 ‘앞 영역 완료 결과’에 의존하는 디자인 스킬/입력은 공유 방향+각 영역의 소유 범위 기준으로 검토한다. 이번 단계에서 디자인 전체 병렬 실행까지 일괄 도입하지 않는다.

작업 스케줄·동시성·저장/재시도는 코드가 소유하고 LLM이 작업 완료/진행률·커서 수를 선언하지 않는다. 스킬은 영역 내 판단과 공통 방향 준수, 프롬프트는 해당 단위의 역할·입출력·보존 범위를 소유한다. 모델/필수 변수/응답 스키마 변경은 별도 Draft와 회귀 검증을 거치며 코드에 빠른 모델을 하드코딩하지 않는다.

## 29. Admin 작업 로그 — 2026-11-23 개발 반영

### 29.1 목적과 범위

고객 화면은 간결하게 유지하면서 관리자에게 중간 오류·실패·재시도·모델 호출과 소요 시간을 제공한다. 기존 promo_builder_events의 일부 이벤트와 브라우저 `.catch(()=>null)`만으로 전체 작업 진단을 대신하지 않는다. 독립된 서버 로그 테이블과 AsyncLocalStorage 요청 문맥으로 생성 여정을 연결한다. 이 변경은 28절의 병렬 생성 구현이 아니며 P0의 요청/모델/일부 초안 시간 기록을 보강한다. 큐 대기/모든 SQL 실행 시간·비용 추정까지 완성한 것은 아니다.

### 29.2 반영한 구성

- `099_admin_work_logs.sql`: promo_work_logs 추가, 작업/요청/문서/세션·단계/API·이벤트·상태·시간·HTTP·오류·안전한 메타데이터, 최신/작업/문서/실패 인덱스. 기존 DB/프롬프트/모델/활성 설정을 변경하거나 과거 기록을 이관하지 않는다.
- `_work-log.js`: 서버 요청 시작/종료, 모델 시작/종료, 진행 체크포인트, 비동기 구성 작업 추적. 로그 실패 시 안전한 콘솔 대체 기록을 남기며 원래 비즈니스 응답/오류는 보존한다.
- 대상: 요청 요약, 부분 초안/전체 PageSchema, 영역 디자인, 미디어, QA, 채팅/요구/문서/와이어프레임, 편집/출력/다운로드, 기존 composition 및 v3 요청/feedback/review/cancel/regenerate/publication, 첨부 소스/분석 관련 component API. 공급자 공통 호출 기록은 이 요청 문맥에서만 작동한다. 운영 플랫폼의 모든 HTTP/SQL/외부 서비스 내부 로그까지 복제하지 않는다.
- 클라이언트: 고객 요청마다 작업 ID 시작, 문서/세션과 연결·탭 세션 복원, API 헤더 전파. 실패는 서버 로그와 별개인 client_error로 보고한다. 오프라인/강제 종료로 전송할 수 없는 보고를 수집 완료로 주장하지 않는다.

### 31.3 운영 준비 순서

1. 기존 migration 099 적용 여부 확인 후 **100 → 101** 순서로 테스트 DB에 적용한다. 운영 DB 적용은 이번 개발에서 수행하지 않았다.
2. Preview에서 `PAGE_PARALLEL_WORK_ENABLED=true`로 P1/P2 경로를 검증한다. 기본값 false이며 기존 누적 초안·영역 디자인의 환경변수와 활성 V2 프롬프트도 필요하다. 영역 프롬프트는 constraintsJson의 unitNodeIdPrefix와 maxRegionNodes를 준수해야 한다. 필수 변수 이름은 유지한다.
3. `PAGE_OVERVIEW_REUSE_ENABLED=true`로 동일 작업의 요약 중복 요청을 검증한다. 기본값 false. 새 요청은 새 작업 ID를 사용한다.
4. 관리자 비교는 **비 Production 환경**에서 `PROMO_ADMIN_BENCHMARKS_ENABLED=true` 설정 후 사용한다. 활성 기준과 같은 타입의 검증된 후보를 고른다. 프롬프트·모델·reasoning·스킬은 기존 등록 계약을 사용한다. Production에서는 저장 결과 조회만 가능하다.
5. 관리자 비교는 요약·계획·영역·PageSchema·영역 디자인·품질검토·이미지 타입을 지원한다. 페이지 단계는 실제 활성 토큰 context와 필요한 page/state/group을 입력한다. JSON 구조 결과 또는 인증된 이미지와 사용량을 비교한다. 자동 고객 문서 저장·모델 활성화·시각 미감 판정을 수행하지 않는다.
6. 실제 대표 요청의 디자인 다양성·사실·이미지·실패/비용/시간을 비교한 뒤 점진 활성화한다. 기능 플래그와 활성화 검증을 건너뛰어 즉시 운영 병렬 처리하지 않는다.

## 38. 프롬프트 저장의 수정 시각 정밀도 거짓 충돌 — 2026-11-24

### 재현과 원인

사용자가 `Prompt draft status changed before the update completed` 저장 실패를 보고했다. 기존 API는 Draft를 읽은 다음 `updated_at = current.updated_at`으로 저장 중 변경을 비교한다. PostgreSQL의 timestamptz는 마이크로초를 보존하지만 기본 JavaScript Date는 밀리초까지만 보존해, 상태/본문이 그대로인 행도 UPDATE 조건이 맞지 않을 수 있다. 명시적인 `2026-11-24 00:00:00.123456+00` 값을 실제 PostgreSQL 호환 저장소에 넣어 같은409·PROMPT_DRAFT_REQUIRED를 재현했다(`/tmp/prompt-timestamp-before.log`). 수정 전 재현 검사는 실패했다. 저장된 운영 행은 네트워크 제한으로 직접 조회하지 못했으며, 개별 보고 건의 실제 시각/동시 변경 여부와 코드 결함 재현을 구분한다.

### 수정

prompt-template, prompt-template-validate, prompt-template-activate의 최초 조회에 `updated_at::text AS edit_updated_at`을 포함하고, DB가 반환한 정확한 텍스트를 timestamptz로 비교한다. 비교 조건을 제거하거나 date_trunc로 정밀도를 낮추지 않는다. 활성화 시 기존 활성 행 비활성화의 후보 존재 검사에도 같은 값을 사용한다. 공개 editToken 형식과 Admin 입력 폼·모델·스킬·정책·프롬프트 본문은 변경하지 않는다. 변경이 없으면 정상 저장/검증/활성화되고, 실제 변경이 있으면409와 PROMPT_EDIT_CONFLICT로 안내한다. 초기에 Draft가 아닌 경우의 기존 상태 게이트는 유지한다.

동일 시각 검사를 쓰던 세 경로를 함께 보정하며 새 migration·환경변수·프런트엔드 빌드는 필요하지 않다. 본문 SQL 재실행이나 timestamp 수동 반올림을 해결책으로 요구하지 않는다. 운영 반영 후 현재 Draft를 다시 불러와 기존 저장/검증/활성화 절차를 사용할 수 있다.

### 검증

실제 SQL 기반 GET→저장, 검증, 활성화의6자리 소수 시각 성공과 세 경로의 정확히1마이크로초 동시 변경 거부를 확인했다. 실패 시 본문/상태·기존 활성 버전·감사 이력이 잘못 변경되지 않는지, 오래된 편집 토큰·모델/스킬/조립 검증 및 기존097/098 검사를 함께 확인했다(`/tmp/prompt-timestamp-qa.log`). 변수 거버넌스·Admin 인증 경계·Snapshot 저장 계약과 서버 구문 검사도 통과했다.

별도 레거시 `test-prompt-lifecycle-admin-contract.js`는 prototype/app.js에서 과거 자동 생성/활성화 안내 문자열을 찾는 기존 기대값 불일치로 실패했다. 해당 UI/검사 파일은 이번 수정에서 변경하지 않았으며 현재 수명주기의 실제 SQL 회귀와 구분한다. 이 실패를 통과로 처리하거나 테스트를 완화하지 않았다. 전체83개 회귀 결과는 후속 기록한다. 실제 운영 DB·Admin 연동 검증과 Production 배포는 미실행이다.

| 동일 밀리초 이벤트 순서 역전 | DB는 created_at이 같으면 임의 UUID 순으로 읽는다. 시작→완료를 같은 시각으로 저장하고 UUID를 역순으로 지정하자 완료가 먼저 처리되고 재검사 시작이 나중에 처리되어 품질 상태가 다시 진행 중이 됐다(`/tmp/chat-progress-debug-order-before.log`). | 새 이벤트 metadata.customerSequence에 같은 고객 요청의 단조 증가 발생 순서를 저장한다. 같은 요청·같은 밀리초의 status 행만 이 순서로 해석하며 다른 메시지의 위치·원본 이력을 변경하지 않는다. 서버의 평탄화/캐시의 중첩 메타데이터와 긴 대화 재개 시 카운터도 지원한다. |

발생 순서가 저장되지 않은 과거 이벤트는 기존 시각/순서를 유지한다. 과거의 모호한 동일 시각 이벤트 순서를 소급 복구했다고 주장하지 않는다. customerSequence는 표시 복원용이며 공급자 작업의 실행 순서·완료 권한·DB Revision이나 출력 게이트를 대체하지 않는다.
