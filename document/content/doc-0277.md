# Promo AI Builder 제품 방향 및 구현 검토

- 대상 프로젝트: `promo_web_builder`
- 최초 작성: 프로젝트 초기(A/B/C 섹션·Temp.4·n8n 단계)
- 현행화: 2026-07-23 (마이그레이션 `030`, Create Promo/Visual Editor/Web Output, i18n·컴포넌트·디자인 토큰 반영 기준)

> 이 문서는 제품 방향과 구현 격차를 추적한다. 초기 버전은 "AI 디자인 이미지 생성 실험" 단계를 기준으로 작성됐으나, 이후 DB 기반 템플릿·섹션·아이템 관리, Visual Editor/Web Output, i18n, 컴포넌트·디자인 토큰 체계가 구현되어 현행화했다. **제품의 최종 방향(운영자용 AI 디자인·퍼블리싱 빌더)은 유지**되며, 아래는 그 방향 대비 현재 위치와 남은 격차다.

## 1. 서비스 개발 배경 (유지)

기존 프로모션 페이지 빌더는 AI 기반이 아니다. 몇 개 고정 템플릿을 제공하고 리전 담당자가 텍스트·콘텐츠를 수정해 운영하는 방식이라, 신규 디자인(템플릿) 추가 요구를 수동으로 따라가야 해 확장성이 낮다. 목표는 AI로 디자인 생성을 자동화하고 최종 퍼블리싱까지 연결하는 프로모션 빌더다.

## 2. 만들고자 하는 방향 (유지)

단순 페이지 생성기가 아니라, 기존 운영형 프로모션 빌더에 AI 디자인/퍼블리싱 레이어를 얹는 구조다.

```text
프로모션 운영 요구
  -> 리전 담당자 입력
  -> 디자인 시스템(디자인 MD/토큰) 기반 디자인 생성
  -> 생성 디자인 확인 및 수정(Visual Editor)
  -> 코드/렌더 산출(Web Output)
  -> 정책 검증
  -> 자동 퍼블리싱
```

## 3. 현재 구현된 범위 (현행화)

초기 문서의 "A/B/C 섹션 + Temp.4 고정 + n8n static + localStorage" 단계에서 크게 진전했다. 현재는 **DB(Neon Postgres) 기반의 운영형 구조**로 전환되었고, 제작 화면이 분리되어 있다.

### 3.1 화면 구성

| 화면 | 파일 | 역할 |
|---|---|---|
| Promo Builder + 관리자 | `prototype/index.html` | A. 디자인 MD 관리 / B. 프로모션 빌더 / C. 생성 결과 + 관리자 탭(webhook·LLM/프롬프트·템플릿/레이아웃) |
| Create Promo | `prototype/create-promo.html` | 프로모션 생성 위저드(Step 1~4, 콘텐츠 입력·AI 생성·적용) |
| Promo Wizard | `prototype/promo-wizard.html` | 위저드형 입력 흐름 |
| Visual Editor | `prototype/visual-editor.html` | 생성 디자인 편집/미리보기(Vue 렌더러) |
| Web Output | `prototype/visual-output.html` | 최종 프로모션 출력 |
| Generated | `prototype/generated.html` | 생성 결과 페이지 |

### 3.2 DB 기반 구조 (마이그레이션 002~030)

초기 문서가 "검토 후보"로 제시했던 테이블 상당수가 실제로 구현되었다.

- 디자인 MD 데이터화·정규화·스타일 분류·raw token (006, 007, 003, 009)
- 프롬프트 템플릿 + 거버넌스(draft/active/version) (010), 모델·워커 설정 (011~015)
- **Wizard 콘텐츠 섹션·아이템** (016), **폼 템플릿·연결·레이아웃** (017, 018, 023), 이미지 소스/설명 (019, 020)
- **섹션 감사 로그(트리거 기반)** (022), 레이아웃 사용 이벤트 (024)
- **섹션 AI 디자인 실행·스냅샷** (025, 030), **섹션 AI 디자인 정책** (026)
- **다국어(i18n) 메시지 관리** (027)
- **섹션 컴포넌트 레지스트리** (028), **아이템 컴포넌트 + 디자인 토큰 + planner** (029)

관련 서버리스 API 42개 이상(`wizard-*`, `promo-section-design-*`, `prompt-template*`, `generate-*`)이 이 구조를 지원한다.

### 3.3 생성·편집 흐름

- 디자인 MD 선택 → 프로모션 입력 → LO-FI 초안 → UI 디자인 이미지 생성(OpenAI/Gemini 계열) → 결과 확인까지 동작.
- 섹션별 AI 디자인(레이아웃 variant + 이미지) 생성·적용, Background/Item 이미지 적용.
- Visual Editor에서 생성 결과 편집·미리보기, Web Output으로 출력.
- 생성 시점 스냅샷 저장(`promo_section_design_runs`)으로 이력 관리.

## 4. 격차 재평가 (완료 vs 남은 항목)

초기 문서의 "보완 필요" 7개 항목을 현재 기준으로 재평가한다.

| # | 초기 지적 | 현재 상태 |
|---|---|---|
| 1 | 기존 운영 빌더 연결 / 템플릿·필드 DB 분리 | **대부분 완료** — 폼 템플릿·섹션·아이템이 DB로 분리(016~018), Temp.4 고정 탈피 |
| 2 | 디자인 MD와 템플릿 관계 강화(지시서화) | **진행 중** — MD 데이터화·디자인 토큰·planner(029) 도입. 생성 결과 검증 조건화는 계속 강화 필요 |
| 3 | 생성 결과 수정 흐름 | **부분 완료** — Visual Editor 편집/미리보기 존재. 수정 요청→재생성→버전 비교→승인의 통합 UX는 미완 |
| 4 | 이미지 생성과 코드 생성 분리 | **부분 완료** — 이미지 생성과 Vue 렌더러/Web Output이 분리. 독립 "코드 생성" 파이프라인 성숙화 필요 |
| 5 | 운영 정책 Rule Base 검증 | **미완(핵심 격차)** — 약관 입력란은 있으나 리전별 필수 약관·RG·연령 고지 등 Rule Base 검증은 아직 약함 |
| 6 | DB 저장 구조 | **완료** — `promo_section_design_runs` 등 DB 저장. localStorage 의존 탈피 |
| 7 | Advanced Mode / 섹션 잠금 | **부분 완료** — 섹션·아이템 잠금(`is_locked`)·AI 디자인 정책(026) 존재. Advanced UX는 계속 보완 |

## 5. 현 진행 방향 (2026-07, 신규)

초기 문서 작성 이후, 운영화·일관성을 위한 아래 방향이 현재 진행 축이다. 관련 계획서는 `docs/proposal/`에 있다.

- **CSS 디자인 토큰 아키텍처** — `design-tokens.css`의 `--app-*` 단일 출처, 앱 UI(Layer A)와 프로모션 콘텐츠(Layer B) 분리, 하드코딩 제거.
- **디자인 토큰 관리(CSV/스키마)** — 관리자에서 값만 채워 적용하는 토큰 입력 포맷(`design-tokens.csv/.schema.json`), 다중 레이어·transition(W3C) 포함.
- **관리자 용어 정리 + i18n(다국어)** — 용어 사전 + `locale_messages`(027) 기반 관리자 문구 다국어화.
- **섹션 아이템 컴포넌트화 + 템플릿 조립** — 섹션 아이템(Text/Image/CTA)을 전역 컴포넌트로 관리, 템플릿은 컴포넌트를 참조·조립(028, 029).
- **브랜드 적용(GGPoker)** — StyleGuide/사이트 분석 기반 브랜드 토큰(레드/골드/블랙)·톤앤매너·이미지 생성 프롬프트를 프로모션 빌더에 반영.
- **소스 정리·통합** — 책임 분리, 중복 제거, 계약·회귀 테스트 보강.

## 6. 남은 우선순위 (현행화)

구현이 진전됨에 따라, 초기 문서의 우선순위(제품 문서화·C섹션 확장·workflow 분리·DB·Rule Base) 중 남은 핵심은 다음이다.

1. **운영 정책 Rule Base 검증** — 가장 큰 미완 격차. 리전별 필수 약관·RG·연령 고지·금지 표현 등을 AI prompt가 아닌 Rule Base로 통제. (관련 후보 테이블: `promo_region_rules`, `promo_compliance_checks`)
2. **검수 → 승인 → 코드 생성 → 퍼블리싱 파이프라인 완성** — Visual Editor 편집과 Web Output을 승인·퍼블리싱 자동화까지 연결.
3. **MD·디자인 토큰의 생성 검증 조건화** — `layoutPhilosophy`, `componentStyle`, `dos/donts`를 생성 결과 검증 규칙으로 활용.
4. **진행 중 구조의 안정화** — 섹션 컴포넌트/디자인 토큰(028, 029) 배포·이관, i18n 전면 라벨 전환.

## 7. 결론 (현행화)

초기 문서 시점의 "디자인 MD + 입력값 → UI 디자인 이미지 생성" 실험 단계는 이미 통과했다. 현재는 **DB 기반 운영형 구조 + 제작 화면 분리(Create Promo/Visual Editor/Web Output) + 섹션 AI 디자인 + i18n·컴포넌트·디자인 토큰 체계**까지 진전한 상태다.

따라서 다음 개발의 무게중심은 초기 문서가 강조한 "C섹션 결과 확인 확장"에서 한 단계 나아가, **① 운영 정책 Rule Base 검증**과 **② 검수→승인→퍼블리싱 자동화 완성**, 그리고 **③ 현재 진행 중인 디자인 토큰/컴포넌트/i18n/브랜드 체계의 안정화·이관**이다. 최종 목표인 "운영자가 쓰는 AI 기반 프로모션 디자인/퍼블리싱 빌더"는 유지된다.
