# 관리자 LLM·프롬프트 버전 그룹화 개발계획서

## 0. 문서 정보

- 최초 작성일: 2026-07-27
- 대상 프로젝트: `promo_web_builder`
- 대상 화면: `설정 > LLM 및 프롬프트 관리`
- 문서 상태: 개발 반영 완료
- 선행 구조:
  - `db/migrations/010_prompt_templates.sql`
  - `db/migrations/033_prompt_template_version_lifecycle.sql`
  - `docs/계획/admin-llm-prompt-control-plane-development-plan-2026-07-25.md`

### 0.1 목적

현재 관리자 화면은 한 프롬프트 기능의 활성·초안·검증 완료·비활성·보관 버전을 모두 같은 깊이의 목록으로 출력한다. 버전이 누적될수록 실제 운영에 사용 중인 활성 버전과 작업 중인 초안을 찾기 어려워진다.

이번 개발의 목적은 동일한 프롬프트 계보를 하나의 그룹으로 묶고 다음 정보를 우선 제공하는 것이다.

- 현재 운영 중인 활성 버전
- 작업 중인 초안 또는 검증 완료 버전 존재 여부
- 과거 비활성·보관 버전 이력
- 선택한 버전의 상세 편집·검증·활성화·롤백 기능

기본 목록에서는 프롬프트 기능별 대표 항목만 보여주고, 사용자가 그룹을 펼쳤을 때에만 전체 버전을 확인할 수 있게 한다.

### 0.2 핵심 결정

1. 그룹 식별자는 이름이나 유형이 아니라 `lineageId`를 사용한다.
2. 그룹 대표는 가장 높은 버전이 아니라 현재 `active` 버전이다.
3. 활성 버전보다 높은 초안이 있어도 초안을 운영 버전처럼 표시하지 않는다.
4. 초안·검증 완료 버전은 대표 항목의 보조 배지로 표시한다.
5. 모든 기존 생명주기 작업은 유지한다.
6. 1차 구현에는 신규 DB 마이그레이션을 추가하지 않는다.

## 2. As-is 분석

### 2.1 현재 목록 UI

`prototype/index.html`의 프롬프트 목록은 다음 구조로 전체 행을 직접 반복한다.

```text
filteredPromptTemplates
  ├─ v15 draft
  ├─ v14 active
  ├─ v13 inactive
  ├─ v12 archived
  └─ 다음 프롬프트 기능...
```

각 버전이 같은 깊이에 있어 다음 문제가 발생한다.

- 동일 기능이 여러 프롬프트처럼 보인다.
- 활성 버전과 과거 버전의 시각적 우선순위가 같다.
- 버전 수가 늘어날수록 목록이 길어진다.
- 초안이 있는지 확인하려면 전체 목록을 탐색해야 한다.
- 보관 버전까지 기본 조회해 탐색 부담이 커진다.

### 2.2 현재 프런트엔드 상태

`prototype/app.js`는 `promptTemplates` 배열을 그대로 보관하며 `filteredPromptTemplates`에서 유형만 필터링한다.

```text
promptTemplates
  └─ filteredPromptTemplates
       └─ type 일치 여부만 검사
```

선택 상태는 `selectedPromptTemplateId` 하나로 관리하고 있으며, 그룹 펼침 상태는 존재하지 않는다.

### 2.3 현재 API

관리자 화면은 다음 API를 사용한다.

```text
GET /api/prompt-templates?includeArchived=true
```

응답에는 이미 그룹화에 필요한 정보가 포함된다.

- `id`
- `type`
- `name`
- `status`
- `version`
- `lineageId`
- `sourcePromptTemplateId`
- `provider`
- `model`
- `updatedAt`

따라서 1차 구현은 API 또는 DB 변경 없이 프런트엔드에서 그룹화할 수 있다.

### 2.4 기존 DB 계약

`033_prompt_template_version_lifecycle.sql`에서 다음 계약이 이미 적용되어 있다.

- 동일 계보 공유 식별자: `lineage_id`
- 계보 내 버전 유일성: `(lineage_id, version)`
- 계보별 후보 버전 제한: `draft` 또는 `validated` 한 개
- 유형별 활성 프롬프트 제한: `active` 한 개
- 버전 출처: `source_prompt_template_id`

프롬프트 이름은 버전마다 변경될 수 있으므로 그룹 키로 사용할 수 없다. 프롬프트 유형 역시 향후 한 유형에 여러 계보가 존재할 수 있으므로 그룹 키로 적합하지 않다.

## 3. To-be 정보 구조

### 3.1 목표 구조

```text
프롬프트 그룹
  ├─ 대표 정보: 현재 활성 버전
  ├─ 작업 상태: 초안/검증 완료 배지
  └─ 아코디언 버전 이력
       ├─ 최신 초안 또는 검증 완료
       ├─ 현재 활성
       ├─ 이전 비활성
       └─ 보관 버전
```

화면 예:

```text
▼ 섹션 배경 이미지
  활성 v14 · Gemini · gemini-3.1-flash-image
  초안 v15 있음 · 최종 수정 2026-07-27

  ├─ v15  초안
  ├─ v14  활성
  ├─ v13  비활성
  └─ v12  보관됨
```

### 3.2 그룹 식별 규칙

기본 그룹 키:

```text
prompt.lineageId
```

레거시 또는 비정상 데이터에 `lineageId`가 없을 경우에만 다음 대체 키를 사용한다.

```text
legacy:{type}:{id}
```

이름을 대체 키에 포함하지 않는다. 이름 변경으로 그룹이 분리되는 것을 방지한다.

### 3.3 대표 버전 선정 규칙

우선순위:

1. `active`
2. `validated`
3. `draft`
4. 최신 `inactive`
5. 최신 `archived`

단, UI 용어는 상태에 따라 구분한다.

| 상황 | 대표 표시 |
|---|---|
| 활성 버전 존재 | `활성 vN` |
| 활성 없음, 검증 완료 존재 | `활성 버전 없음 · 검증 완료 vN` |
| 활성 없음, 초안 존재 | `활성 버전 없음 · 초안 vN` |
| 비활성만 존재 | `활성 버전 없음 · 비활성` |
| 보관만 존재 | `보관된 프롬프트` |

최신 버전 번호만으로 대표를 선정하지 않는다.

예:

```text
v15 draft
v14 active
```

대표는 `v14 active`이며 그룹 배지에 `v15 초안 있음`을 표시한다.

### 3.4 그룹 이름

그룹 대표 이름은 다음 순서로 결정한다.

1. 활성 버전 이름
2. 검증 완료 버전 이름
3. 초안 이름
4. 최신 버전 이름
5. `promptTypeLabel(type)`

버전별 이름이 다르면 아코디언의 각 버전 행에는 해당 버전의 실제 이름을 표시한다.

### 3.5 버전 정렬

그룹 내부 기본 정렬:

```text
version desc
```

동일 버전이 비정상적으로 중복된 경우:

```text
updatedAt desc
```

보관 버전은 데이터에서 제거하지 않고 기본 접힘 또는 `보관 버전 보기` 옵션으로 표시한다.

## 4. UI·UX 설계

### 4.1 왼쪽 목록 구조

기존 `.prompt-list-item` 단일 버튼 구조를 다음 구조로 변경한다.

```text
.prompt-group
  ├─ .prompt-group-header
  │    ├─ 펼침 버튼
  │    ├─ 대표 프롬프트 정보
  │    └─ 상태 배지
  └─ .prompt-version-list
       └─ .prompt-version-item[]
```

펼침 동작과 버전 선택 동작을 분리한다.

- 펼침 버튼: 아코디언 열기·닫기
- 대표 정보 클릭: 대표 버전 선택
- 버전 행 클릭: 해당 버전 선택

하나의 버튼 안에 다른 버튼을 중첩하지 않는다.

### 4.2 대표 항목 표시 정보

필수 표시:

- 프롬프트 이름
- 프롬프트 유형
- 활성 버전 번호
- 활성 상태
- Provider
- Model
- 최종 수정일

조건부 배지:

- `초안 vN`
- `검증 완료 vN`
- `활성 버전 없음`
- `보관됨`
- `Control Plane 미완성`

### 4.3 버전 행 표시 정보

- 버전 번호
- 상태
- 버전별 이름
- Provider와 Model
- 수정일
- 선택 상태

상세 Prompt 본문과 전체 모델 옵션은 오른쪽 편집기에서만 표시한다.

### 4.4 기본 펼침 정책

1. 현재 선택된 프롬프트가 속한 그룹은 펼친다.
2. 최초 진입 시 자동 선택된 활성 프롬프트 그룹을 펼친다.
3. 유형 필터 변경 후 선택 항목이 필터 범위에 있으면 펼침을 유지한다.
4. 선택 항목이 필터 범위 밖이면 첫 활성 그룹을 선택하고 펼친다.
5. 사용자가 직접 접은 상태는 데이터 갱신 전까지 유지한다.

### 4.5 보관 버전

초기 화면에서는 보관 버전을 접는다.

그룹 안에 보관 버전이 있을 때:

```text
보관 버전 3개 보기
```

버튼을 제공한다. `includeArchived=true` 호출은 1차 구현에서 유지하며 UI 표시만 제어한다.

### 4.6 접근성

- 그룹 펼침 버튼에 `aria-expanded` 적용
- 버전 목록에 `aria-controls`로 연결
- 선택된 버전 행에 `aria-current="true"` 또는 동등한 상태 제공
- Enter와 Space로 펼침·선택 가능
- 상태를 색상만으로 구분하지 않고 텍스트 배지 병행
- 포커스 표시 유지
- 아코디언이 닫히면 내부 버전 버튼을 키보드 탐색에서 제외

## 5. 프런트엔드 상태 및 계산 모델

### 5.1 신규 상태

`prototype/app.js`에 다음 UI 상태를 추가한다.

```js
expandedPromptLineageIds: []
promptArchivedVisibilityByLineage: {}
```

Vue 반응성을 고려해 배열 또는 일반 객체로 관리한다. 직접 `Set`을 사용할 경우 Vue 상태 갱신 방식과 직렬화 여부를 검증한다.

### 5.2 그룹 계산 모델

신규 computed:

```text
promptTemplateGroups
filteredPromptTemplateGroups
selectedPromptTemplateGroup
```

그룹 반환 형태:

```js
{
  lineageId,
  type,
  name,
  versions,
  visibleVersions,
  active,
  draft,
  validated,
  latestInactive,
  latestArchived,
  primary,
  archivedCount,
  hasCandidate,
  updatedAt
}
```

### 5.3 순수 함수 분리

그룹 계산은 UI 메서드에 직접 작성하지 않고 테스트 가능한 순수 함수로 분리한다.

권장 파일:

```text
prototype/admin/prompt-template-groups.js
```

브라우저에서는 `globalThis.PromoPromptTemplateGroups`로 노출하거나 현재 Admin 번들 구조에 맞춰 모듈로 포함한다.

권장 함수:

```text
groupPromptTemplates(prompts)
selectPromptGroupPrimary(group)
filterPromptGroups(groups, type)
resolvePromptSelection(groups, selectedPromptTemplateId)
```

### 5.4 선택 상태 복구

데이터를 새로 불러온 뒤 처리 순서:

1. 기존 `selectedPromptTemplateId`가 여전히 존재하면 유지
2. 없으면 기존 선택 계보의 새 `active` 선택
3. 계보도 없으면 `image_execution active` 우선 규칙 유지
4. 그 다음 전체 첫 `active`
5. 활성 버전이 없으면 첫 그룹의 `primary`
6. 선택된 그룹 자동 펼침
7. 선택된 버전 상세 조회

## 6. 생명주기 작업 연동

### 6.1 새 초안 만들기

완료 후:

- 목록 새로고침
- 생성된 초안 선택
- 해당 계보 펼침
- `초안 vN` 배지 표시
- 오른쪽 편집기 편집 가능 상태

### 6.2 초안 검증

완료 후:

- 동일 버전 상태를 `validated`로 갱신
- 그룹 배지를 `검증 완료 vN`으로 변경
- 선택과 펼침 상태 유지
- 오른쪽 편집기는 읽기 전용 상태로 전환

### 6.3 활성화

완료 후:

- 새 활성 버전을 그룹 대표로 변경
- 이전 활성 버전을 아코디언의 `inactive`로 표시
- 새 활성 버전 자동 선택
- 해당 그룹 펼침 유지
- 같은 유형의 다른 계보가 비활성화되는 경우 전체 그룹 재계산

### 6.4 롤백

현재 API는 과거 버전을 직접 active로 바꾸는 대신 롤백 결과 버전을 생성할 수 있으므로 API 응답의 `prompt.id`와 `prompt.version`을 권위값으로 사용한다.

완료 후:

- 새로 생성되거나 활성화된 결과 버전 선택
- 원본 과거 버전과 결과 버전을 구분해 표시
- 그룹 펼침 유지

### 6.5 보관

- 활성 버전 보관 금지 규칙 유지
- 보관 후 같은 그룹에 다른 버전이 있으면 그룹 유지
- 마지막 버전만 남아 모두 보관 상태이면 `보관된 프롬프트` 그룹으로 유지
- `보관 버전 숨김` 조건에서 그룹 전체를 숨길지는 유형 필터와 별개 옵션으로 처리

## 7. API 전략

### 7.1 1차 구현

기존 API를 그대로 사용한다.

```text
GET /api/prompt-templates?includeArchived=true
```

이유:

- 필요한 `lineageId`와 상태 정보가 이미 제공됨
- 현재 프롬프트 개수가 적어 클라이언트 그룹화 비용이 낮음
- API 변경으로 기존 관리자 기능에 회귀를 만들 필요가 없음
- DB 마이그레이션 없이 적용 가능

### 7.2 후속 최적화 조건

다음 중 하나가 발생하면 목록 요약 API를 검토한다.

- 전체 버전 200개 이상
- 목록 응답이 1MB 이상
- 프롬프트 본문 때문에 초기 관리자 진입이 지연됨
- 여러 관리자가 동시에 많은 버전을 운영

후속 API 예:

```text
GET /api/prompt-template-groups
GET /api/prompt-template?id={versionId}
```

목록 API는 본문과 대형 `modelOptions`를 제외하고 상세 API에서만 로드한다.

이번 개발에서는 API를 먼저 변경하지 않는다.

## 12. 위험요소 및 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 이름으로 그룹화 | 버전 이름 변경 시 계보 분리 | `lineageId`만 사용 |
| 가장 높은 버전을 대표로 사용 | 초안이 운영 버전처럼 보임 | `active` 우선 규칙 |
| 초안을 숨김 | 진행 중 작업을 찾지 못함 | 대표 배지와 자동 펼침 |
| 유형만으로 그룹화 | 다른 계보가 합쳐짐 | 유형은 필터에만 사용 |
| 활성 없는 그룹 누락 | 복구 대상 프롬프트를 찾지 못함 | 경고 대표 유지 |
| 활성화 후 선택 초기화 | 관리자가 결과를 오인 | 응답 ID 기반 선택 복구 |
| 버튼 중첩 | 접근성 및 클릭 충돌 | 펼침과 선택 컨트롤 분리 |
| 전체 본문 목록 조회 | 버전 증가 시 초기 로딩 저하 | 임계치 이후 요약 API 전환 |
| 번들만 수정 | 다음 빌드에서 변경 유실 | 원본 수정 후 `build:admin` |

## 13. 최종 완료 정의

다음 조건을 모두 만족하면 개발 완료로 판단한다.

- 동일 프롬프트 계보가 목록에서 한 개 대표 항목으로 표시된다.
- 현재 활성 버전이 항상 대표로 표시된다.
- 초안 또는 검증 완료 버전 존재 여부를 대표 항목에서 확인할 수 있다.
- 아코디언을 열면 모든 과거 버전을 확인하고 선택할 수 있다.
- 기존 편집·저장·검증·활성화·롤백·보관 기능이 유지된다.
- 활성화 직후 대표 버전과 선택 상태가 즉시 갱신된다.
- 유형 필터와 보관 버전 표시가 그룹 구조에서 정상 동작한다.
- 접근성 및 관리자 브라우저 테스트가 통과한다.
- 신규 DB 마이그레이션 없이 배포 및 롤백할 수 있다.
