## 1. 결론

현재 시스템은 섹션 배경 이미지와 컴포넌트 이미지 생성, 3단 레이아웃, 컴포넌트 아코디언, Web Output 새 창 열기 등 주요 UI 기반은 갖추고 있다. 그러나 다음 세 가지 구조적 문제가 남아 있다.

1. **배경 이미지 생성과 AI 레이아웃 생성의 실행 경계가 분리되지 않았다.**
   배경 이미지만 요청해도 전체 레이아웃 패치가 함께 적용될 수 있어 기존 배치가 무너질 수 있다.
2. **관리자 프롬프트와 실제 이미지 생성 프롬프트가 연결되지 않았다.**
   현재 섹션 AI 프롬프트는 백엔드 코드에 하드코딩되어 있으며, 컴포넌트의 `imagePolicy.promptText`도 실행 스냅샷에서 누락된다.
3. **현재 “컴포넌트” 데이터 모델은 단일 필드형 섹션 아이템이다.**
   텍스트 2개와 이미지 1개 같은 복합 컴포넌트를 지원하려면 UI 수정이 아니라 데이터 모델 전환이 필요하다.

따라서 P0에서는 이미지 생성 안정성과 재시도, 레이아웃 보존, 프롬프트 연결을 먼저 해결해야 한다. 이후 P1에서 복합 컴포넌트, 5단계 프로모션 빌더, 메뉴·용어 정리와 편집 UI 개선을 진행하는 순서가 적절하다.

## 4. 현재 AI 생성 프롬프트 분석

### 4.1 섹션 배경 이미지 요청 기준

현재 백엔드는 다음 순서로 섹션 디자인을 결정한다.

1. 섹션 콘텐츠와 제약 조건을 LLM에 전달한다.
2. LLM은 허용된 컴포넌트, 레이아웃 영역, 스타일 슬롯, 디자인 토큰만 사용해 계획을 만든다.
3. 이미지 설명을 이미지 모델용 프롬프트로 변환한다.
4. 텍스트, CTA, 로고, 배지, 법적 문구가 이미지에 포함되지 않도록 제한한다.
5. DOM 텍스트를 위한 여백을 두고, 섹션 배경색과 가장자리 색이 자연스럽게 연결되도록 요구한다.
6. 페이드·그라데이션·비네팅은 이미지에 직접 넣지 않고 CSS로 처리하도록 요구한다.

관련 구현은 `api/_promo-section-design-provider.js`의 `generateSectionDesignPlan()`, `generateSectionLayout()`, `imagePromptForSafeArea()`에 있다.

현재 배경 이미지의 기본 비율은 16:9이며, Gemini 기본 모델은 `gemini-3.1-flash-image`, 기본 출력 크기는 2K다.

### 4.2 컴포넌트 이미지 요청 기준

컴포넌트 이미지도 섹션 콘텐츠, 이미지 설명, safe area, 배경색을 바탕으로 생성된다. 문제는 다음과 같다.

- `safeArea`가 없는 컴포넌트 이미지도 중앙에 텍스트 여백을 두라는 공통 문구가 추가된다.
- 실행 스냅샷에 컴포넌트의 `imagePolicy.promptText`와 `aspectRatio`가 포함되지 않는다.
- 그 결과 관리자 입력 프롬프트가 실제 생성에 반영되지 않고, 이미지 비율이 대부분 1:1 기본값으로 처리될 수 있다.

따라서 컴포넌트 이미지에는 섹션 배경용 safe area 문구를 적용하지 말고, 해당 필드의 용도·비율·관리자 지침을 독립적으로 전달해야 한다.

### 4.3 관리자 프롬프트 관리 현황

관리자 페이지에는 범용 프롬프트 관리 기능이 있지만 현재 관리 유형은 통합 요약, 이미지 실행, 초안, 최종 디자인 중심이다. 섹션 AI 백엔드는 이 저장소를 조회하지 않고 코드 내부 문자열을 사용한다.

필요한 신규 프롬프트 유형은 다음과 같다.

- `section_layout_planner`
- `section_background_image`
- `component_image`

권장 조합 우선순위는 다음과 같다.

1. 시스템 고정 안전 정책
2. 활성화된 관리자 전역 프롬프트
3. 섹션 또는 컴포넌트별 관리자 지침
4. 사용자가 등록한 실제 콘텐츠에서 추출한 설명

안전 정책, 금지 요소, JSON 스키마와 allowlist는 관리자가 제거할 수 없는 서버 고정 규칙으로 유지해야 한다.

## 5. 주요 문제 분석

### 5.1 P0 — AI 디자인 생성 후 섹션 레이아웃 붕괴

#### 원인

`layoutPatchFromDesignPlan()`은 LLM 결과를 기존 레이아웃에 대한 제한적 변경으로 처리하지 않고 다음 값을 적극적으로 덮어쓴다.

- 배치된 모든 아이템을 `positionMode: "free"`로 변경
- 미리 정의된 영역 좌표 적용
- 이미지 폭을 32%로 지정
- 이미지 비율이 없으면 1:1 사용
- 섹션 최소 높이를 520px로 지정

또한 Create Promo에서 배경 이미지 생성을 요청할 때도 전체 디자인 실행 모드가 사용될 수 있다.

#### 영향

- 관리자가 구성한 레이아웃이 이미지 생성만으로 변경된다.
- 사용자가 수동 조정한 위치·크기·섹션 높이가 손실될 수 있다.
- 잠금되지 않은 모든 요소가 의도치 않게 자유 배치로 바뀔 수 있다.

#### 권장 수정

- `배경 이미지 생성`은 `requestMode: "assets"`만 사용한다.
- `AI 레이아웃 제안`을 별도 버튼과 별도 실행으로 분리한다.
- 레이아웃 패치는 선택된 컴포넌트와 변경 허용 속성만 포함하는 delta 형식으로 제한한다.
- 적용 직전에 템플릿 revision과 잠금 정책을 서버에서 재검증한다.
- 적용 전 미리보기와 적용 취소 또는 Undo를 제공한다.

### 5.2 P0 — 배경 이미지 실패 후 재생성 불가

#### 원인

정상적으로 예외가 처리된 작업은 `failed`로 전환되어 재시도할 수 있다. 그러나 서버리스 실행 중단이나 timeout으로 작업이 `processing` 상태에 남으면 현재 재시도 조건인 `queued` 또는 `failed`에 포함되지 않는다.

#### 권장 수정

- asset job에 `lease_expires_at`, `heartbeat_at`, `next_retry_at`을 추가한다.
- 일정 시간 갱신되지 않은 `processing` 작업을 stale로 판단한다.
- stale 작업을 `queued` 또는 `failed`로 복구하는 API/worker를 둔다.
- 이미지 단계만 다시 실행하며 이미 완료된 레이아웃 결과는 유지한다.
- 재시도 횟수 제한, 지수 backoff, 최종 오류 문구를 제공한다.

### 5.3 P0 — 관리자 프롬프트가 실행에 반영되지 않음

#### 원인

- 섹션 AI provider가 프롬프트 DB를 조회하지 않는다.
- 실행 스냅샷이 `imagePolicy.promptText`와 이미지 비율을 누락한다.
- seed에 등록된 이미지 지침도 실제 호출 경로와 연결되지 않는다.

#### 권장 수정

- 실행 생성 시 활성 프롬프트 버전과 컴포넌트 이미지 정책을 함께 스냅샷한다.
- 실행 이력에 prompt template ID, version, body hash 또는 렌더된 프롬프트를 기록한다.
- 실행 중 관리자가 프롬프트를 수정해도 해당 실행 결과가 재현 가능해야 한다.

### 5.4 P1 — 배경 이미지 폭 60% 요구의 의미 불명확

“가로 60% 이상”은 다음 두 의미를 구분해야 한다.

- **생성 프롬프트:** 주요 피사체가 이미지 캔버스의 60~70%를 차지한다.
- **CSS 표시:** 배경 이미지가 섹션 너비의 최소 60% 이상 보인다.

`background-size: contain`은 원본 비율과 섹션 비율이 다르면 전체 너비를 채우지 못한다. 너비 100% 채우기가 우선이면 `cover`가 필요하고, 이미지 전체 보존이 우선이면 `contain`과 빈 공간을 허용해야 한다.

현재 요구의 중심은 `contain`이므로 기본값은 유지하되 다음 프롬프트 구성을 권장한다.

- 왼쪽 페이드: 주요 피사체는 오른쪽 약 60%, 왼쪽 안전 영역 약 40%
- 오른쪽 페이드: 주요 피사체는 왼쪽 약 60%, 오른쪽 안전 영역 약 40%
- 양끝 페이드: 주요 피사체는 중앙 약 60%, 양끝 각 약 20%
- 페이드 없음: 전체 캔버스를 사용하고 인위적인 안전 영역을 강제하지 않음

CSS 페이드 색은 항상 적용 시점의 섹션 배경색 토큰을 참조해야 한다.

### 5.5 P1 — 복합 컴포넌트 미지원

#### 현재 구조

컴포넌트 버전 하나는 `field_kind` 하나만 가진다. 따라서 텍스트 2개, 이미지 1개가 포함된 카드 같은 컴포넌트를 하나의 재사용 단위로 정의할 수 없다.

#### 목표 구조

컴포넌트 버전 아래에 N개의 컴포넌트 필드를 둔다.

예:

```text
Product Card Component
├─ eyebrow: text
├─ title: text
├─ artwork: image
└─ cta: cta
```

콘텐츠 값은 컴포넌트 인스턴스와 필드 키 조합으로 저장하고, 컴포넌트의 배치와 각 필드의 스타일 슬롯을 구분해야 한다.

### 5.6 P1 — 3단 레이아웃의 가로 스크롤

현재 좌·중·우 3단 구조와 각 패널의 `overflow: auto`는 존재한다. 그러나 레이아웃 열 최소 폭 합계가 임베드된 iframe 너비보다 커질 수 있어 바깥 가로 스크롤이 발생한다.

권장 방향:

- 편집기 외곽은 `overflow: hidden`
- 좌측 `section-list`, 중앙 `preview-stage`, 우측 `property-form`만 독립 스크롤
- 중앙 열의 최소 폭을 반응형으로 줄이거나 좁은 폭에서는 좌·우 패널을 Drawer로 전환
- iframe 자체 스크롤은 제거하고, 실제 프로모션 문서 스크롤은 `preview-stage`가 담당

### 5.7 P1 — 프리뷰 선택과 우측 아코디언 연동 누락

프리뷰에서 컴포넌트를 선택하면 선택 상태는 변경되지만 해당 컴포넌트 아코디언을 여는 상태까지 함께 갱신하지 않는다.

필요 동작:

1. 프리뷰 컴포넌트 클릭
2. 섹션 및 컴포넌트 인스턴스 선택
3. 우측 해당 컴포넌트 아코디언 자동 확장
4. 우측 패널에서 해당 아코디언이 보이도록 스크롤
5. 키보드 포커스는 사용자의 현재 입력을 방해하지 않는 방식으로 이동

### 5.8 P2 — 다중 선택 AI 정렬 및 크기 조절

기능 구현은 가능하지만 LLM이 자유 좌표나 CSS를 직접 반환하게 해서는 안 된다.

권장 명령 allowlist:

- 왼쪽/가운데/오른쪽 정렬
- 위/중앙/아래 정렬
- 가로/세로 균등 배치
- 동일 너비/높이
- 지정 gap으로 그룹 배치

LLM은 선택한 명령과 대상만 결정하고, 실제 좌표 계산은 결정론적 레이아웃 엔진이 수행해야 한다. 잠금 요소 제외, 경계·겹침 검증, 적용 전 미리보기, 한 번의 트랜잭션 적용, Undo가 필요하다.

## 6. 프로모션 빌더 단계 개편 검토

현재 4단계를 다음 5단계로 개편하는 방향은 타당하다.

| 단계 | 권장 명칭 | 주요 내용 |
|---|---|---|
| 1 | 테마 설정 | 배경색, 디자인 토큰 세트, 버튼 스타일 |
| 2 | 프로모션 개요 | 목적, 대상, 핵심 메시지 등 |
| 3 | 템플릿 선택 | 활성 템플릿 선택 |
| 4 | 콘텐츠 및 레이아웃 | 섹션·컴포넌트 콘텐츠, 이미지, 위치·스타일 편집 |
| 5 | 웹 출력 확인 | 검증 결과와 Web Output 새 창 열기 |

“템플릿 레이아웃”만으로 명명하면 콘텐츠 편집이 포함된다는 점이 드러나지 않으므로 4단계는 “콘텐츠 및 레이아웃”이 적절하다.

Web Output은 이미 새 창으로 열 수 있으나 동일 기능 버튼이 여러 위치에 노출된다. 5단계에서 준비 상태와 오류를 확인하고 대표 버튼 하나로 여는 흐름으로 정리하는 것이 좋다.

기존 draft의 `currentStep`, 하위 step 값을 새 단계에 매핑하는 마이그레이션이 필요하다.

## 9. 개발 전 결정 필요 사항

다음 항목은 구현 전에 제품 기준을 확정해야 한다.

1. 섹션 배경 기본 표시 방식은 `contain`을 유지할지, 폭 채우기를 우선해 `cover`로 변경할지
2. “이미지 60%”가 피사체 점유율인지 CSS 표시 폭인지
3. AI 레이아웃 제안 적용 전에 반드시 사용자 승인을 받을지
4. 복합 컴포넌트 전환 시 기존 템플릿 데이터를 초기화할지, 변환할지
5. 기존 AI 실행 이력과 이미지 자산을 보존할지 초기화할지
6. Promo Wizard와 기존 Promo Builder 경로의 유예 기간

권장 기본값은 배경 `contain` 유지, 60%는 피사체 점유율로 정의, AI 레이아웃은 미리보기 후 승인, 기존 경로는 한 릴리스 리다이렉트 유지다.

## 10. 최종 의견

현재 개선안은 방향이 맞지만 한 번의 UI 개편 작업으로 묶으면 안 된다. 가장 위험한 문제는 화면 명칭이 아니라 AI 이미지 요청이 레이아웃 변경까지 일으키는 실행 경계다. 이 문제와 재시도, 프롬프트 추적성을 먼저 해결해야 이후 복합 컴포넌트와 5단계 UX를 안전하게 올릴 수 있다.

특히 복합 컴포넌트는 관리자 UI에 필드를 여러 개 추가하는 수준이 아니다. 컴포넌트 버전, 필드, 인스턴스 콘텐츠, 스타일 슬롯, AI 이미지 타깃의 참조 단위를 함께 변경하는 별도 전환으로 관리해야 한다.
