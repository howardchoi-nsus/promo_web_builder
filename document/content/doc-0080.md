# 자연어 기반 섹션 구성 기능 1차 정리

## 구현 현황 업데이트 (2026-07-25)

검토 결과 동적 컴포넌트 추가는 사용자 프로모션 전용 인스턴스 저장 경계가 확정되지 않아 P3 이후로 유지한다. 이번 개발 반영 범위는 기존 섹션에 포함된 컴포넌트만 사용하는 P0~P2이다.

### 반영 완료

- `section_composition_planner` 프롬프트 유형과 관리자 프롬프트 관리 항목
- 자연어 요청, 현재 섹션 계약, 현재 콘텐츠, 선택된 디자인 토큰을 입력으로 받는 계획 API
- 기존 컴포넌트·필드·스타일 슬롯·AI 선택 가능 토큰만 허용하는 서버 검증
- 자연어 요청은 현재 섹션 전체에 적용하며, 변경 대상으로 언급되지 않은 컴포넌트는 기존 콘텐츠와 배치를 유지
- LLM이 호환되지 않는 디자인 토큰을 선택하면 같은 의미 역할의 허용 토큰으로 보정하고, 대체 토큰이 없으면 해당 스타일만 제외
- 잠금 컴포넌트 및 잠금 필드 변경 차단
- 사용자 요청에 명시되지 않은 CTA URL 생성 차단 및 기존 URL 보존
- LLM이 기존 CTA URL을 반복하거나 빈 URL을 반환하면 신규 URL로 판단하지 않고 현재 URL 유지
- 템플릿·섹션·컴포넌트·토큰 버전 fingerprint와 입력 fingerprint의 적용 직전 재검증
- 적용 전 콘텐츠 변경·토큰 적용·배경 이미지 생성 여부 확인 UI
- 콘텐츠와 레이아웃을 하나의 편집 명령으로 적용하여 단일 Undo 제공
- 선택 시에만 기존 섹션 배경 이미지 asset job 경로 호출
- 자연어 이미지 지침과 안전 영역을 기존 배경 이미지 프롬프트에 전달
- 복합 컴포넌트 필드 단위 디자인 토큰 렌더링

### 의도적으로 제외

- 현재 섹션에 없는 컴포넌트의 자동 검색·추가
- 사용자 프로모션 전용 컴포넌트 인스턴스 영속화
- 부분 적용과 단계별 재시도 이력
- 운영 비용·성공률 모니터링

위 제외 범위는 본 문서의 P3~P5에서 저장 모델과 운영 정책을 확정한 후 진행한다. 이번 범위에는 DB 스키마 변경이 없으며, 새 프롬프트 유형은 기존 프롬프트 초기화 경로에서 자동 등록된다.

- 최초 작성일: 2026-07-25
- 대상 프로젝트: `promo_web_builder`
- 문서 상태: P0~P2 구현 반영, P3~P5 후속 검토
- 대상 화면: 프로모션 빌더의 템플릿 레이아웃 편집 단계
- 주요 범위: 자연어 해석, 컴포넌트 선택, 콘텐츠 입력, 필드별 디자인 토큰, 선택형 섹션 배경 이미지

## 1. 작성 목적

사용자가 섹션에 필요한 내용을 자연어로 설명하면 시스템이 등록된 컴포넌트를 찾아 조합하고, 각 컴포넌트 필드에 콘텐츠와 디자인 토큰을 적용한 뒤 선택적으로 섹션 배경 이미지까지 생성하는 기능을 정의한다.

이 문서는 상세 개발계획서를 작성하기 전 다음 사항을 합의하기 위한 1차 정리 문서다.

- 사용자가 입력하는 자연어의 처리 범위
- LLM과 결정론적 서버 로직의 역할 구분
- 관리자 템플릿과 사용자 생성 결과의 분리
- 컴포넌트 및 컴포넌트 필드의 선택 방식
- 필드별 디자인 토큰 적용 방식
- 섹션 배경 이미지 생성 연계 방식
- 현재 구현에서 재사용할 기능과 추가 구현이 필요한 기능
- 단계별 개발 범위와 주요 위험

## 2. 대표 사용 시나리오

### 2.1 사용자 입력 예시

```text
섹션에 "100% 이벤트 1+1 충전"이라는 타이틀을 쓰고,
세컨드 문구로 "게임에 참가하고 이벤트에 참여하세요"를 적용하고,
"게임 참가" 버튼이 필요해.

타이틀은 크게 표시하고 레드 컬러로 강조해줘.
섹션 배경 이미지도 생성해줘.
```

### 2.2 기대 결과

| 사용자 요구 | 시스템 처리 |
|---|---|
| 메인 타이틀 | 제목 역할을 지원하는 활성 컴포넌트 선택 |
| 보조 문구 | 설명 또는 보조 문구 역할을 지원하는 활성 컴포넌트 선택 |
| 게임 참가 버튼 | Primary CTA 컴포넌트 선택 |
| 큰 타이틀 | 선택된 디자인 토큰 세트에서 허용된 제목 크기 토큰 선택 |
| 레드 컬러 | 선택된 디자인 토큰 세트에서 의미가 일치하는 강조 색상 토큰 선택 |
| 배경 이미지 | 컴포넌트 배치가 확정된 뒤 콘텐츠와 배경색을 기준으로 이미지 생성 |

예상 구성 결과는 다음과 같다.

```text
섹션
├─ 제목 컴포넌트 인스턴스
│  └─ Title 필드: 100% 이벤트 1+1 충전
├─ 설명 컴포넌트 인스턴스
│  └─ Description 필드: 게임에 참가하고 이벤트에 참여하세요
├─ CTA 컴포넌트 인스턴스
│  ├─ Label 필드: 게임 참가
│  └─ URL 필드: 사용자 확인 필요
└─ 섹션 배경 이미지
   └─ 콘텐츠 및 컴포넌트 배치를 기준으로 생성
```

CTA 이동 주소처럼 사용자가 제공하지 않은 필수 값은 LLM이 임의로 생성하지 않는다. 프로모션 개요 등에 등록된 기본 이동 주소를 사용할 수 있으면 재사용하고, 사용할 값이 없으면 누락 항목으로 표시한다.

## 3. 용어 정의

### 3.1 컴포넌트 정의

관리자 페이지에서 등록하고 버전 관리하는 재사용 가능한 구성 요소다. 예를 들어 제목, 본문, CTA, 콘텐츠 이미지 등이 해당한다.

### 3.2 컴포넌트 인스턴스

특정 프로모션의 특정 섹션에서 실제로 사용하는 컴포넌트다. 자연어 구성 기능이 “컴포넌트를 생성한다”는 표현은 새로운 컴포넌트 정의를 만드는 것이 아니라, 기존 활성 컴포넌트 버전을 선택하여 사용자 프로모션에 인스턴스로 추가한다는 의미로 제한한다.

### 3.3 컴포넌트 필드

컴포넌트 안에서 사용자가 콘텐츠를 입력하는 최소 단위다. 한 컴포넌트는 N개의 필드를 가질 수 있다.

예:

- Title 텍스트
- Description 텍스트
- CTA Label
- CTA URL
- Image
- Image Description

### 3.4 스타일 슬롯

컴포넌트 필드에 어떤 종류의 스타일을 적용할 수 있는지 정의하는 자리다.

예:

- `fontSize`
- `textColor`
- `backgroundColor`
- `radius`
- `spacing`

### 3.5 디자인 토큰 바인딩

스타일 슬롯에 선택된 디자인 토큰을 연결하는 결과다. LLM은 `80px`, `red` 같은 자유 형식 CSS를 반환하지 않고, 선택된 디자인 토큰 세트 안에 존재하는 토큰 키를 선택한다.

## 4. 목표와 제외 범위

### 4.1 목표

1. 사용자의 자연어에서 섹션 구성 의도를 추출한다.
2. 허용된 컴포넌트 중 필요한 컴포넌트를 선택한다.
3. 사용자 문구를 적절한 컴포넌트 필드에 연결한다.
4. 선택된 디자인 토큰 세트에서 필드별 토큰을 선택한다.
5. 컴포넌트의 배치와 크기를 결정한다.
6. 사용자가 선택한 경우 섹션 배경 이미지를 생성한다.
7. 적용 전에 변경 내용을 검증하고 사용자에게 보여준다.
8. 부분 실패 시 성공한 콘텐츠와 구성 결과를 유지한다.

### 4.2 제외 범위

- LLM의 신규 컴포넌트 정의 생성
- 임의 HTML, CSS 또는 JavaScript 생성
- 관리자 템플릿 원본의 자동 수정
- 비활성 또는 보관된 컴포넌트 사용
- 관리자가 잠근 콘텐츠 또는 스타일 변경
- CTA URL 등 필수 정보를 임의로 추측
- 선택된 디자인 토큰 세트에 없는 CSS 값을 직접 적용
- 사용자가 선택하지 않은 이미지 모델 호출

## 5. 현재 구현 상태

### 5.1 재사용 가능한 구현

현재 저장소에는 다음 기반 기능이 존재한다.

- `wizard_item_components`: 컴포넌트 정의
- `wizard_item_component_versions`: 컴포넌트 버전
- `wizard_item_component_version_fields`: N개 컴포넌트 필드
- `wizard_content_section_component_instances`: 관리자 섹션에 배치된 컴포넌트 인스턴스
- `promo_design_token_sets` 및 버전·토큰 값: 복수 디자인 토큰 세트
- `section_layout_planner`: 섹션 레이아웃 및 토큰 선택
- `multi_component_layout_planner`: 사용자가 선택한 기존 컴포넌트의 정렬 제안
- `section_background_image`: 섹션 배경 이미지 프롬프트
- `promo_section_design_asset_jobs`: 이미지 생성 작업의 분리, 재시도 및 상태 관리
- 프롬프트 버전 관리, 검증 및 활성화
- 생성 시점과 적용 시점의 템플릿·컴포넌트·토큰·레이아웃 재검증

저장소 기본 시드에는 제목, 본문, 보조 문구, Primary CTA, 콘텐츠 이미지, 로고 이미지, 배지 이미지 컴포넌트가 정의되어 있다.

### 5.2 현재 기능의 한계

현재 `Section Design Planner`는 섹션에 이미 포함된 컴포넌트만 배치할 수 있다.

현재 `multi_component_layout_planner`도 사용자가 이미 선택한 동일 섹션의 컴포넌트만 정렬한다.

따라서 현재 기능만으로는 다음 처리가 불가능하다.

- 자연어에서 필요한 컴포넌트 종류 추론
- 전체 또는 허용 컴포넌트 카탈로그 검색
- 섹션에 없는 컴포넌트 인스턴스 추가
- 사용자 프로모션에만 적용되는 동적 구성 저장
- 복합 컴포넌트의 특정 필드 단위 토큰 선택

## 6. 핵심 설계 원칙

### 6.1 관리자 템플릿과 사용자 결과 분리

프로모션 빌더에서 LLM이 선택한 컴포넌트는 관리자 템플릿 원본을 변경하면 안 된다.

```text
관리자 템플릿
  └─ 사용 가능한 섹션, 컴포넌트, 버전, 잠금 및 AI 정책

사용자 프로모션
  └─ 해당 프로모션에 선택된 컴포넌트 인스턴스와 콘텐츠·스타일 결과
```

현재 관리자 섹션의 컴포넌트 추가 API는 초안 상태의 관리자 섹션을 수정하는 기능이므로 프로모션 생성 결과 저장에 재사용하지 않는다.

### 6.2 LLM은 선택하고 서버는 검증·실행

LLM은 다음만 결정한다.

- 사용자 의도
- 필요한 컴포넌트 역할
- 허용 목록 안의 컴포넌트 버전
- 필드별 콘텐츠 연결
- 허용된 스타일 슬롯과 토큰
- 허용된 레이아웃 영역
- 선택형 배경 이미지 콘셉트와 안전 영역

서버는 다음을 담당한다.

- 컴포넌트 및 필드 ID 검증
- 버전, 상태, 잠금 및 허용 정책 검증
- 디자인 토큰 존재 여부와 의미 역할 검증
- 콘텐츠 길이와 필수 값 검증
- 결정론적 좌표·크기 계산
- 이미지 작업 생성
- 사용자 프로모션 상태 저장
- 적용 및 실행 취소

### 6.3 자유 형식 CSS 금지

LLM은 다음과 같이 직접 스타일 값을 반환하지 않는다.

```json
{
  "fontSize": "80px",
  "color": "red"
}
```

대신 선택된 디자인 토큰 세트에서 토큰 키를 선택한다.

```json
{
  "fieldKey": "fld_title",
  "slotKey": "fontSize",
  "tokenKey": "--promo-title-xl"
}
```

## 7. 권장 사용자 경험

### 7.1 입력 UI

섹션 속성 또는 콘텐츠 패널에 다음 UI를 제공한다.

- `자연어로 섹션 구성` 입력 영역
- `섹션 배경 이미지 생성` 선택 항목
- 이미지 추가 지시사항
- 배경 이미지 페이드 선택
  - 없음
  - 왼쪽
  - 오른쪽
  - 양끝
- `구성 제안` 버튼

### 7.2 결과 검토 UI

LLM 결과를 즉시 최종 저장하지 않고 다음 내용을 비교 형태로 표시한다.

- 재사용할 기존 컴포넌트
- 새로 추가할 컴포넌트 인스턴스
- 제거 또는 숨김 제안
- 필드별 입력 문구
- 필드별 적용 디자인 토큰
- 컴포넌트 배치 및 크기
- 배경 이미지 생성 여부
- 누락된 필수 입력
- 요청과 실제 토큰 사이의 보정 내용

사용자는 전체 적용 또는 부분 적용을 선택할 수 있어야 한다.

### 7.3 적용 후 동작

- Live Preview에 즉시 반영
- 실행 취소 가능
- 컴포넌트 콘텐츠 개별 수정 가능
- 디자인 토큰 개별 변경 가능
- 배경 이미지만 별도 재생성 가능
- 이미지 실패 시 콘텐츠·컴포넌트·레이아웃 결과 유지

## 8. 권장 처리 파이프라인

```text
[사용자 자연어 입력]
        ↓
[입력 정규화]
  문구, 역할, 디자인 요구, CTA, 이미지 요청 분리
        ↓
[Section Composition Planner]
  허용된 컴포넌트와 필드 선택
        ↓
[Composition Validator]
  상태, 버전, 잠금, 개수, 필수 필드 검증
        ↓
[Field Content Mapper]
  사용자 문구를 필드 주소에 연결
        ↓
[Token Selection Planner]
  선택된 토큰 세트 안에서 필드별 토큰 선택
        ↓
[Layout Planner]
  컴포넌트 영역, 순서, 크기 및 안전 영역 결정
        ↓
[선택: Background Image Asset Job]
  콘텐츠·레이아웃·배경색 기준 이미지 생성
        ↓
[최종 Validator]
  컴포넌트·토큰·레이아웃·이미지 정책 재검증
        ↓
[변경 내용 미리보기]
        ↓
[사용자 적용]
```

컴포넌트 배치를 먼저 결정하고 배경 이미지를 나중에 생성해야 한다. 그래야 제목이 왼쪽에 있으면 이미지의 주요 피사체를 오른쪽에 배치하는 등 콘텐츠와 이미지의 충돌을 피할 수 있다.

- LLM은 서버가 제공한 컴포넌트 및 필드 식별자만 반환한다.

- LLM이 임의의 `componentVersionId`, `itemKey`, `fieldKey`, `tokenKey`를 만들 수 없다.
- 결과에는 실행 시점의 컴포넌트 버전과 토큰 세트 버전을 고정한다.

## 10. 컴포넌트 검색 정책

### 10.1 권장 검색 범위

초기에는 전체 글로벌 활성 컴포넌트를 무조건 노출하지 않는다. 다음 순서로 검색 범위를 제한한다.

1. 현재 섹션에 이미 포함된 컴포넌트
2. 현재 템플릿 또는 섹션 정책에서 추가를 허용한 컴포넌트
3. 관리자가 AI 선택 가능으로 표시한 활성 컴포넌트 버전

### 10.2 필요한 의미 메타데이터

컴포넌트 이름과 설명만으로는 안정적인 선택이 어렵다. 다음 메타데이터가 필요하다.

- 역할 태그: `primary-title`, `supporting-copy`, `primary-action`
- 지원 콘텐츠 종류
- 사용 가능한 섹션 유형
- 허용 레이아웃 영역
- AI 선택 가능 여부
- 섹션 내 최대 인스턴스 수
- 함께 사용할 수 있는 컴포넌트 역할
- 필수 필드와 선택 필드
- 필드별 의미 역할

컴포넌트 수가 적은 초기 단계에서는 허용 목록 전체를 LLM에 전달할 수 있다. 컴포넌트 수가 증가하면 태그 기반 후보 검색 후 소수 후보만 LLM에 제공한다.

## 11. 필드별 디자인 토큰 적용

### 11.1 필드 주소

복합 컴포넌트를 지원하려면 기존 `itemKey + slotKey + tokenKey` 주소를 다음과 같이 확장해야 한다.

```text
componentInstanceId 또는 itemKey
+ fieldKey
+ slotKey
+ tokenKey
```

### 11.2 의미 역할 검증

| 스타일 슬롯 | 허용 토큰 의미 |
|---|---|
| `fontSize` | `title-size`, `body-size`, `caption-size` |
| `textColor` | `text-color`, `accent-color`, `muted-color` |
| `backgroundColor` | `surface-color`, `accent-color` |
| `radius` | `radius` |
| `spacing` | `spacing` |

서버는 슬롯과 토큰의 의미 역할이 일치하지 않으면 적용을 거부한다.

### 11.3 요청 값이 토큰에 없는 경우

사용자가 `80px 레드`를 요청했지만 선택된 디자인 토큰 세트에 정확히 일치하는 값이 없을 수 있다.

초기 권장 정책:

1. 의미가 일치하는 가장 가까운 허용 토큰을 선택한다.
2. 정확한 값이 아니라는 사실을 `adjustments`에 기록한다.
3. 의미가 일치하는 토큰이 전혀 없으면 해당 스타일을 미적용한다.
4. LLM이 임의 CSS 값을 만들어 적용하지 않는다.

예:

```json
{
  "requested": "80px red",
  "applied": {
    "fontSize": "--promo-title-lg",
    "textColor": "--promo-accent"
  },
  "adjustments": [
    "80px 토큰이 없어 가장 가까운 72px 토큰을 적용했습니다."
  ]
}
```

## 12. 섹션 배경 이미지 생성

### 12.1 실행 조건

- 사용자가 `섹션 배경 이미지 생성`을 선택한 경우에만 실행한다.
- 자연어에 이미지 요청이 포함되어도 UI 선택이 꺼져 있으면 이미지 모델을 호출하지 않는다.
- 비용과 실행 시간을 사용자가 예측할 수 있도록 이미지 생성 상태를 별도로 표시한다.

### 12.2 프롬프트 생성 기준

배경 이미지 프롬프트는 다음 정보를 사용한다.

- 섹션에 등록된 실제 콘텐츠
- 선택된 컴포넌트와 역할
- 컴포넌트 배치
- 텍스트 안전 영역
- 섹션 배경색
- 선택된 디자인 토큰의 색상 분위기
- 관리자 추가 프롬프트
- 사용자 이미지 추가 지시사항
- 페이드 모드
- 이미지 해상도 설정

### 12.3 이미지 출력 정책

- 이미지 내부 텍스트, CTA, 로고 및 법적 문구 금지
- full-bleed, edge-to-edge 출력
- 외곽 여백, 카드, 프레임, 둥근 외곽 캔버스 및 그림자 금지
- 페이드는 이미지에 굽지 않고 Renderer가 CSS로 적용
- 배경색은 색상 연결 기준으로만 사용
- 이미지 생성 실패 시 컴포넌트와 콘텐츠 결과 유지
- 배경 이미지만 재시도 가능

## 13. 저장 구조 검토

### 13.1 P0 범위

현재 섹션에 이미 존재하는 컴포넌트만 사용하면 기존 `sectionInputs`와 레이아웃 상태를 재사용할 수 있으므로 신규 DB 마이그레이션 없이 1차 구현이 가능하다.

### 13.2 동적 컴포넌트 추가 범위

현재 섹션에 없는 컴포넌트를 사용자 프로모션에 추가하려면 관리자 섹션 인스턴스와 분리된 프로모션 전용 저장 계층이 필요하다.

저장 대상:

- 프로모션 또는 편집 세션 식별자
- 섹션 키
- 선택된 컴포넌트 및 버전
- 서버가 생성한 인스턴스 키
- 필드별 콘텐츠
- 필드별 토큰 바인딩
- 레이아웃 결과
- 배경 이미지 작업 및 결과
- 생성·적용·취소 이력

정확한 테이블 추가 여부와 저장 위치는 프로모션 결과의 현재 영속화 구조를 별도로 분석한 뒤 상세 개발계획서에서 확정한다.

## 14. 검증 및 보안 정책

### 14.1 컴포넌트 검증

- 활성 버전인가
- 현재 템플릿 및 섹션 정책에서 사용 가능한가
- AI 선택 가능 컴포넌트인가
- 최대 인스턴스 수를 넘지 않는가
- 필수 역할이 중복되지 않는가

### 14.2 콘텐츠 검증

- 필드 종류와 값 형식이 일치하는가
- 최대 길이를 넘지 않는가
- 필수 필드가 입력되었는가
- 잠긴 필드를 변경하지 않는가
- CTA URL이 허용된 형식인가

### 14.3 토큰 검증

- 선택된 토큰 세트 버전에 존재하는가
- `aiSelectable=true`인가
- 스타일 슬롯도 AI 선택을 허용하는가
- 슬롯과 토큰의 의미 역할이 일치하는가
- 안전한 CSS 속성으로 변환 가능한가

### 14.4 LLM 출력 검증

- JSON Schema 이외 출력 거부
- 제공하지 않은 ID 반환 거부
- 자유 형식 CSS·HTML·JS 거부
- 관리자 잠금 및 정책 재검증
- 적용 시점의 템플릿·컴포넌트·토큰 버전 재검증

## 15. 실패 및 재시도 정책

기능을 하나의 긴 동기 작업으로 처리하지 않고 단계별 결과를 보존한다.

| 실패 단계 | 유지할 결과 | 재시도 범위 |
|---|---|---|
| 자연어 구조화 실패 | 원본 사용자 입력 | 구성 계획만 재시도 |

| 토큰 선택 실패 | 컴포넌트와 콘텐츠 | 토큰 선택만 재시도 |

### P3. 컴포넌트 라이브러리 자동 검색·추가

| 이미지와 텍스트 충돌 | 가독성 저하 | 레이아웃 확정 후 안전 영역 기반 이미지 생성 |

| 긴 실행 시간 | 사용자 이탈, 함수 제한 | 단계별 비동기 실행 및 상태 표시 |

## 18. 1차 권장 결정

다음 내용을 1차 기본 정책으로 권장한다.

1. LLM은 신규 컴포넌트 정의를 만들지 않는다.
2. LLM은 활성화되고 AI 선택이 허용된 컴포넌트 버전만 선택한다.
3. P0에서는 현재 섹션에 이미 존재하는 컴포넌트만 사용한다.
4. 동적 추가는 프로모션 전용 컴포넌트 인스턴스 저장 구조가 준비된 후 적용한다.
5. 모든 콘텐츠와 스타일은 필드 주소를 기준으로 저장한다.
6. 스타일은 선택된 디자인 토큰 세트의 토큰 키로만 적용한다.
7. 정확한 요청 토큰이 없으면 가장 가까운 허용 토큰을 사용하고 보정 사실을 표시한다.
8. 섹션 배경 이미지는 사용자가 선택한 경우에만 생성한다.
9. 이미지 생성은 컴포넌트 배치 확정 후 실행한다.
10. 적용 전 비교 화면과 실행 취소를 필수로 제공한다.

## 19. 상세 개발계획 전 확인할 사항

1. 컴포넌트 자동 검색 범위를 템플릿 허용 목록으로 제한할지, 전체 활성 라이브러리까지 허용할지
2. 프로모션 전용 동적 컴포넌트 인스턴스를 어느 저장소에 영속화할지
3. CTA URL의 기본 출처를 프로모션 개요로 지정할지
4. 정확한 디자인 토큰이 없을 때 자동 보정할지, 사용자 선택을 요구할지
5. 섹션별 최대 자동 추가 컴포넌트 수
6. 자연어 결과를 자동 적용할지, 항상 비교 화면을 거칠지
7. 배경 이미지 생성 비용과 대기 시간을 UI에서 어떻게 안내할지
8. 컴포넌트 의미 메타데이터를 기존 `capabilities`에 확장할지 별도 필드로 관리할지

## 20. 1차 결론

기능 구현 가능성은 높다. 현재 저장소에는 컴포넌트 버전, N개 필드, 디자인 토큰, LLM 레이아웃, 이미지 asset job 및 적용 재검증 기반이 이미 존재한다.

가장 먼저 구현할 수 있는 범위는 현재 섹션에 존재하는 제목·설명·CTA 컴포넌트에 자연어 콘텐츠를 자동 매핑하고, 필드별 디자인 토큰을 선택하며, 사용자가 선택한 경우 배경 이미지 생성을 연계하는 것이다.

가장 중요한 구조적 과제는 “관리자 템플릿의 컴포넌트 구성”과 “사용자 프로모션에서 동적으로 선택한 컴포넌트 인스턴스”를 분리하는 것이다. 이 경계가 확정되기 전에 전체 활성 컴포넌트 라이브러리에서 임의로 인스턴스를 추가하는 기능을 구현하면 관리자 원본과 사용자 결과가 섞일 위험이 있다.

따라서 P0~P2로 자연어 해석, 기존 컴포넌트 콘텐츠 매핑, 필드별 토큰, 선택형 배경 이미지 흐름을 먼저 검증한 뒤 P3에서 프로모션 전용 동적 컴포넌트 저장 구조를 도입하는 순서를 권장한다.
