## 2. 오늘 확정한 제품 및 구조 방향

### 2.1 용어와 구성 단위

- 섹션(Section): 프로모션 페이지의 가로 100% 단위 영역
- 컴포넌트(Component): 섹션 안에 배치되는 재사용 가능한 UI 묶음
- 컴포넌트 필드(Component Field): 컴포넌트 안에 포함되는 텍스트, 이미지, CTA 등의 실제 입력 요소
- 템플릿(Template): 여러 섹션과 컴포넌트 인스턴스를 조합한 프로모션 페이지 골격
- 디자인 토큰 세트(Design Token Set): 라운드형, 각진형 등 서로 다른 디자인 방향을 제공하는 복수 등록 가능한 토큰 집합

기존처럼 섹션에서 Item을 매번 직접 정의하는 방향이 아니라, 관리자가 다중 필드 컴포넌트를 만들고 섹션에서 해당 컴포넌트를 조립하는 방향으로 진행한다.

### 2.2 AI의 역할

사용자가 AI 기능을 요청했을 때 다음 범위에 AI가 관여한다.

- 섹션 레이아웃 제안
- 선택한 디자인 토큰 범위 안에서 강조 색상과 디자인 속성 선택
- 섹션 배경 이미지 생성
- 컴포넌트 이미지 필드용 이미지 생성
- 향후 여러 컴포넌트의 정렬, 크기 및 배치 제안

AI 응답은 임의 HTML/CSS를 직접 적용하지 않고 서버의 계약, allowlist, 잠금 정책 및 적용 단계 검증을 거친 구조화된 결과만 사용한다.

## 3. P0 구현 내용 — AI 디자인 실행 안정화

### 3.1 요청 목적 분리

섹션 AI 요청을 다음 목적별로 구분했다.

- `layout-style`: 섹션 레이아웃 제안
- `assets`: 섹션 배경 또는 컴포넌트 이미지 생성

이미지 생성 요청은 더 이상 불필요한 레이아웃 planner와 layout patch를 함께 수행하지 않는다. 따라서 이미지 생성 때문에 기존 섹션 레이아웃이 무너질 가능성을 줄였다.

### 3.2 실행 중복 방지 계약 보강

실행 키와 입력 해시 계약을 v2로 확장했다. 다음 값이 달라지면 별도 실행으로 판단한다.

- 요청 모드
- 이미지 대상
- 템플릿 및 설정 revision
- 프롬프트 스냅샷
- 디자인 토큰 및 이미지 옵션
- 섹션 콘텐츠

서로 다른 컴포넌트 이미지 요청이 동일 실행으로 잘못 합쳐지거나, 변경된 프롬프트가 과거 실행에 섞이는 문제를 방지한다.

### 3.3 관리자 관리형 프롬프트

다음 프롬프트 유형을 DB 관리 대상으로 추가했다.

- `section_layout_planner`
- `section_background_image`
- `component_image`

코드에는 초기 기본값을 제공하며, 실제 실행 시 사용한 프롬프트 버전과 내용을 실행 스냅샷에 고정한다. 관리자가 나중에 프롬프트를 변경해도 기존 실행 이력의 재현 근거가 사라지지 않도록 했다.

### 3.4 이미지 생성 기준

- 섹션 배경 이미지:
  - 섹션에 등록된 콘텐츠를 주요 입력으로 사용
  - 설정된 섹션 배경색을 프롬프트에 포함
  - 페이드 옵션 사용 시 배경색과 자연스럽게 연결되도록 요청
  - 전체 캔버스를 사용하는 경우 `safeArea=none`
- 컴포넌트 이미지:
  - 선택한 컴포넌트 필드와 해당 섹션 콘텐츠를 입력으로 사용
  - 결과는 `<img>`가 아니라 조절 가능한 이미지 프레임의 background로 적용
  - 섹션 전체 배경으로 잘못 적용되지 않도록 대상 필드 정보를 검증

Gemini `gemini-3.1-flash-image` 경로는 이미지 응답 형식에 맞는 interactions API 경로를 사용하도록 보정했다.

### 3.5 Asset Job 안정화

Asset Job에 다음 운영 필드를 추가했다.

- lease token 및 만료 시각
- heartbeat
- 재시도 횟수와 최대 횟수
- 다음 재시도 시각과 backoff
- provider 요청 및 응답 메타데이터
- 저장소 및 적용 상태

추가 API:

- `api/promo-section-design-asset-retry.js`
- `api/promo-section-design-apply-complete.js`
- `api/promo-section-design-asset-apply-complete.js`

이미지 생성 실패 후 다시 생성할 수 없던 경로를 보완했고, 이미지 단계만 재시도할 수 있도록 분리했다.

### 3.6 적용 상태 전이

적용 완료를 서버가 먼저 확정한 뒤 클라이언트 반영이 실패하는 문제를 줄이기 위해 다음 순서로 변경했다.

`ready → applying → 클라이언트 저장/반영 → apply-complete → applied`

`applying` 상태가 장시간 남는 경우에는 timeout 복구가 가능하도록 했다. 기존 Asset 전용 완료 경로도 호환용으로 유지했다.

### 3.7 생성 결과 자동 적용

- 섹션 배경 이미지는 생성 성공 후 즉시 적용
- 컴포넌트 이미지도 대상 필드에 즉시 적용
- 별도의 의미 없는 `AI 이미지 적용` 클릭 단계를 제거
- 배경 이미지 적용 시 기존 background color와 레이아웃 속성을 보존
- 컴포넌트 이미지 삭제는 중첩 필드 값을 대상으로 처리

## 4. P1 구현 내용 — 다중 필드 컴포넌트

### 4.1 DB 모델

신규 마이그레이션:

`db/migrations/031_section_ai_v2_and_multi_field_components.sql`

주요 추가 테이블:

- `wizard_item_component_version_fields`

한 컴포넌트 버전에 N개의 필드를 둘 수 있다. 필드 key는 관리자가 직접 입력하지 않고 서버가 다음 형식으로 자동 생성한다.

`fld_<uuid>`

필드에는 타입, 정렬 순서, 필수 여부, 잠금 여부, 이미지 옵션과 관리자 프롬프트 등의 설정을 저장한다.

### 4.2 컴포넌트 API와 저장소

- 신규 컴포넌트 생성 시 여러 필드 저장

- 필드 추가·수정·삭제·정렬 검증
- 마이그레이션 적용 전 기존 DB에서도 조회가 완전히 중단되지 않도록 호환 읽기 경로 유지

### 4.3 관리자 컴포넌트 편집 UI

컴포넌트에 대해 다음 기능을 추가했다.

- 필드 추가
- 필드 삭제
- 필드 복제
- 순서 변경
- 텍스트, 이미지, CTA 타입 선택

- 이미지 비율 설정

섹션 key는 관리자 수동 입력이 아니라 서버에서 `sec_<uuid>` 형식으로 자동 생성하며 관리자 화면에는 자동 생성 값으로 표시한다.

### 4.4 Create Promo 입력 구조

Wizard 입력 schema를 v2에서 v3으로 올렸다.

```json

    "fields": {
      "fld_example": "사용자 입력값"
    }
  }

```

섹션 인스턴스에 연결된 컴포넌트 필드 정의를 기준으로 오른쪽 Contents 패널의 아코디언 입력을 만든다.

### 4.5 Renderer와 Web Output

- 한 컴포넌트 안의 여러 필드를 순서대로 렌더링
- 이미지 필드는 background-image 기반의 조절 가능한 프레임으로 렌더링
- AI 처리 상태 표시
- Preview에서 컴포넌트를 선택하면 오른쪽 해당 컴포넌트 아코디언 활성화
- Web Output은 별도 페이지/창으로 열림

### 4.6 Create Promo 5단계

Create Promo 흐름을 다음 5단계로 정리했다.

1. 배경 및 버튼 스타일 선택
2. 프로모션 개요 등록
3. 프로모션 템플릿 선택
4. 템플릿 레이아웃 및 콘텐츠 편집
5. Web Output 미리보기

세션 저장 key는 `currentStep.v2`를 사용하며 기존 `contentSubstep` 값은 새 단계에 호환 매핑한다.

## 7. 배포 전 필수 작업

### 7.1 최우선 주의사항

`920e06a` 코드는 마이그레이션 `031`의 신규 컬럼과 테이블을 사용한다. **DB 마이그레이션 전에 Production 코드를 배포하면 API 오류가 발생할 수 있다.**

권장 순서:

1. Neon `main`에서 현재 시점 백업 branch 생성
2. 운영 DB 스키마와 마이그레이션 `031`의 적용 여부 조회
3. 백업 branch에서 `031` 사전 적용 및 검증
4. 운영 DB에 `031` 적용
5. 테이블, 컬럼, 인덱스 및 backfill 결과 확인
6. Vercel Production 배포 또는 재배포
7. 관리자 프롬프트 유형과 provider/model 설정 확인
8. 아래 smoke test 수행

### 7.2 프롬프트 확인

설정 화면의 프롬프트 관리 또는 관련 API에서 다음 활성 프롬프트가 존재하는지 확인한다.

- `section_layout_planner`
- `section_background_image`
- `component_image`

권장 provider 설정:

- Layout Planner: 구조화 JSON 응답을 지원하는 LLM
- 이미지 프롬프트: Google Gemini 이미지 모델 또는 지원되는 이미지 provider
- Gemini 모델 사용 시 예: `gemini-3.1-flash-image`

실제 API key와 DB 연결 문자열은 문서나 Git에 기록하지 않는다.

## 8. 알려진 이슈와 위험

### 높음

1. **운영 DB에 마이그레이션 031 미적용**
   - 배포 전 반드시 적용해야 한다.
   - 운영 DB는 오늘 변경하지 않았다.

2. **실제 provider 기반 최종 E2E 미검증**
   - 자동 테스트는 fixture와 mock을 포함한다.
   - Gemini, Private Blob, 실제 DB 상태 전이를 Production에서 별도로 확인해야 한다.

3. **Asset Job heartbeat가 주기적 갱신 방식은 아님**
   - claim과 주요 처리 시점에는 기록하지만 장시간 이미지 생성 중 별도 timer가 주기적으로 heartbeat를 갱신하지 않는다.
   - 현재 lease는 충분히 길게 잡았지만 provider 응답 지연이 길면 중복 claim 가능성을 추가 점검해야 한다.

### 중간

1. **좁은 화면의 3단 편집기**
   - 데스크톱 3단 구조를 우선 반영했다.
   - Drawer 전환 경계와 외부 가로 overflow 여부를 실제 1023/980/768/390px에서 다시 검증해야 한다.

2. **중첩 이미지 필드의 세부 스타일 편집**
   - AI 생성, 즉시 적용, 삭제와 기본 background 렌더링은 지원한다.
   - 모든 이미지 필드에 대해 자유 비율 resize, 원형, radius, contain/cover 등의 UI가 기존 단일 이미지 기능과 완전히 동일한지는 추가 검증이 필요하다.

3. **이전 독립 페이지 정리**
   - Promo Wizard, Visual Editor, 생성된 UI는 메뉴에서 숨겼지만 URL과 코드는 호환 목적으로 남아 있다.
   - 즉시 삭제하지 말고 사용 경로와 데이터 의존성을 확인한 후 단계적으로 제거해야 한다.

4. **AI Run 집계 경계 조건**
   - ready/failed/cancelled가 섞인 여러 Asset Job의 최종 집계와 최대 재시도 종료 조건은 실제 DB 동시성 테스트가 필요하다.
