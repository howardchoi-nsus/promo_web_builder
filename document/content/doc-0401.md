# V3 프롬프트별 역할·구성·업무 경계 검토

> 후속 결정 안내(2026-11-23): 본문은 당시 코드 검토/분리 제안이다. 사용자 구성 승인·재승인·히어로 기본형 관련 과거 제안은 현재 정책이 아니다. 최신 기준은 AGENTS.md 및 통합 개발 계획 26절의 디자인 품질 우선·사용자 최소 액션·내부 자동 검증을 따른다.

2026-11-23 · 1차 분석 문서 · **운영 프롬프트 교체본 아님**

## 0. 목적·검토 기준

요청 내용과 생성 결과가 불명확해지는 문제를 줄이고 단계별 품질을 높이기 위해, 각 프롬프트의 책임과 결과물을 명시한다.

요청한 항목에 따라 각 프롬프트를 **① 역할 ② 구성 내용: 정책/스킬/그 외 ③ 검토 의견: 수정/분리 ④ 권장 업무 경계·완료 기준**으로 정리한다. 사용자가 비워 둔 4번은 이 문서에서 검증 가능한 업무 구분 항목으로 제안한다.

### 확인 범위와 상태

- 현재 저장소 코드의 호출 경로·입력 변수·응답 계약·검증 코드를 기준으로 한다. 최신 로컬 디버깅 변경도 작업 트리에 포함되어 있으므로 이를 모두 Production 상태라고 간주하지 않는다.
- 생성 관련 프롬프트 MD 7종과 관련 스킬·서버 조립 코드를 검토했다. 개요 분석 및 기존 컴포지션 프롬프트는 호출·변수·응답 계약을 확인했으나 **Admin DB의 실제 활성 본문·연결 스킬·모델은 확인하지 못했다.** 아래 구성 분류는 확인한 본문/계약의 분류이며 숨겨진 Admin 본문을 추정한 것이 아니다.
- `[현행]`은 코드/문서에서 확인한 동작, `[수정 제안]`·`[분리 제안]`은 후속 반영 검토 사항이다.
- 상세 중복/추가 이력은 같은 폴더의 `policy-skills-prompts-consolidated-review-2026-11-23.md`와 함께 본다. 본 문서는 그 내용을 **프롬프트별 업무**로 재구성했다.

## 1. V3 범위와 실행 흐름

V3는 제품/컴포지션 경로 이름이다. `작업 계획 V2`는 점진적 초안 계약 버전, `page-schema-v1`은 저장 스키마 버전이다. 숫자가 다르다고 다른 제품이나 중복 프롬프트로 판단하면 안 된다.

```text
고객 자연어
  → A1 개요 분석
  → 고객의 요청 요약 확인/자연어 보완
  → 누적 생성 활성: A2 작업 계획 → A3 영역 구성 × 실제 작업 수 → 서버 최종 조립
    누적 생성 비활성/전체 구조 수정: A4 전체 PageSchema 설계
  → 채팅 구성 승인
  → 영역 디자인 활성: A5 영역 디자인 × 실제 그룹 수
  → 필요한 이미지마다 A6 배경 이미지 또는 A7 컴포넌트 이미지
  → 브라우저 측정·규칙 보정
  → 품질 에이전트 활성: A8 검토/제한 보정 → 브라우저 재검사
  → 현재 Revision 품질 통과 → 출력/에디터
```

- A2와 A4는 기본적으로 **대체 생성 경로**이며 매 요청마다 모두 실행하는 고정 단계가 아니다. A4는 기존 페이지 수정·모바일 전용 수정에도 사용될 수 있다.
- A5/A6/A7은 영역별로 이어질 수 있으며 모든 스타일 작업 후에만 모든 이미지가 시작되는 단일 일괄 순서를 뜻하지 않는다.
- A6/A7은 이미지가 필요한 경우에만 실행한다. 프롬프트 하나가 1회만 실행된다고 가정하지 않는다.
- 구성 승인·JSON/소스/토큰 검사·DB 저장·스웜 효과·브라우저 검사·출력 권한은 프롬프트가 아닌 애플리케이션의 책임이다.
- 코드 기본값에서 `pageSchemaV1=true`, `compositionV3=true`, `pageDraftV1=false`이며 운영 환경변수는 별도다. 현재 운영 경로를 기본값만으로 확정하지 않는다. 별도 `serviceContractV3` 플래그도 제품 V3 전체 활성 여부와 같지 않다.

## 2. 책임을 구분하는 기준

| 분류 | 소유할 내용 | 예시 | 프롬프트와의 관계 |
|---|---|---|---|
| 정책 | 반드시 지킬 제품/안전/승인/디자인 제약 | 등록 토큰만, 사실 보존, 승인 전 구조 결정, 이미지 속 문구 금지 | 서버 입력·검증으로 강제하고 호출별 최소 지침 유지 |
| 스킬 | 정책 안에서 더 좋은 결과를 선택하는 방법 | 히어로 구도, 정보 계층, 이미지 여백, 반복 리듬 | 단계에 맞는 등록 버전을 연결. 권한·스키마를 변경하지 못함 |
| 그 외: 역할·작업 | 이번 호출이 수행할 업무 | 빈 계획 작성, 단일 영역 생성, 스타일 패치 | 프롬프트 본문이 명확히 소유 |
| 그 외: 입력 데이터 | 판단의 근거 | 고객 요청, 개요, 소스, 현재 문서, 후보, 측정 보고 | 명령·권한 부여와 구분 |
| 그 외: 출력 계약 | 반환 형식과 범위 | manifest, subtree, PageSchema, patches, 이미지 | 코드의 실제 스키마와 일치해야 함 |
| 그 외: 실행 제어 | 호출·저장·검사·재시도 상태 | CAS/lease/Revision/작업 완료/브라우저 QA | 서버/프런트엔드가 소유. 모델이 성공을 선언하지 않음 |

## 3. 현재 PageSchema 경로 — 프롬프트별 상세

### A1. 프로모션 개요 분석 — `promo_overview_parser`

**① 역할**

고객의 자연어를 다음 단계가 사용할 구조화 요구사항과 콘텐츠로 변환한다. 레이아웃 설계나 이미지 제작을 수행하는 단계가 아니다.

**② 구성 내용 분석**

| 구분 | 확인 내용 |
|---|---|
| 정책 | 지원된 enum·사실 보존·입력 신뢰 경계·미정 사실 취급 등의 공통 계약. 실제 활성 본문은 DB 확인 필요 |
| 스킬 성격 | 섹션/반복 항목으로 콘텐츠 구조화, 사용자 문구와 편집적 보완 구분. 본문에 포함되는 판단 방법과 별도 연결 스킬은 구분 필요 |
| 그 외: 입력 | 필수 `naturalLanguage`, `allowedValuesJson`; 선택 `generationMode`, `currentOverviewJson`, `productCatalogJson`, `localeAndMarketJson` |
| 그 외: 출력 | `OVERVIEW_PARSE_SCHEMA`에 맞는 개요 분석 결과. 서버 정규화 이후 overview·누락/결정 등 관련 결과를 API가 반환 |
| 실행 제어 | 서버가 prompt execution snapshot 생성·모델 호출·결과 정규화. 현재 호출은 currentOverview를 주면서 generationMode를 `new-draft`로 전달 |

**③ 검토 의견**

- `[수정 제안]` 고객이 확정한 사실, AI가 보완한 편집 문구, 미정 사실을 서로 혼동하지 않게 명시한다. 누락 항목은 자동 생성 차단이나 필수 폼이 아니다.
- `[수정 제안]` 이미지 의도와 고객이 지정한 구도를 보존한다. 이 단계가 정한 콘텐츠 순서를 곧 최종 DOM 순서로 고정하지 않는다.
- `[수정 제안]` 수정 요청에서도 `generationMode=new-draft`로 전달되는 의미가 적절한지 재검토한다. mode 이름만 수정 모드로 바꾸기보다 currentOverview/수정 우선순위/회귀를 함께 검증해야 한다.
- `[분리 제안]` 콘텐츠 구조화 방법은 분석 스킬, enum/사실/금지 조건은 공통 정책, 필드 매핑·응답 계약은 프롬프트/서버로 나눈다.

**④ 권장 업무 경계·완료 기준**

고객 요청이 소스와 이미지 의도를 잃지 않고 개요로 전달되어야 한다. 레이아웃·최종 색상·렌더링 완료를 선언하지 않는다. 필수 사실이 미정이면 발명하지 않고 제외/표시하며 다음 처리에 미정임을 전달한다.

출처: `api/promo-overview-parse.js`, `api/_promo-overview-contract.js`, `api/_prompt-template-store.js`.

### A2. 페이지 제작 · 작업 계획 V2 — `promo_page_manifest_planner`

**① 역할**

완성 페이지 대신, 순서·부모 관계·영역 책임·소스 배정이 있는 가벼운 작업 계획을 만든다. 빈 스켈레톤의 구조적 출발점이다.

**② 구성 내용 분석**

| 구분 | 확인 내용 |
|---|---|
| 정책 | 허용 소스/토큰·사실 발명 금지·고정 템플릿 금지·페이지/그룹 역할·깊이/개수 제한 |
| 스킬 성격 | 섹션 수·중첩·비율·반응형·작업 분할 판단이 본문에 포함됨. 현재 전체 구조 스킬의 Scope는 이 타입을 명시하지 않음 |
| 그 외: 입력 | `overviewJson`, `candidateSnapshotJson`, `constraintsJson`; 공통 브리프·후보·previewContract·이미지 요구 등 서버 데이터 |
| 그 외: 출력 | `contractVersion:2`, 빈 `root`, 1~12 `regions`(shell/parentId/intent/sourceIds), summary. 셸 children/sourceIds는 비어 있어야 함 |
| 실행 제어 | 서버가 검증·저장 후 전체 계획의 빈 스켈레톤 표시. 계획 중 가짜 완료 비율을 반환하지 않음 |

**③ 검토 의견**

- `[수정 제안]` ‘페이지를 설계한다’와 ‘작업 계획만 만든다’의 차이를 첫 문장과 출력 설명에서 유지한다. 완성 문구/컴포넌트 트리를 요구하지 않는다.
- `[수정 제안]` 히어로 배경형/분리형과 콘텐츠 관계를 계획 의도에 명확히 남긴다. 모든 제목을 배경형으로 만들지 않는다.
- `[수정 제안]` 셸의 레이아웃을 여기서 정하면 A3는 그 셸 속성을 변경하지 못한다. 그래서 이 단계의 비율·폭·중첩 결정이 품질에 직접 영향을 준다. 빈 계획이라는 이유로 구조 판단을 소홀히 해서는 안 된다.
- `[분리 제안]` 별도 ‘작업 계획 스킬’을 두고 소스 배정/작업 분할/가벼운 구조 판단을 담당시킨다. 전체 PageSchema 반환 지침은 연결하지 않는다.

**④ 권장 업무 경계·완료 기준**

필수 소스가 중복 없이 배정되고 부모/순서/깊이가 유효해야 한다. 아직 문구·이미지·전체 하위 트리를 완성하지 않는다. 각 단위가 후속 노드 한도 안에서 생성될 수 있어야 한다. 계획 저장 후에만 스켈레톤을 노출한다.

출처: `docs/mouse-swarm-builder/prompts/page-unit-plan.md`, `api/_page-draft-service.js`, `api/_page-draft-units.js`.

### A3. 페이지 제작 · 영역 구성 V2 — `promo_page_region_builder`

**① 역할**

현재 작업 단위 하나의 실제 컴포넌트 구조·콘텐츠 연결·이미지 요청을 구성한다. 전체 페이지를 다시 설계하지 않는다.

**② 구성 내용 분석**

| 구분 | 확인 내용 |
|---|---|
| 정책 | 해당 셸·배정 소스·예약 ID 보존, 임의 사실/CSS 금지, 다른 영역 수정 금지, 단위 48노드 제한 |
| 스킬 성격 | 텍스트/카드/이미지/CTA의 내부 배치·정보 계층·헤딩 순서·연속성 판단 |
| 그 외: 입력 | `overviewJson`, `candidateSnapshotJson`, `constraintsJson`; 현재 region·manifest·저장 page·브리프·단위별 이미지 요구 |
| 그 외: 출력 | `node`, `sourceAssignments`, `mediaRequests`. 전송은 compact 형식, 서버가 전체 PageSchema 형태로 복원 |
| 소스 계약 | 빈 text·빈 sourceIds·editorial mode로 노드를 보내고 `sourceAssignments`를 통해 서버가 승인 source mode로 결합 |
| 실행 제어 | 검증·저장 후 그 단위만 반영. 마지막 단위 저장과 최종 조립은 별도 요청 |

**③ 검토 의견**

- `[수정 제안]` 구조 생성, 편집 문구 작성, 사실 결합, 이미지 요청의 네 하위 업무를 본문에서 명확히 구분한다. 이미지 파일을 여기서 생성하는 것은 아니다.
- `[수정 제안]` 배경형 히어로라면 배경 이미지 노드와 전경 텍스트/CTA 관계를 승인 전에 실제 구조로 만들어야 한다. A5에 구도 수정을 넘기지 않는다.
- `[수정 제안]` 본문과 스킬의 소스 결합 방식 충돌을 주의한다. 기존 전체 구조 스킬은 직접 source mode를 요구하지만 이 타입은 sourceAssignments 경로를 사용한다. 그대로 공통 연결하면 충돌할 수 있다.
- `[분리 제안]` ‘영역 구조 스킬’을 별도로 둔다. 정책/경계는 유지하고 구도·밀도·위계 판단을 재사용한다. 역할별 여러 모델 호출로 무조건 분리할 필요는 없다.

**④ 권장 업무 경계·완료 기준**

현재 단위의 소스와 명시된 이미지 요구가 누락되지 않고, 셸·기존 단위를 보존한 유효 subtree여야 한다. non-heading level=0, heading=1~6 등 실제 검증 조건을 따른다. 미디어 요청 연결과 이미지 제작 완료는 구분한다. 실패한 단위는 저장하지 않고 완료 단위는 보존한다.

출처: `prompts/page-unit-region.md`, `api/_page-draft-units.js`, `api/_page-draft-compact.js`, `api/_page-image-requirements.js`.

### A4. AI 동적 페이지 구조 설계 — `promo_page_schema_planner`

**① 역할**

전체 PageSchema를 한 번에 설계하거나 기존 페이지를 자연어로 수정한다. V2의 ‘전체 계획→영역 구성’과는 출력 범위가 다른 경로다.

**② 구성 내용 분석**

| 구분 | 확인 내용 |
|---|---|
| 정책 | 선언형 구조·등록 토큰·소스 보존·안전 URL·현재 수정 범위·반응형·접근성·노드 한도 |

**③ 검토 의견**

- `[수정 제안]` 한 타입이 신규 생성·전체 수정·선택 수정·모바일 수정을 모두 담당하므로 실행 목적과 허용 범위를 호출마다 분명히 전달해야 한다.

- `[수정 제안]` A2/A3와 동일한 히어로·이미지 요구 기준을 적용한다. 경로마다 다른 구도 기본값을 갖지 않도록 한다.
- `[수정 제안]` ‘전체 트리를 반환한다’는 사실이 ‘원치 않는 전체 변경을 허용한다’는 뜻은 아니다. 보존 대상과 허용 범위는 별도로 명시한다.

- `[수정 제안]` DOM 오버레이 금지/허용 토큰과 이미지 안의 자연스러운 명암은 구분한다. 이미지의 모든 픽셀을 CSS 토큰으로 제한하지 않는다.

공통 브랜드 방향을 따르고 제목/CTA와 피사체가 충돌하지 않을 구도가 목표다. 이미지 생성 응답만으로 페이지 준비 완료를 선언하지 않는다. 서버 저장·소스 연결·브라우저 load/decode·전체 품질검사가 별도로 필요하다.

## 4. V3 기존 컴포지션·편집 경로의 프롬프트

아래 타입은 저장소에 존재하며 V3 기능과 관련된다. 현재 PageSchema 주 경로와 동일한 호출 계약으로 혼합하면 안 된다. 운영 플래그/화면/기존 문서에 따라 실제 사용 여부가 달라지므로 단순히 ‘미사용’ 또는 ‘삭제 대상’으로 분류하지 않는다. 실제 활성 본문을 못 본 항목은 **수정 필요 확정이 아닌 계약 기준 검토**다.

| 타입 | ① 역할 | ② 정책 / 스킬 성격 / 그 외 | ③ 수정·분리 검토 | ④ 경계·완료 기준 |
|---|---|---|---|---|
| `promo_page_composer` | 후보 섹션·레이아웃·컴포넌트 기반 페이지 구성/수정 | 정책: 등록 후보/소스/허용 구성. 스킬: 후보 선택·페이지 리듬. 그 외: overview/candidate/constraints와 컴포지션 결과 | A4와 이름이 비슷해 자유 PageSchema 생성으로 혼동 가능. ‘후보 기반 컴포지션’으로 명시하고 구도 정책만 공유 | 허용 후보/콘텐츠 경로를 사용한 유효 composition. 범용 subtree와 혼합 금지 |
| `promo_composition_editor` | 기존 컴포지션 수정 작업 제안 | 정책: 허용 operation/기존 문서 보호. 스킬: 변경 의도 해석. 그 외: instruction/currentSnapshot/allowedOperations | 신규 생성과 수정 계약 분리. 반환 작업과 실제 적용을 구분 | 허용 작업만 제안, Revision 검증 뒤 서버 적용 |
| `section_composition_planner` | 선택 섹션의 컴포넌트 구성 수정 | 정책: 허용 요소/소스/토큰. 스킬: 내부 정보 구조. 그 외: instruction/section/content/constraints/tokenSet | 섹션 구성과 스타일/정렬 업무를 구분. generateBackgroundImage/imageGuidance 선택 입력이 실제 이미지 실행을 의미하지 않도록 설명 | 선택 섹션 범위만 유효한 구성 결과 |

| `promo_page_outline_planner` | 구버전 누적 초안의 전체 outline | 정책/스킬/입력 계약이 새 manifest와 다름. 기존 draft 복원 호출 | 새 계획 타입으로 무조건 치환하지 않음. 신규 생성 기본과 복구 경로 표기 | 진행 중 구버전 draft를 해당 계약으로 복원 |

호출 근거: `api/_promo-page-composition-service.js`, `promo-page-composition-proposals.js`, `promo-page-composition-operations.js`, `promo-section-composition-plan.js`, `promo-section-design-runs.js`, `promo-multi-component-layout-plan.js`, `_page-draft-legacy-service.js`.

컴포넌트 시각 분석·레퍼런스 분석·프롬프트 번역·템플릿 추천·과거 이미지/최종 생성 타입은 별도 보조 경로다. 전체 27종 목록은 앞선 통합 문서 부록에 있고, 이름만으로 현재 V3 기본 여정에 모두 포함하지 않는다.

| 1 | 히어로 구도를 A5가 해결할 것으로 기대 | 승인 후 구조 보존 때문에 배경형 변경 불가 | A2/A3 또는 A4에서 구도 확정, A5는 등록 스타일만 |

## 6. 권장 Admin 설명 형식

각 프롬프트 관리 항목에 다음 설명을 동일한 순서로 제공하는 것을 권장한다. 이는 관리 메타데이터 제안이며 현재 Admin UI 구현 완료를 뜻하지 않는다.

1. **실행 목적:** 한 문장으로 책임 정의.
2. **호출 조건:** 신규/수정/영역별/이미지 필요/검사 필요 등.
3. **입력:** 필수 변수와 JSON 내부에 실제 전달되는 주요 근거.
4. **반환 결과:** 실제 응답 스키마와 결과 소비자.
5. **허용/금지 범위:** 변경할 필드와 보존할 필드.
6. **공통 정책:** 적용 정책 버전·필수 경계.
7. **연결 스킬:** 해당 단계의 스킬 버전과 역할.
8. **완료 기준:** 모델 응답 유효성과 서버 저장/실제 표시/검사 완료 구분.
9. **실패·재시도:** 재시도 단위·완료 결과 보존·보정 한도.
10. **검증 기록:** 현재 프롬프트/모델/스킬 조합으로 수행한 테스트와 미검증 범위.

예: **영역 구성 V2** — “승인 전 작업 계획의 한 영역을 실제 범용 컴포넌트 구조로 구성하고 배정 콘텐츠·이미지 요구를 연결합니다. 전체 페이지 재생성·이미지 파일 생성·최종 디자인/품질 승인은 수행하지 않습니다.”

## 7. 후속 정리 순서와 완료 조건

1. 실제 Admin 활성 프롬프트·스킬 연결·모델/옵션·환경 플래그를 목록화해 이 문서의 코드 기준과 대조한다.
2. 정책 원본과 스킬 소유 업무를 확정한다. 히어로 기본/예외는 정책, 구도 판단은 스킬, 이번 타깃/출력은 프롬프트에 둔다.
3. 계획·영역·전체 구조의 스킬 범위를 분리한다. 이미 적용한 마이그레이션을 수정하지 않고 새 Draft로 관리한다.
4. 입력/출력·허용 변경 범위를 기준으로 프롬프트 Draft를 보정한다. 기존 필수 변수·등록 모델 설정을 보존한다.
5. 대표 요청·명시 이미지·이미지 없음·배경/분리형·모바일/선택 수정·실패/재시도·구버전 복구를 검증한다.
6. 코드/DB/프롬프트/스킬/토큰 조합과 실제 모델 여정을 확인한 뒤 운영 활성화를 판단한다. 로컬 테스트를 실제 모델 검증으로 표현하지 않는다.

**이 문서는 분석·업무 분리 제안이다. 프롬프트 본문·스킬 연결·정책 강제 코드·운영 활성화·배포를 변경하지 않았다.**
